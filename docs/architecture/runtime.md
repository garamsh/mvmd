# Runtime

What mvmd owns on a node, its boundary with gaon, and the invariants it provides.

## Boundary with gaon

mvmd is a node-local microVM runtime, the kind of component containerd is to Kubernetes. It does not know gaon, imports nothing from gaon, and does not define gaon's resource API, Lease or epochs. gaon's Node Agent is its client and the dependency runs gaon to mvmd only (#2 decision-change reply; §3 principle 3).

| Concern | Owner | Source |
|---|---|---|
| Runtime API definition and versioning | mvmd | #2 decision-change reply |
| Machine lifecycle execution on the node | mvmd | #2 decision-change reply |
| Image pull, MachineImage conversion, node image cache | mvmd | #2 decision-change reply; §5 image section |
| Snapshot store | mvmd | #2 decision-change reply |
| VMM Drivers and the Guest Agent | mvmd | #2 decision-change reply |
| Local fencing deadline mechanism | mvmd | #2 decision-change reply |
| Watch, Lease renewal, epoch checks, status reports | gaon Node Agent | #2 decision-change reply |
| The decision to run, wake, suspend or stop a Machine | gaon Node Agent | #2 decision-change reply; §3 wake case |
| Desired state, binding and epochs | gaon | #2 §3 state ownership table |
| Cells, the global layer, Gateway and Cell Router | gaon | #2 §3 stability structure |

mvmd executes what its client asks and reports what happened. Wake signals from the Gateway and Cell Router go to gaon's Node Agent, which decides and calls mvmd.

## Runtime API scope

The runtime API models a Machine, not a Pod or a container, and is not CRI (#2 §1 conclusion; decision-change reply). Its scope:

- Machine create, start, stop, pause, resume, snapshot and restore.
- Disk attach and detach, and resource resize.
- Inspect, list and events.
- Exec, a file API and a console.
- Runtime info, which reports what the node has: its Drivers, and its CPUs, memory and the space of its state directory's filesystem. The node reports these as facts and admits no call by them; whether a Machine fits is the client's decision ([ADR 0039](./adr/0039-runtime-info-reports-the-nodes-capacity-and-mvmd-admits-no-call-by-it.md)).
- List snapshots and delete a snapshot. A snapshot is a public resource of the runtime API: the identifier a client gives Snapshot is the one it gives Restore, and the client sees what the node holds and removes it ([ADR 0034](./adr/0034-the-node-reclaims-nothing-by-its-own-policy-and-the-runtime-api-lists-and-removes-what-it-holds.md)). Its files stay inside the node.

mvmd defines and versions it. Each operation states its idempotency and the state a Machine is left in after a failure (#2 §3 principle 5). The contract is published as `lib/runtimeapi/` and is a leaf module ([structure.md](./structure.md) §Repository layout). Its operations, calling rules and version are in [runtime-api.md](./runtime-api.md).

## State and stability

mvmd owns the actual VM state on its node and the snapshot and image caches; their files are not exposed outside it, and a client sees a snapshot only through the runtime API's list and delete (#2 §3 state ownership table). Desired state, binding and epochs are its client's.

- VMs survive an mvmd restart, until the recorded fencing expiry. The VMM runs as a separate process under its supervisor (§Fencing). Before serving any call, mvmd reattaches to each supervisor through its socket in the Machine's state directory, then to the VMMs through the Driver's `List` (#2 §5 design principle 4; [driver.md](./driver.md)). A VMM's end while mvmd runs reaches the daemon through the supervisors it already lists, since a supervisor exits with its VMM, and not through the guest: the daemon lists them every second and moves a Running or Paused Machine that has none to Stopped, and the start-up reconciliation does the same for one that ended while mvmd was down ([ADR 0033](./adr/0033-a-vmm-that-ends-on-its-own-moves-its-machine-to-stopped-with-the-reason.md)).
- mvmd keeps its own state durably on local storage and continues after a restart (#2 §3 stability structure, the node as the reference for actual state).
- **The store is bbolt**, one database file, `mvmd.db`, in mvmd's state directory (the daemon's configuration names it). It holds the Machine records with their request IDs, the fencing deadline record and each Machine's exec records, a bucket each (`machines`, `deadline`, `execs`). A write returns once its transaction is committed and the file synced, which the fencing rule "acknowledged only after durably recorded" needs ([runtime-api.md](./runtime-api.md) §Fencing deadline). It is embedded and pure Go, and one process holds the file at a time.
- **A Machine record holds its run configuration, secrets included** ([ADR 0051](./adr/0051-create-machine-takes-a-command-args-env-user-and-files-which-the-machine-keeps-and-sends-at-every-boot.md)). The command, args, env, user and files Create Machine was given are in the Machine record, so every boot sends the guest the same ones. Env values and file content may be Secret data: they are in this database file, which only the daemon's user reads, and in the daemon's memory while the record is held, and in no response, event, error or log. A snapshot does not carry them.
- **Snapshots are files beside it**, in a `snapshots/` directory of mvmd's state directory: one directory per snapshot holding its root disk copy, its state files and its record, with a `staging/` directory for snapshots being built or removed, which the Snapshot Store adapter empties when it opens. The record is not in bbolt, so a snapshot becomes visible by one rename. `snapshots/` must be on the same file system as the Machines' run directories, because a Put takes the Driver's state files in by rename; on another file system Put fails and leaves the files where they were. A Put makes each state file owned by mvmd's own user and group, mode 0444, before the publishing rename, so the VMM of any restoring Machine, a user of its own, can read them through the read-only bind of its root, and no other host user reaches the store's 0700 directories; the root disk copy stays 0600 ([ADR 0031](./adr/0031-the-snapshot-store-publishes-a-snapshots-state-files-owned-by-mvmd-and-read-only.md)).
- **Disks are files beside them**, in a `disks/` directory of mvmd's state directory, which the Disk adapter alone creates, reads and removes ([ADR 0021](./adr/0021-a-root-disk-is-a-file-in-the-disks-directory-of-mvmds-state-directory.md)): one file per Machine for its root disk, and one per disk the runtime API's Create disk made, which keeps the request that made it as an extended attribute of the file ([ADR 0036](./adr/0036-the-runtime-api-creates-lists-and-deletes-a-node-local-disk-through-the-disk-adapter.md)). No file is published over another. A Machine's state directory is the supervision adapter's, made at start and removed by Delete Machine after the root disk and before the record, so no hard link to a disk file outlives the Machine; the removal fails while the Machine has a supervisor, a failure fails Delete Machine and keeps the record so that a repeat retries it, and the start-up reconciliation removes the state directory of a Machine the State Store does not hold. A root disk exists before any start and outlives a stop. A restore's root disk is a sparse copy of the snapshot's, made in `disks/` under a temporary name and published by rename. A disk file is owned by the user of the Machine that holds it, and by mvmd's own user when no Machine does, so the VMM's user can open what it is attached ([ADR 0038](./adr/0038-a-disk-file-belongs-to-the-machine-that-holds-it.md)).
- Running Machines keep running while the control plane or the client is down, until the fencing deadline passes, whether or not the mvmd process is running (#2 §3 stability structure, static stability).
- Lease, epochs, cells and the global layer belong to gaon.

## Fencing

If gaon's Node Agent dies while mvmd keeps VMs running, a rescheduled Machine could run on two nodes (#2 §4 invariant 1). mvmd therefore holds a deadline its client renews; when the deadline is not renewed in time, mvmd stops every Machine under it. The client sets the length of the deadline; the mechanism is mvmd's (#2 decision-change reply). How the client sets and renews it, and what holds across an mvmd restart, is in [runtime-api.md](./runtime-api.md) §Fencing deadline. The expiry is enforced whether or not the mvmd process is running: a VM runs at most δ past a recorded expiry, where δ is the time the enforcing process takes to end the VMM. The guarantee covers failures of mvmd, of the enforcing process and of the host, not a privileged host process acting on the enforcing process, and the client's margin covers δ ([runtime-api.md](./runtime-api.md) §Fencing deadline).

How it is enforced ([ADR 0003](./adr/0003-a-per-machine-supervisor-enforces-the-fencing-expiry.md)):

- **A supervisor per Machine.** Every Machine whose VMM process exists runs under its own `mvmd-supervisor` process. The supervisor is the init process of a PID namespace and starts the VMM inside it, so the kernel kills the VMM and everything it started when the supervisor ends, however it ends.
- **No VMM without an expiry.** mvmd gives the supervisor the current expiry as part of its start, and the supervisor refuses to start the VMM without one or with one that has passed. Each start and each restore is a new supervisor.
- **A converter's VMM is supervised too**, with the end of the conversion time limit as its expiry in place of the fencing deadline, since it runs no workload ([ADR 0005](./adr/0005-untrusted-images-are-converted-in-a-converter-microvm.md)).
- **The supervisor counts the expiry.** It holds the expiry as an absolute `CLOCK_BOOTTIME` value, in mvmd's time namespace, and ends its namespace when the clock reaches it. It runs under a real-time scheduling policy that its VMM does not inherit, with its memory locked. It depends on nothing of mvmd's while it counts.
- **mvmd counts it too.** While running, mvmd kills every supervisor through its pidfd at the expiry.
- **Renewal reaches every supervisor before it is acknowledged.** An extension is recorded and then passed on; a shortening is passed on and then recorded, and a supervisor that does not take a shortening is killed first. No supervisor ever holds an expiry later than the recorded one.
- **Reboot.** The record carries the host's `boot_id`; a different one at start means no supervisor or VM survived, and the deadline is not armed.
- **The supervisor runs outside mvmd's cgroup**, so stopping mvmd under a service manager does not stop it.
- **mvmd holds a pidfd to the supervisor and one to its VMM.** The supervisor reports its VMM's number in its own namespace, and mvmd maps it to the host id through the supervisor's child list in `/proc`. A Machine has ended when both are readable.
- **mvmd confirms an end by the namespace.** After it kills a supervisor it waits until no process of the host is in the supervisor's PID namespace, read from `/proc/<pid>/ns/pid`. A process of another user is visible there only to a reader with ptrace access, so mvmd needs `CAP_SYS_PTRACE` as well as `CAP_SYS_ADMIN`.
- **Bound.** In each failure case the ADR lists, mvmd dying while it starts a Machine among them, a VM runs past the expiry for at most δ, the time the supervisor takes to wake and end its namespace. δ is not yet measured.

## Network

How a Machine reaches the network on its node ([ADR 0011](./adr/0011-each-machine-gets-a-routed-tap-and-addresses-mvmd-assigns.md), [ADR 0012](./adr/0012-nftables-on-the-host-enforces-each-machines-policy-at-its-tap.md)). Cross-node networking, the Gateway and the Cell Router are gaon's (#2 §3, §4).

- **One routed tap per Machine.** mvmd creates it, with its link down, before the VMM starts and deletes it after the VMM has ended. No two Machines share an L2 segment; the host is each guest's only next hop.
- **Addressing, dual stack.** The node's configuration names an IPv4 prefix, an IPv6 prefix, or both. mvmd assigns each Machine one address per configured family, at Create Machine and at Restore, and releases them at Delete Machine. A prefix with no free address for a family ends Create Machine and Restore as precondition failed, naming the prefix, with the UID, the disks and any address already taken released before the call returns ([ADR 0046](./adr/0046-a-bound-the-node-is-configured-with-is-reported-and-refused-as-precondition-failed-while-measured-capacity-stays-the-clients.md)); the prefix's assignable addresses, with the VMM user range, bound the Machines the node holds. The gateways are an IPv4 address and `fe80::1`, the same on every tap. The Guest Agent configures the addresses statically; no router advertisement or DHCP runs. A restored Machine gets new addresses, which the agent applies after the restore.
- **A real Driver needs the `network` section.** A node whose Driver is Firecracker or Cloud Hypervisor refuses a configuration without it, at load, as it does for `supervision`, `conversion` and `disk`. No mode runs Machines unenforced: a Machine starts only once its policy is applied (§Invariants 6), and without the section the node would hold a tap name that was never made. The memory Driver may leave the section out and then keeps the in-memory Network, which makes no tap and no rule; it may also set it.
- **Forwarding is a prerequisite the host sets.** For each family the node serves, `net.ipv4.ip_forward` (IPv4) and `net.ipv6.conf.all.forwarding` (IPv6) must read 1 in the network namespace mvmd runs in. mvmd writes no host-wide sysctl; it owns its nftables table and its taps (ADR 0012), and a switch it flipped would outlive it and surprise whatever else runs on the host. mvmd reads them at start, before it serves any call, and refuses to start on a served family that reads anything else, or cannot be read, naming the sysctl. A family the node does not serve is not read. This is the node's part of ADR 0011's "a prefix and forwarding for each family it serves".
- **Enforcement.** One nftables table mvmd owns. At each tap, frames not from the Machine's MAC and addresses are dropped, ARP and the ICMPv6 neighbour solicitations and advertisements it needs are admitted, and router advertisements, redirects and router solicitations from a guest are dropped. The inet chains accept only what the Machine's policy allows, plus replies and their ICMP errors; everything else is dropped. Traffic leaving the node is masqueraded to the node's address of its family, IPv6 included, unless its destination is in a no-masquerade prefix (below).
- **A destination in `network.no_masquerade` keeps the Machine's source address** ([ADR 0049](./adr/0049-traffic-to-a-configured-no-masquerade-prefix-keeps-the-machines-source-address-and-runtime-info-reports-the-machine-prefixes.md)). The list is CIDRs in the node's configuration, empty by default; each must be a valid CIDR in a family the node serves, or the start is refused naming it. One accept for each prefix sits in the table's postrouting chain ahead of the masquerade, so every other destination is masqueraded as above, and the Machine's egress policy still decides what leaves. Routes to those prefixes are the network's and gaon's, not mvmd's.
- **The node reports the prefixes it assigns from.** Runtime info lists them, one for each configured family ([runtime-api.md](./runtime-api.md) §Observation), so gaon's Node Agent can read them from the node.
- **One table of two families.** nftables gives a table one family, so mvmd's table is a netdev table (a chain at each tap) and an inet table (the policy chains), both named `mvmd`, created, replaced and changed in the same transaction ([ADR 0012](./adr/0012-nftables-on-the-host-enforces-each-machines-policy-at-its-tap.md), Errata).
- **Changed only by transactions**, which take effect whole or not at all (ADR 0012, at the Linux and nftables versions it names), and the table outlives an mvmd restart, which replaces it from mvmd's durable state before serving any call.
- **No IP traffic from a VMM's own sockets.** The table's output chain drops every packet whose socket belongs to a UID in the node's VMM range, which covers a VMM that shares the host's network namespace ([ADR 0015](./adr/0015-the-supervisor-confines-every-vmm-process-the-same-way.md)).

## VMM confinement

How the supervisor confines the VMM process it starts, Machine and converter alike, so that a guest escaping into its VMM reaches as little of the node as possible ([ADR 0015](./adr/0015-the-supervisor-confines-every-vmm-process-the-same-way.md), at the Linux, Firecracker and Cloud Hypervisor versions it names).

- **The supervisor confines, the same way for every VMM.** Its inputs are the Driver's description of the VMM process ([driver.md](./driver.md)); no step depends on which VMM runs, and none can be skipped. The VMM's own seccomp filter stays on beneath it. Firecracker's jailer is not used.
- **A user per Machine.** One UID and GID from the node's VMM range per Machine, allocated at Create Machine and Restore and released at Delete Machine, and one per conversion. The range's size bounds the Machines a node holds: a Create Machine or Restore that finds it spent is precondition failed, naming the range, with nothing taken ([ADR 0046](./adr/0046-a-bound-the-node-is-configured-with-is-reported-and-refused-as-precondition-failed-while-measured-capacity-stays-the-clients.md)). It owns the Machine's tap, root disk and run directory, and no supplementary groups.
- **A mount namespace with nothing else in it.** An empty root holding the VMM executable and the host files and device nodes the Driver names, each at its host path, the boot description's files at fixed paths with their read-only flags, and the Machine's run directory at `/run`, read-write. No `/proc` or `/sys`. The VMM's API and vsock sockets are in the run directory, where mvmd connects by its host path; the files the process description lists, which a restore's disks are, are hard-linked there by the supervisor before the VMM starts ([ADR 0042](./adr/0042-the-supervisor-links-the-files-a-process-description-lists-into-the-run-directory-before-the-vmm-starts.md)), a disk attached while it runs is hard-linked there by the Driver, and a snapshot is written there and moved to the snapshot store.
- **Fixed names for the Machine's files** ([ADR 0019](./adr/0019-a-vmm-sees-its-machines-files-at-fixed-paths-in-its-root.md)). The kernel is `/boot/kernel`, the initrd `/boot/initrd`, the block device at position `n` of the boot description `/disk/n` (for a Machine its image, then its root disk; a disk attached or named at create is added to the running VMM and has no position), the run directory `/run`, and for a restored VMM the directory `/snapshot` that holds the snapshot's files, the same for every Machine. A Driver describes devices to its VMM by these paths only, so a snapshot names no host path and a Machine restored from it has its own files bound to the same paths. The names are defined once, in `daemon/internal/machine/`, and the supervisor refuses a description whose paths are not absolute and clean, collide, nest, or are the root or under `/dev`.
- **The file checked is the file presented** (ADR 0019). The supervisor opens each host path once, hashes a pinned file (the kernel the Machine boots, one of the kernels the node offers by name ([ADR 0045](./adr/0045-a-node-offers-named-kernels-a-machine-records-the-name-it-is-created-with-and-a-restore-matches-the-recorded-digest.md)), and the VMM executable, which the Driver pins by SHA-256) from that open file, and mounts that same open file, so a file replaced at the path after the hash is not the one the VMM is given. A mismatch fails the start before the VMM runs. A write into the very file after the hash is not prevented; only a privileged host process can make one.
- **The run directory is a directory of its own** under the Machine's state directory, owned by the Machine's user. The supervisor's socket and log are beside it in the state directory, not in it, so a VMM cannot replace the socket mvmd connects to. The run directory outlives its VMM, and the supervision adapter removes the API and vsock sockets an earlier VMM left in it before it starts the next, since Firecracker fails to bind a path that exists; no other file is removed for this.
- **The serial console is served outside the root** ([ADR 0020](./adr/0020-the-supervisor-serves-the-vmms-serial-console-on-a-socket-outside-its-root.md), its pipes replaced by [ADR 0025](./adr/0025-the-supervisor-gives-the-vmm-a-raw-mode-pseudo-terminal-as-its-console.md)). The VMM's standard input and output are two separate opens of the subordinate side of a pseudo-terminal in raw mode, which passes every byte unchanged and echoes none, and whose controlling side the supervisor holds; the VMM has no controlling terminal and its root holds no `/dev/pts` or `/dev/ptmx`. The controlling side's `EIO` after the last subordinate closes is the end of the output. It writes the output to `vmm.log` in full and to each open session, and serves the sessions on `console.sock` in the state directory, mode 0600, beside its own socket and not in the run directory, so the VMM has no path to the socket and cannot replace it. The VMM gets no descriptor, mount or capability for it, and no step of this list changes. The supervisor copies bytes and interprets none; a session that falls behind is dropped, so the log, the other sessions and the expiry never wait for one.
- **A socket in a state directory is reached through a descriptor of its directory.** A Unix socket address holds 107 bytes, which a state directory's path and a Machine ID of any length can pass. mvmd, the supervisor and the Driver open the directory `O_PATH` and bind or connect to `/proc/self/fd/<n>/<name>`, which is short whatever the path, and `daemon/internal/unixsock/` does it for all of them. No length of `state_dir` or of an ID bounds a Machine. The runtime API's own socket is the operator's configured path and is not reached this way.
- **An event pipe, when the Driver names one** ([ADR 0026](./adr/0026-the-supervisor-ends-a-vmm-whose-event-pipe-reports-a-guest-reset.md)). The supervisor passes the write end of a pipe as the descriptor the description names (7 or above), holds the read end, and reads it in pieces of at most 4096 bytes, matching the description's byte string across reads. On a match it writes why to its log and kills the VMM, and then reads to the pipe's end. The VMM's end then follows as for any VMM: the console drains and the supervisor exits. The pipe carries bytes the supervisor only compares; a VMM that writes the string ends only itself. A description with no pipe passes none.
- **A network namespace with only loopback**, for a converter and for a VMM whose Driver takes the tap by descriptor. A VMM that opens the tap by name, Firecracker v1.17.0, shares the host's, under the output rule in §Network.
- **No capabilities and `no_new_privs`.** The bounding and ambient sets are emptied before the change to the Machine's UID, so the VMM execs with none and cannot gain any.
- **Landlock ABI 6.** File access only beneath the mount namespace's paths, `ioctl` only on the named devices, no TCP bind or connect, and no abstract Unix socket or signal outside its own domain. mvmd refuses to start on a kernel without it.
- **A seccomp baseline** stacked under the VMM's own filters: no creating or entering namespaces (`unshare`, `setns`, `clone` with a namespace flag), and `clone3` answered `ENOSYS` so its flags are checked through `clone`.
- **A cgroup per VMM**, under a parent of mvmd's outside mvmd's cgroup, entered at creation: `memory.max` at the guest's memory ceiling plus the Driver's overhead, `pids.max` at the Driver's task count, `cpu.max` at the guest's vCPU ceiling plus the Driver's overhead ([ADR 0029](./adr/0029-a-machine-has-a-resource-ceiling-chosen-at-create-which-bounds-a-live-resize-and-the-vmms-limits.md)). The supervisor is not in it; on a kernel with `CONFIG_RT_GROUP_SCHED` the supervisors are in the root cgroup.
- **Order, before `execve`:** open the descriptors to pass, enter the namespaces and build the root, drop capabilities and change user, `no_new_privs`, Landlock, the baseline filter. A failure at any step fails the start before the VMM runs.

## Registry access

What the node's `registry` configuration section makes mvmd read and run on the node; the pull itself is [image.md](./image.md) §Pull image.

- **Three keys**: `credentials_file`, `credential_helpers` and `ca_file`, each checked at start and read again at each use, so a credential or a CA bundle that is rewritten reaches the next pull without a restart ([ADR 0047](./adr/0047-a-pull-reads-the-registry-credentials-and-ca-at-each-lookup-and-takes-a-credential-from-a-helper.md)).
- **A helper is a process of mvmd's node**: `docker-credential-<name>`, found on mvmd's `PATH`, run with mvmd's environment inherited whole and nothing filtered (`PATH`, `AWS_CONFIG_FILE`, `AWS_PROFILE`, `AWS_REGION` among it), and free to run other programs, such as `credential_process`. Installing the helper and its AWS identity is the node's, not mvmd's.

## Invariants

mvmd provides the mechanism for three of the invariants of #2 §4; gaon's Node Agent enforces invariants 4 and 5 (issue garamsh/mvmd#1, Context). Invariant 3, who writes spec, binding and status, concerns gaon's resource API and is not mvmd's.

| Invariant (#2 §4) | mvmd's part |
|---|---|
| 1. A Machine runs on at most one node at a time | The fencing deadline above |
| 2. A Volume has at most one writer at a time | One holder per disk on its node, recorded durably by the inside before a Driver attaches it and released only once the holder's VMM process has ended ([ADR 0009](./adr/0009-a-machines-root-disk-is-a-sparse-raw-file-with-one-holder.md)) |
| 6. A Machine does not start until its network policy is applied | Fail-closed start: the Machine's rules are committed in one nftables transaction before its tap's link comes up and before its VMM starts; a failed commit fails the start ([ADR 0012](./adr/0012-nftables-on-the-host-enforces-each-machines-policy-at-its-tap.md)) |

## Open questions

These are #2 §6 questions inside mvmd's scope, as they apply to the runtime. They bind nothing.

- **Preservation default (#2 §6 item 8):** whether a Machine keeps its disk only or its memory as well by default. #2 §2 offers disk-only as a proposal, not a decision. That a snapshot is a public resource of the runtime API is decided (§Runtime API scope).
- **Volume classes (item 9):** classes, durability (replication, backup) and movement between nodes, as far as the runtime stores or moves a volume. A Machine's root disk is a node-local sparse raw file ([ADR 0009](./adr/0009-a-machines-root-disk-is-a-sparse-raw-file-with-one-holder.md)), and so is a disk the runtime API's Create disk makes ([ADR 0036](./adr/0036-the-runtime-api-creates-lists-and-deletes-a-node-local-disk-through-the-disk-adapter.md)); any class beyond that, any durability and any movement are not decided.
- **I/O limits per Machine.** A VMM's cgroup limits memory, tasks and CPU, not disk I/O, which needs per-device figures from the node's storage (§VMM confinement).
- **Density and restore numbers (item 13):** the fencing deadline's default, restore time and the latency right after a restore, and idle and active memory per node. None is measured; a value is set only after the single-node prototype of #2 §6 measures it.
- **The time a supervisor takes to end its namespace at the expiry**, under load and after a suspend; measured with the prototype numbers above. First observation, not a figure: GitHub Actions run 42506399573 (https://github.com/garamsh/mvmd/actions/runs/42506399573), on the hosted runner whose log prints kernel 7.0.0-1017-azure and CPU AMD EPYC 7763 64-Core Processor. A polling observer, which scans `/proc` every 0.2 ms and so includes its own scan time, saw the process tree gone 21.3 to 24.9 ms after the expiry in six observations (expiry reached, mvmd's side gone, three renewals, and a SIGKILL of the supervisor, the last measured from the kill). The runner was not idle by any measure the log gives, and there was no suspend; nothing here is a bound.
- **How many earlier releases' supervisors mvmd must speak to**, since a supervisor outlives an mvmd upgrade until its Machine is next started.
