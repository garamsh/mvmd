# Guest

The Guest Agent that runs inside each Machine, the channel mvmd reaches it by, and the boot order of a Machine.

Checked against garamsh/discussions#2 as read on 2026-11-08, §2 (discussioncomment-19288318), §5 (discussioncomment-19288321) and the decision-change reply (discussioncomment-19466961), and garamsh/discussions#3 as read on 2026-11-11, decision 6 and the reply discussioncomment-19533418, which replace the guest kernel reply (discussioncomment-19466922). Claims about a VMM or a kernel configuration are ADR 0010's, at the versions it names, except those under "Kernel candidates checked", which were checked on 2026-11-09 against the files and versions they name.

## Current decisions

- **The Guest Agent is the guest's init.** It runs as PID 1 from the initrd, prepares the guest, then runs the entrypoint and stays to supervise it. It serves exec and the file API (#2 §5, guest boot order; §2, file operations through the guest agent API).
- **mvmd reaches it over vsock.** The Guest Agent channel is a driven port ([structure.md](./structure.md) §Ports).
- **The channel is gRPC, and the contract is the Guest Agent's.** `mvmd.guest.v1alpha1.GuestService` is defined in `guest-agent/proto/mvmd/guest/v1alpha1/guest.proto`; the daemon generates its client from that file. It covers exec (start under the client's exec ID, resumable output by offset, signal), read, write, patch, list and search, boot and network update, find, release and grow a hot-plugged disk, bring vCPUs online, watch the workload's probes, terminate, health and info; console is the VMM's serial device and is not in it. The agent listens on vsock port 1024 (`guest-agent/crates/guest-agent/src/main.rs`). Rust code is generated at build time and not committed ([ADR 0014](./adr/0014-the-guest-agent-serves-a-grpc-contract-it-owns-over-vsock.md)).
- **An exited command carries when it ended.** The exec record has `ended_at`, the guest's `CLOCK_REALTIME` at the moment the agent reaped the command, set when the status is `EXITED` and unset otherwise, for every exec and for the entrypoint. It is the guest's clock, which the host sets at `Boot` ([ADR 0044](./adr/0044-boot-sets-the-guests-wall-clock-to-the-hosts-as-catchup-does.md)) and at a restore (`CatchUp`), and between those is the guest's own, not a reading of the host's, and the agent stamps it when the wait on the child returns, not when the output drains, which can take up to a second longer ([ADR 0043](./adr/0043-an-exited-command-carries-the-time-the-guest-agent-reaped-it-by-the-guests-clock.md).)
- **Calls are safe to repeat.** A repeated exec with the same exec ID returns the same record and never runs the command twice. A write leaves whole old or whole new content, and a patch applies only to the base digest and succeeds without change at the expected one ([runtime-api.md](./runtime-api.md) §Guest access).
- **Exec output is bounded.** The agent keeps the newest bytes of each command's output, up to a retention it is configured with (16 MiB per command by default, `guest-agent/crates/guest-agent/src/lib.rs`), because it is PID 1 and a command that prints without end would otherwise exhaust the guest's memory. A read resumes after any offset still held; a read after an earlier one fails with `OUT_OF_RANGE` naming the earliest offset held, and the exec record carries that offset as `earliest_offset`, so a client resynchronises from it as it does from events ([runtime-api.md](./runtime-api.md) §Observation). A read may instead set `tail_bytes`: it starts that many bytes before the end of the output held when the call arrives (at the earliest byte held if fewer are held), then follows as usual, on any exec record, `entrypoint` included. Zero leaves it unset, and setting it with a non-zero `after_offset` is `INVALID_ARGUMENT`.
- **Paths follow links.** Every file operation acts on the file its path names after following symbolic links. A write or patch replaces the resolved regular file in its own directory, so a link to a file stays a link and its target changes. A target that resolves to anything but a regular file (a device, FIFO, socket or directory) is refused as invalid and nothing is replaced, and a read of one is refused before any blocking open. A replaced file keeps its owner, group and mode, set before any content is written; a new file gets the mode a plain create gives. Writes and patches to one file are serialised, so a patch applies only to the base digest it names.
- **Listings and searches stream.** `ListFiles` and `SearchFiles` send their entries, sorted by path, across the messages of a server stream, so no result is bounded by one message. The service sets explicit message size limits.
- **Boot order (#2 §5):** kernel, init in the initrd, set the wall clock from the host's, check the root filesystem device, mount the EROFS read-only, overlay the writable disk as the upper layer, switch root, apply the run configuration (configure the network, place the files, mount the disks, resolve the user), run the entrypoint as that user.
- **How the agent finds its devices.** mvmd sends it, over the Guest Agent channel, the filesystem UUIDs of the MachineImage's EROFS and of the root disk, and the run configuration. The agent mounts the block device carrying each UUID; nothing Machine-specific is on the kernel command line, and the boot waits for mvmd's message ([ADR 0010](./adr/0010-a-machine-boots-a-pinned-kernel-and-the-guest-agent-initrd-from-raw-block-devices.md)). The agent recognises a device by reading its superblock, so it needs no udev or blkid: the filesystem's magic and UUID must both match, which is also what "check the root filesystem device" in the boot order means. It runs no `fsck`, since the initrd holds only the agent.
- **The boot description is the `Boot` call.** `GuestService.Boot` carries the two UUIDs, the run configuration (argv, environment, working directory, user, files, probes), the network configuration and the host's wall clock (`host_unix_nanos`), and `UpdateNetwork` carries the network configuration alone (`guest-agent/proto/mvmd/guest/v1alpha1/guest.proto`). Every other call except `Terminate`, `Health`, `Info`, `FindDisk`, `ReleaseDisk` and `OnlineVcpus` is refused as a failed precondition until `Boot` has succeeded. `Boot` returns when the entrypoint runs. It waits for the agent to listen within the boot timeout, retrying with backoff, and fails at once if the VMM has ended, with an error that is both `machine.ErrVMMEnded` and `machine.ErrGuestUnreachable`. It is safe to repeat, and to abandon: the steps run in a task of the agent's own, so a client that gives up or a connection that resets leaves the boot running, and a repeat waits for it and returns its outcome. The same description, files included, succeeds without running a step again (no file is placed twice), a different one, a different file included, is refused, and a repeat after a failure fails the same way; the time is not part of the description, so a repeat with another time succeeds and does not set the clock again. Before any other step the agent sets `CLOCK_REALTIME` to a positive `host_unix_nanos`, leaves it as the kernel set it when it is 0, and refuses a negative one as invalid. The daemon fills it from the clock it gives `CatchUp`, read after `Info` has answered and as it sends `Boot`, so the wait for the agent to listen does not age it ([ADR 0044](./adr/0044-boot-sets-the-guests-wall-clock-to-the-hosts-as-catchup-does.md)). The daemon calls `Info` on the same connection before it sends `Boot`, and sends nothing when the agent's `api_versions` lack `v1alpha1`: the Start fails and the Machine ends Stopped, with a reason naming the versions the agent serves and the one the daemon speaks (`daemon/internal/guestchannel/guest.go`; [runtime-api.md](./runtime-api.md) §Machine lifecycle, the Start row and "Start waits for the guest's `Boot`"). A restore sends `CatchUp` and reads no `Info`. `UpdateNetwork` without a network is refused as invalid, since applying none would wipe the Machine's.
- **A boot step that fails is named in the status `Boot` returns.** The steps are set the wall clock, check the devices, mount the image, mount the root disk, overlay, switch root, configure the network, place the files, mount the disks, apply the user and start the entrypoint; a failed one stops the boot, nothing after it runs, and the agent stays up as it is, refusing every call but `Terminate`, `Health`, `Info` and a repeat of `Boot`, until mvmd stops the Machine. A failed step is also written to the console, in the form `mvmd-guest-agent: boot failed step=<step> detail=<detail>`. A description that does not parse is refused as invalid and leaves the agent waiting.
- **The run configuration names the user and the files the entrypoint sees ([ADR 0048](./adr/0048-the-guest-agent-runs-the-entrypoint-as-a-named-user-and-places-files-from-the-boot-call-in-a-tmpfs-it-alone-mounts.md)).** `RunConfig.user` is an OCI-form string (`user`, `uid`, `user:group`, `uid:gid`, `user:gid`, `uid:group`); empty is root, 0:0. Names resolve against the booted root's `/etc/passwd` and `/etc/group` after the switch root and after the files are placed. With no group the gid is the user's primary group, or 0 for a uid with no passwd entry; a named user gets the supplementary groups `/etc/group` lists for it and a bare uid none. The entrypoint runs after `setgroups`, `setgid` and `setuid`, in that order, and `HOME` is set from passwd when the environment lacks it. A name that does not resolve fails the boot at `apply the user`; `ExecRequest.user` takes the same form, empty is root, and a name that does not resolve is `NOT_FOUND` with nothing started. `RunConfig.files` lists `{path, content, mode, uid, gid}`. The agent writes each content into a tmpfs it alone mounts (`/run/mvmd/files`, mode 0700, root) and bind-mounts it read-only onto its path in the booted root, creating missing parents (0755, root) and an empty target file, at `place the files`. The target is resolved within the booted root first, as the file calls resolve a path: every link is followed, the reserved-directory check applies to the resolved path too, a resolved target that exists and is not a regular file is refused naming the path sent, a dangling link whose parent exists gets its resolved file created, and the resolved file is the one bound, the link kept. Content never reaches the root disk, and an image file at the same path is shadowed, not overwritten; the empty target, the parent directories created and the empty `/run/mvmd/files` the tmpfs is mounted on do persist on the root disk's upper layer, and a later boot of that root disk finds them and places the same files again. A path must be absolute and clean, not `/`, not under `/proc`, `/sys`, `/dev` or `/run/mvmd`, and not repeated; at most 64 files and 1 MiB of content in all; anything else is refused as invalid at the parse. A file's content may be a secret: the agent never writes it to a log, the console, an error or a status detail, and an error names the path only.
- **The run configuration lists the workload's probes, and the agent runs them and reports their results ([ADR 0054](./adr/0054-the-guest-agent-runs-the-workloads-probes-and-streams-their-results-and-acts-on-none.md)).** `RunConfig.probes` is a list of `{name, kind, initial_delay, period, timeout, success_threshold, failure_threshold}`, with at most 8, and a name unique among them, 1 to 63 bytes of letters, digits, `_`, `.` and `-`. The kind is one of `exec {argv}`, `tcp {port}` and `http_get {port, path, scheme}`. A port is 1 to 65535, the scheme is empty or `http`, and a path starts with `/`, holds printable ASCII only and is at most 2048 bytes. An unset value, or a threshold of 0, takes the default: period 10 s, timeout 1 s, success threshold 1, failure threshold 3, initial delay 0; a duration is at most 24 h, and a period or timeout is at least 1 ms. The defaults are applied at the parse, so a probe that states a default equals one that leaves it unset, and the probes are part of the description a repeat `Boot` is compared by: other probes are refused, the same ones succeed. A list that does not parse is refused as invalid and leaves the agent waiting.
  Each probe starts its initial delay when the entrypoint starts and runs every period until the entrypoint ends; a run that is late is not made up. A run is bounded by its timeout and fails when it is exceeded. An exec probe runs outside the exec table, so it has no exec ID and is not listed or killed through `Exec` calls, with the run configuration's environment, working directory and user, no stdin, and is killed at its timeout and when the entrypoint ends; the first 1 KiB of its output, standard output and standard error in the order read, is kept as the result's `last_output` for its most recent run and nothing more is held. A `tcp` probe passes when the connection opens. An `http_get` probe sends `GET <path>` over HTTP/1.1 and passes on a status from 200 to 399, reading only the status line. `tcp` and `http_get` connect to the loopback address, `::1` when the network configuration has IPv6 and no IPv4, and 127.0.0.1 otherwise.
  A probe is UNKNOWN until a threshold is met: its success threshold of consecutive passes makes it PASSING, and its failure threshold of consecutive failures makes it FAILING, and from then on each threshold flips it the same way. A result carries the status, the guest-clock time it last changed (empty while UNKNOWN), the consecutive passes and failures, and the last failure message, which names the cause and never holds output of the workload. `WatchProbes` is a server stream: it sends the result of every probe, in the order given, on open, then one message for each change of a status, and ends after the entrypoint has ended and the final results are sent. A count that moves without a status change sends nothing. A watcher that falls behind is sent the current result of every probe in place of the changes it missed. With no probes, nothing is sent and the stream ends with the entrypoint. It is refused as a failed precondition until `Boot` has succeeded. The agent acts on no result: it does not restart, kill or stop anything, and it does not hold a Machine back from running; a client reads the stream and decides.
- **A condition a client must act on is a status detail, not message text.** The agent attaches the detail to the gRPC status (a `google.rpc.Status` in `grpc-status-details-bin`, the detail packed as an `Any`), and a client branches on its type and fields. The message stays for people and may change, so no client parses it. The messages are in `guest-agent/proto/mvmd/guest/v1alpha1/guest.proto`, and the statuses that carry them are:

  | Status | Raised by | Detail | Fields |
  |---|---|---|---|
  | `OUT_OF_RANGE` | `ReadExecOutput`, a read after an offset the retention has dropped | `ExecOutputGone` | `earliest_offset`, where the read resumes |
  | `INTERNAL` | `Boot`, and `UpdateNetwork` when its network step fails, a boot step that failed (a repeat of a failed `Boot` carries the same one) | `BootFailed` | `step` (the enum of the eleven steps above) and `detail`, the step's failure text |
  | `INVALID_ARGUMENT` | a file call whose path names a file of the wrong kind: a directory or a device, FIFO or socket for read, write and patch, a non-directory for list and search | `WrongFileKind` | `path`, and `expected`, `FILE` or `DIRECTORY` |
  | `FAILED_PRECONDITION` | every call refused because `Boot` has not succeeded, `Exec` and the file calls included, and `UpdateNetwork` and `CatchUp` | `NotBooted` | `state`: `PENDING` when `Boot` was not called or its steps still run, `FAILED` when a step failed |
  | `FAILED_PRECONDITION` | `ReleaseDisk`, a device the kernel has claimed (mounted, held, swap), or a filesystem the agent mounted for it that is busy (the message names its path) | `DiskInUse` | `disk_id`, the disk that was asked for |

  Any other status carries no detail: a request that is malformed, a path that does not exist, a patch that does not apply, the size limit's `OUT_OF_RANGE` and a signal to an ended command among them. Detail messages are additions to `v1alpha1`: a client that does not know one ignores it and has the code.
- **A hot-plugged disk is found, released and grown by three calls.** Firecracker v1.17.0 delivers no hotplug notification to the guest, and a device must be released by the guest before the host removes it (its `docs/device-hotplug.md`), so the daemon calls the agent around the Driver's attach and detach, and at Start for each disk the Machine names, between the agent answering and the `Boot` call ([ADR 0022](./adr/0022-the-guest-finds-a-hot-plugged-disk-by-rescan-and-releases-it-before-the-unplug.md)). All three are served before `Boot` has succeeded and name the disk by the ID mvmd attached it under; all are refused as a failed precondition by `guest-agent-channel`. Calls for one Machine are serialised.
  - *`FindDisk`* writes `1` to `/sys/bus/pci/rescan` and waits up to five seconds for exactly one unaccounted virtio block device in `/sys/class/block` ([ADR 0028](./adr/0028-find-disk-takes-the-one-virtio-block-device-the-agent-has-not-accounted-for.md)). A device is accounted for when it was present as the agent started (listed once, after it mounts `/sys` and before it listens), or when a record the agent holds names it; a released record's device is gone, so it holds nothing. The rescan stays and the device may come before it (a VMM that notifies the guest, so the kernel adds the device itself), after it, or during the wait. The call records the disk ID against the device's PCI address and returns the device name, its size in bytes and whether it is read-only. With a `mount_path` it also records the mount the disk is to have, which is made as the next bullet says. Firecracker's virtio-blk serial is built from the backing file's inode numbers and cannot be chosen, and mvmd knows no filesystem UUID of a disk it never reads, so the device is identified by being the one the agent has not accounted for. A repeat for an ID the agent holds returns the record without rescanning, and for one it released rescans as for a new one. No unaccounted device within the bound, or more than one, fails the call and records nothing.
  - *`ReleaseDisk`* opens `/dev/<name>` with `O_EXCL`, which the kernel refuses with `EBUSY` while the device or a partition of it is claimed (a mounted filesystem of any kind, swap, a device-mapper table), and that is `DiskInUse`. Otherwise, still holding the open descriptor so that nothing can mount the device in between, it writes `1` to `/sys/bus/pci/devices/<address>/remove`, waits up to five seconds for the block device to be gone, and keeps the record as released. A repeat for a released ID succeeds without a removal, so a detach that failed after the release is retried and converges; an ID the agent never found is `NOT_FOUND`. A process that holds the raw device open without claiming it does not stop a release. The unit tests stand in for the open; `make test` also runs two tests on a loop device over a file, each under passwordless sudo and failing where it cannot get it, that show that a mounted filesystem refuses the claim, that a held claim refuses a mount, and that with neither the claim and the mount succeed.
  - *The mount* ([ADR 0050](./adr/0050-the-guest-agent-mounts-an-attached-disks-ext4-at-a-path-and-grows-it-online.md)). A disk is ext4 or none, and the host formats it; the agent never formats or partitions. `FindDisk` carries `mount_path` and `read_only`; an empty path keeps the disk unmounted, the device node left for the entrypoint. The path obeys the file API's rules: absolute, clean, not `/`, not under `/proc`, `/sys`, `/dev` or `/run/mvmd`, and a path that does not obey them is `INVALID_ARGUMENT` before the disk is touched. The agent mounts the device's ext4 there in the booted root, creating the directory (0755, root), with `nodev` and `nosuid`, and read-only when the attachment is or when the device itself is. The path is resolved within the booted root first, every link followed and the reserved check applied to what it resolves to. A disk found before `Boot` is only recorded: the root it mounts under does not exist yet, so the mount is made at the boot step `mount the disks`, after `place the files` and before `apply the user` and the entrypoint, and a mount that fails fails the boot at that step. A disk found after that step is mounted by the call. A second disk for a path another disk holds, and a repeat of a held ID that asks for another mount, are `FAILED_PRECONDITION` with nothing changed.
  - *`ReleaseDisk` unmounts first.* A filesystem the agent mounted is unmounted before the claim is taken; one that is busy (`EBUSY`) fails the call as `DiskInUse`, the message naming the path, and the mount stays. A repeat after a release succeeds as before.
  - *`GrowDisk {disk_id}`* reads the device's size again from `/sys/class/block/<name>/size` and, for a disk the agent mounted, grows the mounted ext4 to fill it online with `EXT4_IOC_RESIZE_FS`, which takes the new size in blocks and changes nothing when the filesystem has it. It answers the size in bytes. A disk with no mount only has its size read, and an ID never found or released is `NOT_FOUND`. The caller resizes the disk in the VMM first. A filesystem the kernel will not grow online, a read-only mount among them, fails the call with the kernel's error.
- **Every non-root disk reaches the guest by `FindDisk` and `ReleaseDisk`** ([ADR 0041](./adr/0041-a-snapshot-records-its-disks-a-restore-takes-exactly-those-and-a-non-root-disk-reaches-the-guest-by-hot-plug.md)). A Machine boots with its image and its root disk only; Start hot-plugs each disk the Machine names and asks the guest to find it before it sends `Boot`, so the agent holds a record for every non-root disk and `ReleaseDisk` finds one a Machine was created with. A restored guest's mounts are in its memory as its records are, so nothing is mounted again. The boot description carries no disk's identity, since the agent has nothing but the order of a device to match one with, and it rejects that. A snapshot holds those records in the guest's memory, so a restored guest already has each, a repeated `FindDisk` returns it without a rescan, and a restored Machine detaches a disk as the Machine it came from did.
- **A hot-added vCPU is brought online by one call.** The pinned guest kernel brings hot-plugged memory online by itself (`CONFIG_MHP_DEFAULT_ONLINE_TYPE_ONLINE_AUTO=y`) and a hot-added vCPU not at all, so the daemon calls `GuestService.OnlineVcpus` after a Driver's resize (garamsh/mvmd#176, the PM decision's item 7; the kernel facts are §1 and §3 of its research). Removed vCPUs are taken offline by the kernel with no call.
  - *The operation* takes the target vCPU count; a target of 0 is refused as `INVALID_ARGUMENT`. It counts the CPUs under `/sys/devices/system/cpu` that are online (the CPU with no `online` file, the boot CPU, counts as online), then, in CPU number order and only while fewer than the target are online, writes `1` to the `online` file of each present CPU that reads `0`, and reads that file back. At or above the target it writes nothing, so a CPU the guest's own workload took offline, or one the VMM's removal has taken offline and is about to unregister, is not brought back. A CPU whose write fails, or that still reads `0` after the write, fails the call as `INTERNAL`, and the message names it (`cpuN`); the CPUs after it are not tried.
  - *The answer* is the number of CPUs online after the writes and the kernel's `MemTotal` from `/proc/meminfo`, in bytes. The caller judges whether the count reached its target; the agent does not wait for it. A repeat with nothing to bring online writes nothing and answers the same counts, and the call is served before `Boot` has succeeded, as `FindDisk` is.
- **The network.** mvmd sends the agent the Machine's addresses (IPv4, IPv6 or both, as its node serves, each with its prefix length), a gateway for each and the resolvers, with the boot description. The interface is the one whose driver is `virtio_net`, which a kernel's fallback tunnel devices (`sit0`, `tunl0`, `ip6tnl0`) are not; the step fails unless exactly one is. The agent configures it statically before the entrypoint runs: `accept_ra` and `accept_dad` off on every boot, before the link comes up (the link-local address forms whatever the configuration holds), the IPv6 address without DAD, the default routes via the gateways sent (`fe80::1` for IPv6, by ADR 0011), and the resolvers written to `/etc/resolv.conf` in the booted root. The IPv4 route is on-link, so a `/32` address reaches its gateway. After a restore mvmd sends only `CatchUp`, which carries the new Machine's configuration and applies it with the same rules. `UpdateNetwork` is the network-only call for a running Machine, and the agent applies it whole: the default routes and the addresses it applied before are removed first, so a family the new configuration drops keeps neither, and the old ones are forgotten only once that removal has succeeded ([ADR 0011](./adr/0011-each-machine-gets-a-routed-tap-and-addresses-mvmd-assigns.md)). The daemon does not call it: its `machine.Guest` port has no such operation, and a policy is fixed for a Machine's life in `v1alpha2`, so nothing in the runtime API changes a running Machine's network. It stays in the contract as the guest half of the replace operation that [runtime-api.md](./runtime-api.md) §Open questions ("Changing a running Machine's policy") says would be an addition, so that adding the operation costs no Guest Agent version.
- **A restore is followed by `CatchUp`.** mvmd sends one `GuestService.CatchUp` call with a restore ID, 32 to 256 bytes of entropy drawn on the host, the host's wall clock and the Machine's network; the agent has caught up when it returns ([ADR 0016](./adr/0016-a-restored-guest-reseeds-from-host-entropy-and-takes-its-time-from-the-host.md)). In order, it mixes the entropy into the kernel's pool and counts it (`RNDADDENTROPY`), makes the kernel reseed from the pool (`RNDRESEEDCRNG`), sets `CLOCK_REALTIME` from the host's time (as `Boot` does at a boot, [ADR 0044](./adr/0044-boot-sets-the-guests-wall-clock-to-the-hosts-as-catchup-does.md)), and applies the network as `UpdateNetwork` does. A step that fails fails the call naming it and stops the rest. A call with the restore ID of the last one that succeeded succeeds and does nothing, so the clock is never set back by a repeat; one that failed records nothing and is carried out again whole. The call is refused before `Boot` has succeeded and when its parts are invalid. The agent does nothing to work in progress at the snapshot: commands keep running in the restored guest, and cut streams are resumed by the client as ADR 0014 provides. User-space random state is not the agent's to change.
- **The entrypoint is the exec record `entrypoint`.** The agent starts it through the exec table, so its output is read with offsets, it is signalled and its end is recorded as any command's is, and the exec ID `entrypoint` belongs to it: an `Exec` under that ID is a repeat and runs nothing. It inherits no environment but the one described. Its output is carried by the channel and not by the serial console.
- **PID 1 duties.** The agent is the init of the Machine:
  - *Reaping.* On every child exit it waits for the exited children it did not start, which are the processes orphaned onto it; the children it did start are waited for by the exec table, so their exit status is never taken. This reads the zombies from `/proc` and needs it mounted.
  - *Termination.* It forwards `SIGTERM` and `SIGINT` (the signal the kernel sends init on a ctrl-alt-del) to the entrypoint as the signal received. A request when the entrypoint is not running (before it runs, or after it failed to start) ends the Machine, since there is nothing to terminate.
  - *The `Terminate` call.* `GuestService.Terminate` asks for the same thing as `SIGTERM` to init, and is how a graceful stop reaches the agent whatever the VMM and the kernel, since the VMM's keyboard and power requests need devices a kernel may lack ([ADR 0018](./adr/0018-a-graceful-stop-goes-through-the-guest-agent-and-the-vmm-request-is-the-fallback.md)). It sends `SIGTERM` into the loop that handles the signals to init, and one function applies the rule to both, so a call when the entrypoint is not running ends the Machine as a signal does. It is served before `Boot` has succeeded, returns when the agent has taken the request and not when the Machine has ended, and a repeat sends `SIGTERM` again. The request carries no signal. `guest-agent-channel` refuses it as a failed precondition.
  - *The entrypoint's end.* When the entrypoint exits, its record is final for every client reading it, the agent writes one line saying how it ended to the console, stops accepting calls, waits up to five seconds for connected clients to finish, and ends the Machine by the method the kernel command line names (*How the Machine ends*, below).
  - *It never returns.* The kernel panics when init exits, so a failure of the agent itself (preparing the guest, listening, the server stopping, the power-off) is written to the console and ends the Machine the same way, and so is a panic on any thread and the runtime failing to build: a panic hook runs the same sequence before the process could abort. An end that returns has failed: the agent then tries the other method, and if that returns too it waits for ever. The console line for a panic is `mvmd-guest-agent: panic: <message and location>`.
  - *How the Machine ends.* How a guest ends its VMM is a property of the VMM and the architecture, so the Driver states it and the agent obeys: the Driver puts `mvmd.end=poweroff` (`reboot(RB_POWER_OFF)`) or `mvmd.end=reset` (`reboot(RB_AUTOBOOT)`, which `reboot=k` turns into the keyboard-controller reset on x86) on the kernel command line. Each Driver sets it per architecture (`driver.md`, each Driver's *How the Machine ends*), so a Machine takes the case below only on a command line no Driver built. The agent reads `/proc/cmdline` once, after it has mounted `/proc`, and parses it into one typed value that every end uses: the entrypoint's end, a termination before it ran, the agent's own failure and a panic. A line with no `mvmd.end`, any other value, or a command line that cannot be read, is written to the console as one `mvmd-guest-agent: ` line, and the Machine then ends by power off, so a Driver that does not set the parameter keeps what the agent did before it. An end before `/proc` is mounted, a failure to mount it included, is a power-off for the same reason. The other method is the fallback when the named one returns ("It never returns", above). The parameter belongs to the VMM and not to the Machine, so "nothing Machine-specific is on the kernel command line" (*How the agent finds its devices*) still holds. [ADR 0032](./adr/0032-the-guest-agent-ends-the-machine-by-the-method-the-kernel-command-line-names.md).
  - *The console lines.* Each is one line that begins `mvmd-guest-agent: `, which the VMM's console carries to the run directory's log, where the daemon reads it, through the Driver's `ConsoleLog` ([driver.md](./driver.md)), when it had no stream open on the entrypoint: a read of the record `entrypoint` of a Machine that is Stopped or Faulted, or Running with a guest that no longer answers, is answered from these lines, and one that none of them speaks of is cut short. They are `entrypoint exited code=<n> at=<time>`, `entrypoint exited signal=<n> at=<time>` (the time is the record's `ended_at` as RFC 3339 in UTC, as `prost_types::Timestamp` writes it, with a fraction of 0, 3, 6 or 9 digits, such as `2026-11-11T12:34:56.123456789Z`; a line from an older initrd has no ` at=`, and the daemon then gives the code or signal and no time), `entrypoint not started reason=<text>`, `entrypoint ended reason=<text>` (cut short), `terminated before the entrypoint ran`, `boot failed step=<step> detail=<text>` and `failed to <what>: <error>` for the agent's own failures. The log is complete when the VMM has ended, which the agent's end of the Machine brings about: under each Driver on x86_64 a Machine whose entrypoint exited with code 7 became Stopped, and the first read of its record with no stream open returned that code (`TestE2E_AnEntrypointThatEndsStopsTheMachineWithItsExitCode`, `e2e` job, CI run 42810030070 on head 9b1ed0ee1b3c124e38bdc026ae91d42e9b6426e2).
- **A host-side binary serves the channel alone, for tests.** `guest-agent-channel` (`guest-agent/crates/guest-agent/src/guest_agent_channel.rs`) serves `GuestService` on a Unix socket through `guest_agent::serve`, answering the `CONNECT <port>` handshake of a Firecracker host-side socket when given `--handshake-port`; it is a test seam, built by `make build` for the host, and is not in the initrd or shipped.
- **The initrd is a pinned input.** The node's configuration names the Guest Agent's initrd and the converter's, each with its SHA-256, as it names the kernel; the Driver checks the digest when mvmd starts, and the supervisor checks it on the file it mounts before every boot and, for Cloud Hypervisor, every restore ([ADR 0030](./adr/0030-the-guest-agent-and-converter-initrds-are-pinned-by-digest-as-the-kernel-is.md)). A rebuilt initrd has a new digest, which the configuration then names.
- **The initrd is the agent, alone.** `make build` writes `guest-agent/target/initrd.cpio`, an uncompressed cpio archive in the kernel's newc format with the statically linked musl binary as `init`, so the kernel needs no decompressor beyond `CONFIG_BLK_DEV_INITRD`. `guest-agent/crates/mkinitrd` names the one file and `lib/initrd/` writes the archive, with fixed owner, times and inode numbers. `make build` builds the initrd's binary with the workspace, Cargo's home and the target directory remapped to fixed names (`--remap-path-prefix`; the `trim-paths` profile key is unstable in the pinned toolchain), so it carries no path of the machine that builds it, and it checks that two builds give one digest by building a second time in a fresh target directory. The initrd's binary is therefore built with other flags than the host and shipped builds of the same command. The agent creates the mount points it needs and attaches `/dev/console` again from devtmpfs, so the archive holds no directory or device node. At the switch root it deletes the initramfs's files, as `switch_root(8)` does, when the root is a ramfs or a tmpfs; mounts are left.
- **The overlay.** Lower: the EROFS, holding no whiteouts or opaque marks ([image.md](./image.md) §Conversion). Upper and work directories: on the root disk, an ext4 filesystem the host formatted ([ADR 0009](./adr/0009-a-machines-root-disk-is-a-sparse-raw-file-with-one-holder.md)).
- **Integrity is not the guest's.** The host kernel verifies every read of the EROFS file ([image.md](./image.md) §Integrity), so the agent sets up no verity device.
- **The host never mounts a guest disk.** A host kernel would interpret an untrusted filesystem, and a second writer would be possible (#2 §2, and §5 security). The host formats a root disk once, before any guest has written it, and reads nothing from it afterwards.
- **Language: Rust**, because one runs per VM and memory and start time matter (#2 §5, implementation language).
- **Guest kernel.** Build and management belong to naru, the node OS project (garamsh/discussions#3, decision 6, read on 2026-11-11; it replaces the guest kernel reply's "a separate project"). The reasons are the GPLv2 source-distribution obligation and a build toolchain and update cadence different from mvmd's. mvmd holds no kernel configuration or patches. The kernel conditions the Guest Agent requires are stated explicitly (#2 §5).
- **The kernel is a pinned input.** The node's configuration names the kernels it offers, each a name, a file and its SHA-256, with one the default ([ADR 0045](./adr/0045-a-node-offers-named-kernels-a-machine-records-the-name-it-is-created-with-and-a-restore-matches-the-recorded-digest.md)); mvmd checks the digest before every boot, converter included (which has one kernel of its own), and records the name and digest in inspect and in each snapshot. On x86_64 it is an uncompressed ELF kernel with a PVH entry, on aarch64 a PE `Image` ([ADR 0010](./adr/0010-a-machine-boots-a-pinned-kernel-and-the-guest-agent-initrd-from-raw-block-devices.md)).
- **Kernel conditions**, built in since the initrd carries no modules: `CONFIG_BLK_DEV_INITRD`, `CONFIG_VIRTIO_BLK`, `CONFIG_VIRTIO_VSOCKETS`, the virtio transport of the Driver's VMM, `CONFIG_EROFS_FS`, `CONFIG_OVERLAY_FS`, `CONFIG_EXT4_FS`, and on x86_64 `CONFIG_PVH`. The agent's own code adds `CONFIG_DEVTMPFS` (it mounts devtmpfs), `CONFIG_PROC_FS` and `CONFIG_PROC_SYSCTL` (it scans `/proc` and writes `/proc/sys`), `CONFIG_SYSFS` (it reads `/sys/class/block` and `/sys/class/net`, and writes the PCI bus's `rescan` and a device's `remove` for a hot-plugged disk), `CONFIG_PCI` and `CONFIG_VIRTIO_PCI` (the transport a hot-plugged disk arrives on under Firecracker, which runs with `--enable-pci`; Kata Containers 4.3.1's kernel has both `=y`), `CONFIG_HOTPLUG_CPU` (the `online` file of a CPU; Kata Containers 4.3.1's kernel has it `=y` on x86_64 and aarch64, garamsh/mvmd#176 research §3), `CONFIG_NET`, `CONFIG_INET` and `CONFIG_VIRTIO_NET` (rtnetlink, IPv4 and the one device it configures) (ADR 0010). The kernel's own reseed after a restore, which the agent's `CatchUp` does not wait on, needs `CONFIG_VMGENID` and, on x86_64, `CONFIG_ACPI` ([ADR 0016](./adr/0016-a-restored-guest-reseeds-from-host-entropy-and-takes-its-time-from-the-host.md)). The agent's own reseed and time setting use the `/dev/urandom` ioctls and `clock_settime`, which no configuration removes. For a node that serves IPv6, `CONFIG_IPV6` ([ADR 0011](./adr/0011-each-machine-gets-a-routed-tap-and-addresses-mvmd-assigns.md)).
- **A published kernel meets every kernel condition but one.** The kernel configurations Firecracker v1.17.0 and Cloud Hypervisor's `ch-7.2.8` branch publish leave EROFS out. Kata Containers 4.3.1 ships a kernel (6.18.56) whose own configuration has every condition built in on x86_64 and aarch64 except `CONFIG_VMGENID`, which is not set; the agent's `CatchUp` does not wait on it ([ADR 0016](./adr/0016-a-restored-guest-reseeds-from-host-entropy-and-takes-its-time-from-the-host.md)). What was checked, in which file and version, is under Rationale. A kernel meeting the conditions is supplied to the node from outside mvmd (ADR 0010). **Decision (PM, 2026-11-09):** the first real Machine and the Driver end-to-end tests boot on Kata Containers 4.3.1's kernel 6.18.56 (`vmlinux-6.18.56-208`), pinned by the SHA-256 digests under Rationale. A kernel built by naru to the kernel conditions replaces it when a condition no published kernel meets becomes necessary, or when the missing `CONFIG_VMGENID` is shown to matter.

## Rationale

- Why a Rust agent in a Go project: [ADR 0001](./adr/0001-mvmd-is-a-containerd-like-microvm-runtime-that-does-not-know-gaon.md); the cost of two languages is acknowledged in #2 §5.
- Why exec and files go through the agent and not the host: #2 §2.
- Why devices are found by filesystem UUID and the kernel is pinned by digest, and the kernel configurations checked: [ADR 0010](./adr/0010-a-machine-boots-a-pinned-kernel-and-the-guest-agent-initrd-from-raw-block-devices.md).
- Why the Driver names how the guest ends, and why the command line carries it: [ADR 0032](./adr/0032-the-guest-agent-ends-the-machine-by-the-method-the-kernel-command-line-names.md).
- Restore concerns the agent must address after a snapshot restore: vsock connections are reset (Firecracker resets them on restore), the guest clock jumps, and cloned guests share random state (#2 §2). What the pinned VMMs offer for each, and why the agent does the work itself: [ADR 0016](./adr/0016-a-restored-guest-reseeds-from-host-entropy-and-takes-its-time-from-the-host.md).

## Open questions

- **What the guest does with a non-root disk (#2 §6 item 9) is decided.** The host formats a disk ext4 or leaves it unformatted; the agent mounts an ext4 one at the path `FindDisk` names, releases it by unmounting first, and grows it online ([ADR 0050](./adr/0050-the-guest-agent-mounts-an-attached-disks-ext4-at-a-path-and-grows-it-online.md)). How the agent identifies a disk is settled ([ADR 0041](./adr/0041-a-snapshot-records-its-disks-a-restore-takes-exactly-those-and-a-non-root-disk-reaches-the-guest-by-hot-plug.md)). What a client formats a disk with and the runtime API that names a path are not the Guest Agent's.
- **Guest kernel management and the allowed scope of user-supplied kernels (#2 §6 item 11).** The first real Machine boots on a published kernel (Current decisions), so what remains open is the scope of user-supplied kernels. A kernel the node provides, naru's included, is a named entry in the node's configuration ([ADR 0045](./adr/0045-a-node-offers-named-kernels-a-machine-records-the-name-it-is-created-with-and-a-restore-matches-the-recorded-digest.md)).
