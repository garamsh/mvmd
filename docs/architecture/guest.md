# Guest

The Guest Agent that runs inside each Machine, the channel mvmd reaches it by, and the boot order of a Machine.

Checked against garamsh/discussions#2 as read on 2026-11-08, §2 (discussioncomment-19288318), §5 (discussioncomment-19288321) and the decision-change reply (discussioncomment-19466961), and the guest kernel reply (discussioncomment-19466922). Claims about a VMM or a kernel configuration are ADR 0010's, at the versions it names, except those under "Kernel candidates checked", which were checked on 2026-11-09 against the files and versions they name.

## Current decisions

- **The Guest Agent is the guest's init.** It runs as PID 1 from the initrd, prepares the guest, then runs the entrypoint and stays to supervise it. It serves exec and the file API (#2 §5, guest boot order; §2, file operations through the guest agent API).
- **mvmd reaches it over vsock.** The Guest Agent channel is a driven port ([structure.md](./structure.md) §Ports).
- **The channel is gRPC, and the contract is the Guest Agent's.** `mvmd.guest.v1alpha1.GuestService` is defined in `guest-agent/proto/mvmd/guest/v1alpha1/guest.proto`; the daemon generates its client from that file. It covers exec (start under the client's exec ID, resumable output by offset, signal), read, write, patch, list and search, boot and network update, find and release a hot-plugged disk, bring vCPUs online, terminate, health and info; console is the VMM's serial device and is not in it. The agent listens on vsock port 1024 (`guest-agent/crates/guest-agent/src/main.rs`). Rust code is generated at build time and not committed ([ADR 0014](./adr/0014-the-guest-agent-serves-a-grpc-contract-it-owns-over-vsock.md)).
- **Calls are safe to repeat.** A repeated exec with the same exec ID returns the same record and never runs the command twice. A write leaves whole old or whole new content, and a patch applies only to the base digest and succeeds without change at the expected one ([runtime-api.md](./runtime-api.md) §Guest access).
- **Exec output is bounded.** The agent keeps the newest bytes of each command's output, up to a retention it is configured with (16 MiB per command by default, `guest-agent/crates/guest-agent/src/lib.rs`), because it is PID 1 and a command that prints without end would otherwise exhaust the guest's memory. A read resumes after any offset still held; a read after an earlier one fails with `OUT_OF_RANGE` naming the earliest offset held, and the exec record carries that offset as `earliest_offset`, so a client resynchronises from it as it does from events ([runtime-api.md](./runtime-api.md) §Observation).
- **Paths follow links.** Every file operation acts on the file its path names after following symbolic links. A write or patch replaces the resolved regular file in its own directory, so a link to a file stays a link and its target changes. A target that resolves to anything but a regular file (a device, FIFO, socket or directory) is refused as invalid and nothing is replaced, and a read of one is refused before any blocking open. A replaced file keeps its owner, group and mode, set before any content is written; a new file gets the mode a plain create gives. Writes and patches to one file are serialised, so a patch applies only to the base digest it names.
- **Listings and searches stream.** `ListFiles` and `SearchFiles` send their entries, sorted by path, across the messages of a server stream, so no result is bounded by one message. The service sets explicit message size limits.
- **Boot order (#2 §5):** kernel, init in the initrd, check the root filesystem device, mount the EROFS read-only, overlay the writable disk as the upper layer, switch root, apply the run configuration, run the entrypoint.
- **How the agent finds its devices.** mvmd sends it, over the Guest Agent channel, the filesystem UUIDs of the MachineImage's EROFS and of the root disk, and the run configuration. The agent mounts the block device carrying each UUID; nothing Machine-specific is on the kernel command line, and the boot waits for mvmd's message ([ADR 0010](./adr/0010-a-machine-boots-a-pinned-kernel-and-the-guest-agent-initrd-from-raw-block-devices.md)). The agent recognises a device by reading its superblock, so it needs no udev or blkid: the filesystem's magic and UUID must both match, which is also what "check the root filesystem device" in the boot order means. It runs no `fsck`, since the initrd holds only the agent.
- **The boot description is the `Boot` call.** `GuestService.Boot` carries the two UUIDs, the run configuration (argv, environment, working directory) and the network configuration, and `UpdateNetwork` carries the network configuration alone (`guest-agent/proto/mvmd/guest/v1alpha1/guest.proto`). Every other call except `Terminate`, `Health`, `Info`, `FindDisk`, `ReleaseDisk` and `OnlineVcpus` is refused as a failed precondition until `Boot` has succeeded. `Boot` returns when the entrypoint runs. It waits for the agent to listen within the boot timeout, retrying with backoff, and fails at once if the VMM has ended, with an error that is both `machine.ErrVMMEnded` and `machine.ErrGuestUnreachable`. It is safe to repeat, and to abandon: the steps run in a task of the agent's own, so a client that gives up or a connection that resets leaves the boot running, and a repeat waits for it and returns its outcome. The same description succeeds without running a step again, a different one is refused, and a repeat after a failure fails the same way. `UpdateNetwork` without a network is refused as invalid, since applying none would wipe the Machine's.
- **A boot step that fails is named in the status `Boot` returns.** The steps are check the devices, mount the image, mount the root disk, overlay, switch root, configure the network and start the entrypoint; a failed one stops the boot, nothing after it runs, and the agent stays up as it is, refusing every call but `Terminate`, `Health`, `Info` and a repeat of `Boot`, until mvmd stops the Machine. A failed step is also written to the console, in the form `mvmd-guest-agent: boot failed step=<step> detail=<detail>`. A description that does not parse is refused as invalid and leaves the agent waiting.
- **A condition a client must act on is a status detail, not message text.** The agent attaches the detail to the gRPC status (a `google.rpc.Status` in `grpc-status-details-bin`, the detail packed as an `Any`), and a client branches on its type and fields. The message stays for people and may change, so no client parses it. The messages are in `guest-agent/proto/mvmd/guest/v1alpha1/guest.proto`, and the statuses that carry them are:

  | Status | Raised by | Detail | Fields |
  |---|---|---|---|
  | `OUT_OF_RANGE` | `ReadExecOutput`, a read after an offset the retention has dropped | `ExecOutputGone` | `earliest_offset`, where the read resumes |
  | `INTERNAL` | `Boot`, and `UpdateNetwork` when its network step fails, a boot step that failed (a repeat of a failed `Boot` carries the same one) | `BootFailed` | `step` (the enum of the seven steps above) and `detail`, the step's failure text |
  | `INVALID_ARGUMENT` | a file call whose path names a file of the wrong kind: a directory or a device, FIFO or socket for read, write and patch, a non-directory for list and search | `WrongFileKind` | `path`, and `expected`, `FILE` or `DIRECTORY` |
  | `FAILED_PRECONDITION` | every call refused because `Boot` has not succeeded, `Exec` and the file calls included, and `UpdateNetwork` and `CatchUp` | `NotBooted` | `state`: `PENDING` when `Boot` was not called or its steps still run, `FAILED` when a step failed |

  | `FAILED_PRECONDITION` | `ReleaseDisk`, a device the kernel has claimed (mounted, held, swap) | `DiskInUse` | `disk_id`, the disk that was asked for |

  Any other status carries no detail: a request that is malformed, a path that does not exist, a patch that does not apply, the size limit's `OUT_OF_RANGE` and a signal to an ended command among them. Detail messages are additions to `v1alpha1`: a client that does not know one ignores it and has the code.
- **A hot-plugged disk is found and released by two calls.** Firecracker v1.17.0 delivers no hotplug notification to the guest, and a device must be released by the guest before the host removes it (its `docs/device-hotplug.md`), so the daemon calls the agent around the Driver's attach and detach ([ADR 0022](./adr/0022-the-guest-finds-a-hot-plugged-disk-by-rescan-and-releases-it-before-the-unplug.md)). Both are served before `Boot` has succeeded and name the disk by the ID mvmd attached it under; both are refused as a failed precondition by `guest-agent-channel`. Calls for one Machine are serialised.
  - *`FindDisk`* writes `1` to `/sys/bus/pci/rescan` and waits up to five seconds for exactly one unaccounted virtio block device in `/sys/class/block` ([ADR 0028](./adr/0028-find-disk-takes-the-one-virtio-block-device-the-agent-has-not-accounted-for.md)). A device is accounted for when it was present as the agent started (listed once, after it mounts `/sys` and before it listens), or when a record the agent holds names it; a released record's device is gone, so it holds nothing. The rescan stays and the device may come before it (a VMM that notifies the guest, so the kernel adds the device itself), after it, or during the wait. The call records the disk ID against the device's PCI address and returns the device name, its size in bytes and whether it is read-only. Firecracker's virtio-blk serial is built from the backing file's inode numbers and cannot be chosen, and mvmd knows no filesystem UUID of a disk it never reads, so the device is identified by being the one the agent has not accounted for. A repeat for an ID the agent holds returns the record without rescanning, and for one it released rescans as for a new one. No unaccounted device within the bound, or more than one, fails the call and records nothing.
  - *`ReleaseDisk`* opens `/dev/<name>` with `O_EXCL`, which the kernel refuses with `EBUSY` while the device or a partition of it is claimed (a mounted filesystem of any kind, swap, a device-mapper table), and that is `DiskInUse`. Otherwise, still holding the open descriptor so that nothing can mount the device in between, it writes `1` to `/sys/bus/pci/devices/<address>/remove`, waits up to five seconds for the block device to be gone, and keeps the record as released. A repeat for a released ID succeeds without a removal, so a detach that failed after the release is retried and converges; an ID the agent never found is `NOT_FOUND`. A process that holds the raw device open without claiming it does not stop a release. The unit tests stand in for the open; `make test` also runs two tests on a loop device over a file, each under passwordless sudo and failing where it cannot get it, that show that a mounted filesystem refuses the claim, that a held claim refuses a mount, and that with neither the claim and the mount succeed.
  - *What the guest does with the disk* is nothing: it does not mount, format or partition it, and leaves the device node for the entrypoint, because what a non-root disk is for is open (#2 §6 item 9).
- **A hot-added vCPU is brought online by one call.** The pinned guest kernel brings hot-plugged memory online by itself (`CONFIG_MHP_DEFAULT_ONLINE_TYPE_ONLINE_AUTO=y`) and a hot-added vCPU not at all, so the daemon calls `GuestService.OnlineVcpus` after a Driver's resize (garamsh/mvmd#176, the PM decision's item 7; the kernel facts are §1 and §3 of its research). Removed vCPUs are taken offline by the kernel with no call.
  - *The operation* takes the target vCPU count; a target of 0 is refused as `INVALID_ARGUMENT`. It counts the CPUs under `/sys/devices/system/cpu` that are online (the CPU with no `online` file, the boot CPU, counts as online), then, in CPU number order and only while fewer than the target are online, writes `1` to the `online` file of each present CPU that reads `0`, and reads that file back. At or above the target it writes nothing, so a CPU the guest's own workload took offline, or one the VMM's removal has taken offline and is about to unregister, is not brought back. A CPU whose write fails, or that still reads `0` after the write, fails the call as `INTERNAL`, and the message names it (`cpuN`); the CPUs after it are not tried.
  - *The answer* is the number of CPUs online after the writes and the kernel's `MemTotal` from `/proc/meminfo`, in bytes. The caller judges whether the count reached its target; the agent does not wait for it. A repeat with nothing to bring online writes nothing and answers the same counts, and the call is served before `Boot` has succeeded, as `FindDisk` is.
- **The network.** mvmd sends the agent the Machine's addresses (IPv4, IPv6 or both, as its node serves, each with its prefix length), a gateway for each and the resolvers, with the boot description. The interface is the one whose driver is `virtio_net`, which a kernel's fallback tunnel devices (`sit0`, `tunl0`, `ip6tnl0`) are not; the step fails unless exactly one is. The agent configures it statically before the entrypoint runs: `accept_ra` and `accept_dad` off on every boot, before the link comes up (the link-local address forms whatever the configuration holds), the IPv6 address without DAD, the default routes via the gateways sent (`fe80::1` for IPv6, by ADR 0011), and the resolvers written to `/etc/resolv.conf` in the booted root. The IPv4 route is on-link, so a `/32` address reaches its gateway. After a restore mvmd sends only `CatchUp`, which carries the new Machine's configuration and applies it with the same rules. `UpdateNetwork` is the network-only call for a running Machine, and the agent applies it whole: the default routes and the addresses it applied before are removed first, so a family the new configuration drops keeps neither, and the old ones are forgotten only once that removal has succeeded ([ADR 0011](./adr/0011-each-machine-gets-a-routed-tap-and-addresses-mvmd-assigns.md)).
- **A restore is followed by `CatchUp`.** mvmd sends one `GuestService.CatchUp` call with a restore ID, 32 to 256 bytes of entropy drawn on the host, the host's wall clock and the Machine's network; the agent has caught up when it returns ([ADR 0016](./adr/0016-a-restored-guest-reseeds-from-host-entropy-and-takes-its-time-from-the-host.md)). In order, it mixes the entropy into the kernel's pool and counts it (`RNDADDENTROPY`), makes the kernel reseed from the pool (`RNDRESEEDCRNG`), sets `CLOCK_REALTIME` from the host's time, and applies the network as `UpdateNetwork` does. A step that fails fails the call naming it and stops the rest. A call with the restore ID of the last one that succeeded succeeds and does nothing, so the clock is never set back by a repeat; one that failed records nothing and is carried out again whole. The call is refused before `Boot` has succeeded and when its parts are invalid. The agent does nothing to work in progress at the snapshot: commands keep running in the restored guest, and cut streams are resumed by the client as ADR 0014 provides. User-space random state is not the agent's to change.
- **The entrypoint is the exec record `entrypoint`.** The agent starts it through the exec table, so its output is read with offsets, it is signalled and its end is recorded as any command's is, and the exec ID `entrypoint` belongs to it: an `Exec` under that ID is a repeat and runs nothing. It inherits no environment but the one described. Its output is carried by the channel and not by the serial console.
- **PID 1 duties.** The agent is the init of the Machine:
  - *Reaping.* On every child exit it waits for the exited children it did not start, which are the processes orphaned onto it; the children it did start are waited for by the exec table, so their exit status is never taken. This reads the zombies from `/proc` and needs it mounted.
  - *Termination.* It forwards `SIGTERM` and `SIGINT` (the signal the kernel sends init on a ctrl-alt-del) to the entrypoint as the signal received. A request when the entrypoint is not running (before it runs, or after it failed to start) ends the Machine, since there is nothing to terminate.
  - *The `Terminate` call.* `GuestService.Terminate` asks for the same thing as `SIGTERM` to init, and is how a graceful stop reaches the agent whatever the VMM and the kernel, since the VMM's keyboard and power requests need devices a kernel may lack ([ADR 0018](./adr/0018-a-graceful-stop-goes-through-the-guest-agent-and-the-vmm-request-is-the-fallback.md)). It sends `SIGTERM` into the loop that handles the signals to init, and one function applies the rule to both, so a call when the entrypoint is not running ends the Machine as a signal does. It is served before `Boot` has succeeded, returns when the agent has taken the request and not when the Machine has ended, and a repeat sends `SIGTERM` again. The request carries no signal. `guest-agent-channel` refuses it as a failed precondition.
  - *The entrypoint's end.* When the entrypoint exits, its record is final for every client reading it, the agent writes one line saying how it ended to the console, stops accepting calls, waits up to five seconds for connected clients to finish, and powers the Machine off through `reboot(RB_POWER_OFF)`.
  - *It never returns.* The kernel panics when init exits, so a failure of the agent itself (preparing the guest, listening, the server stopping, the power-off) is written to the console and ends the Machine the same way, and so is a panic on any thread and the runtime failing to build: a panic hook runs the same sequence before the process could abort. A power-off that returns has failed: the agent then calls `reboot(RB_AUTOBOOT)`, and if that returns too it waits for ever. The console line for a panic is `mvmd-guest-agent: panic: <message and location>`.
  - *The console lines.* Each is one line that begins `mvmd-guest-agent: `, which the VMM's console carries to the run directory's log, where the daemon reads it, through the Driver's `ConsoleLog` ([driver.md](./driver.md)), when it had no stream open on the entrypoint: a read of the record `entrypoint` of a Machine that is Stopped or Faulted, or Running with a guest that no longer answers, is answered from these lines, and one that none of them speaks of is cut short. They are `entrypoint exited code=<n>`, `entrypoint exited signal=<n>`, `entrypoint not started reason=<text>`, `entrypoint ended reason=<text>` (cut short), `terminated before the entrypoint ran`, `boot failed step=<step> detail=<text>` and `failed to <what>: <error>` for the agent's own failures.
- **A host-side binary serves the channel alone, for tests.** `guest-agent-channel` (`guest-agent/crates/guest-agent/src/guest_agent_channel.rs`) serves `GuestService` on a Unix socket through `guest_agent::serve`, answering the `CONNECT <port>` handshake of a Firecracker host-side socket when given `--handshake-port`; it is a test seam, built by `make build` for the host, and is not in the initrd or shipped.
- **The initrd is the agent, alone.** `make build` writes `guest-agent/target/initrd.cpio`, an uncompressed cpio archive in the kernel's newc format with the statically linked musl binary as `init`, so the kernel needs no decompressor beyond `CONFIG_BLK_DEV_INITRD`. `guest-agent/crates/mkinitrd` names the one file and `lib/initrd/` writes the archive, with fixed owner, times and inode numbers. `make build` builds the initrd's binary with the workspace, Cargo's home and the target directory remapped to fixed names (`--remap-path-prefix`; the `trim-paths` profile key is unstable in the pinned toolchain), so it carries no path of the machine that builds it, and it checks that two builds give one digest by building a second time in a fresh target directory. The initrd's binary is therefore built with other flags than the host and shipped builds of the same command. The agent creates the mount points it needs and attaches `/dev/console` again from devtmpfs, so the archive holds no directory or device node. At the switch root it deletes the initramfs's files, as `switch_root(8)` does, when the root is a ramfs or a tmpfs; mounts are left.
- **The overlay.** Lower: the EROFS, holding no whiteouts or opaque marks ([image.md](./image.md) §Conversion). Upper and work directories: on the root disk, an ext4 filesystem the host formatted ([ADR 0009](./adr/0009-a-machines-root-disk-is-a-sparse-raw-file-with-one-holder.md)).
- **Integrity is not the guest's.** The host kernel verifies every read of the EROFS file ([image.md](./image.md) §Integrity), so the agent sets up no verity device.
- **The host never mounts a guest disk.** A host kernel would interpret an untrusted filesystem, and a second writer would be possible (#2 §2, and §5 security). The host formats a root disk once, before any guest has written it, and reads nothing from it afterwards.
- **Language: Rust**, because one runs per VM and memory and start time matter (#2 §5, implementation language).
- **Guest kernel.** Build and management are a separate project, created at the prototype stage when mvmd first needs to build a kernel itself. The reasons are the GPLv2 source-distribution obligation and a build toolchain and update cadence different from mvmd's. Until then mvmd holds no kernel configuration or patches (guest kernel reply). The kernel conditions the Guest Agent requires are stated explicitly (#2 §5).
- **The kernel is a pinned input.** The node's configuration names one kernel file per architecture and its SHA-256; mvmd checks the digest before every boot, converter included, and records it in inspect and in each snapshot. On x86_64 it is an uncompressed ELF kernel with a PVH entry, on aarch64 a PE `Image` ([ADR 0010](./adr/0010-a-machine-boots-a-pinned-kernel-and-the-guest-agent-initrd-from-raw-block-devices.md)).
- **Kernel conditions**, built in since the initrd carries no modules: `CONFIG_BLK_DEV_INITRD`, `CONFIG_VIRTIO_BLK`, `CONFIG_VIRTIO_VSOCKETS`, the virtio transport of the Driver's VMM, `CONFIG_EROFS_FS`, `CONFIG_OVERLAY_FS`, `CONFIG_EXT4_FS`, and on x86_64 `CONFIG_PVH`. The agent's own code adds `CONFIG_DEVTMPFS` (it mounts devtmpfs), `CONFIG_PROC_FS` and `CONFIG_PROC_SYSCTL` (it scans `/proc` and writes `/proc/sys`), `CONFIG_SYSFS` (it reads `/sys/class/block` and `/sys/class/net`, and writes the PCI bus's `rescan` and a device's `remove` for a hot-plugged disk), `CONFIG_PCI` and `CONFIG_VIRTIO_PCI` (the transport a hot-plugged disk arrives on under Firecracker, which runs with `--enable-pci`; Kata Containers 4.3.1's kernel has both `=y`), `CONFIG_HOTPLUG_CPU` (the `online` file of a CPU; Kata Containers 4.3.1's kernel has it `=y` on x86_64 and aarch64, garamsh/mvmd#176 research §3), `CONFIG_NET`, `CONFIG_INET` and `CONFIG_VIRTIO_NET` (rtnetlink, IPv4 and the one device it configures) (ADR 0010). The kernel's own reseed after a restore, which the agent's `CatchUp` does not wait on, needs `CONFIG_VMGENID` and, on x86_64, `CONFIG_ACPI` ([ADR 0016](./adr/0016-a-restored-guest-reseeds-from-host-entropy-and-takes-its-time-from-the-host.md)). The agent's own reseed and time setting use the `/dev/urandom` ioctls and `clock_settime`, which no configuration removes. For a node that serves IPv6, `CONFIG_IPV6` ([ADR 0011](./adr/0011-each-machine-gets-a-routed-tap-and-addresses-mvmd-assigns.md)).
- **A published kernel meets every kernel condition but one.** The kernel configurations Firecracker v1.17.0 and Cloud Hypervisor's `ch-7.2.8` branch publish leave EROFS out. Kata Containers 4.3.1 ships a kernel (6.18.56) whose own configuration has every condition built in on x86_64 and aarch64 except `CONFIG_VMGENID`, which is not set; the agent's `CatchUp` does not wait on it ([ADR 0016](./adr/0016-a-restored-guest-reseeds-from-host-entropy-and-takes-its-time-from-the-host.md)). What was checked, in which file and version, is under Rationale. A kernel meeting the conditions is supplied to the node from outside mvmd (ADR 0010). **Decision (PM, 2026-11-09):** the first real Machine and the Driver end-to-end tests boot on Kata Containers 4.3.1's kernel 6.18.56 (`vmlinux-6.18.56-208`), pinned by the SHA-256 digests under Rationale. The guest kernel project is created when a condition no published kernel meets becomes necessary, or when the missing `CONFIG_VMGENID` is shown to matter.

## Rationale

- Why a Rust agent in a Go project: [ADR 0001](./adr/0001-mvmd-is-a-containerd-like-microvm-runtime-that-does-not-know-gaon.md); the cost of two languages is acknowledged in #2 §5.
- Why exec and files go through the agent and not the host: #2 §2.
- Why devices are found by filesystem UUID and the kernel is pinned by digest, and the kernel configurations checked: [ADR 0010](./adr/0010-a-machine-boots-a-pinned-kernel-and-the-guest-agent-initrd-from-raw-block-devices.md).
- Restore concerns the agent must address after a snapshot restore: vsock connections are reset (Firecracker resets them on restore), the guest clock jumps, and cloned guests share random state (#2 §2). What the pinned VMMs offer for each, and why the agent does the work itself: [ADR 0016](./adr/0016-a-restored-guest-reseeds-from-host-entropy-and-takes-its-time-from-the-host.md).

## Open questions

- **How the agent identifies a disk the Machine booted with, and what the guest does with any non-root disk (#2 §6 item 9).** A disk attached at create has no recorded ID, so `ReleaseDisk` answers `NOT_FOUND` and a Running Machine cannot detach it (stop first). The agent stops at finding and releasing a hot-plugged disk until item 9 says what a disk is for, and whether it has an identity the agent can match.
- **Guest kernel management and the allowed scope of user-supplied kernels (#2 §6 item 11).** The first real Machine boots on a published kernel (Current decisions), so what remains open is when the guest kernel project is created (a condition no published kernel meets becomes necessary, or the missing `CONFIG_VMGENID` is shown to matter), and the scope of user-supplied kernels.
- **Whether `reboot(RB_POWER_OFF)` ends a Machine on each VMM.** Not verified: the code states no VMM's power-off behaviour, and the Firecracker Driver's end-to-end test is where it is checked. If a VMM ends only on a reset, the agent's power-off call changes with it.
- **Whether the daemon's read of the console log is enough for the exit code.** The agent powers off a few seconds after the entrypoint ends, so a daemon with no stream open on the record learns the code from the console line in the run directory's log (PID 1 duties); that the log is complete at that moment is the Driver's to establish.
