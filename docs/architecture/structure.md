# Structure

The shape mvmd is partitioned into, what may reference what, how the repository is laid out, and when a new port is earned.

Checked against garamsh/discussions#2 as read on 2026-11-08 (decision-change reply discussioncomment-19466961) and against garamsh/garam at commit 743f7b390ac60cb18ae3ba6e867237a57fe8cc8f, `docs/architecture/structure.md` §Services. Claims about #2 hold for those; they promise nothing about later edits of the discussion.

## The shape

mvmd is a hexagonal application ([ADR 0002](./adr/0002-mvmd-is-structured-as-a-hexagonal-application.md)). The inside is the Machine lifecycle on one node and the invariants over it; it names no VMM, disk, network, registry or wire format. Adapters translate between the inside and each technology.

The inside is not divided into rings. The Go package layout of `docs/convention/stack-go.md` §1 is file placement and adds no direction rule between packages inside it.

Nothing here states how an adapter is built inside, or how mvmd is deployed.

## Repository layout

Follows the monorepo shape of garamsh/garam at the commit above: each top-level folder is one responsibility, and one unit reaches another only through what that unit publishes. A folder is created by the pull request that first adds code to it, and not before.

- `daemon/` — the mvmd daemon: a Go module in the service layout of `docs/convention/stack-go.md` §1, binary at `daemon/cmd/mvmd/main.go`. It holds the inside, the driving adapter for the runtime API, and every driven adapter, including the in-process VMM Drivers. The inside is four packages, `daemon/internal/machine/` for the Machine lifecycle, `daemon/internal/fencing/` for the fencing deadline, `daemon/internal/events/` for the node's event log and `daemon/internal/image/` for Pull image and the start-up sweep of the image cache, with the in-memory substitute of each driven port under the `memory/` folder of its package. Around them: `daemon/internal/app/` is the composition site, which `main.go` calls (`docs/convention/stack-go.md` §1 "Project envelope"); `daemon/internal/api/` is the driving adapter for the runtime API; `daemon/internal/boltstore/` is the State Store and Deadline record adapter, on bbolt; `daemon/internal/bootclock/` is the Clock adapter, on the host's boot clock; and `daemon/internal/imagestore/` is the Image Store adapter, the node image cache as an OCI image layout with fs-verity. `daemon/internal/drivertest/` is test-support only: the real scenarios every VMM Driver is held to, which each Driver's real test calls under its own build tag, and the root of the supervisor's shape those tests run the VMM in ([driver.md](./driver.md)). What both VMM Drivers do the same way is defined once, in a leaf named for what it does, and each Driver calls it: `daemon/internal/vsockdial/` connects to a guest's port through the hybrid vsock socket, `daemon/internal/vmconsole/` reaches the serial console the supervisor leaves, as a live session and as a log, `daemon/internal/hostcpu/` names the host's CPU model, and `daemon/internal/pinnedfile/` checks a file against its pinned SHA-256. What differs by VMM stays in its Driver: the API client, the boot sequence and the process description.
- `daemon/cmd/mvmd-supervisor/main.go` — the per-Machine supervisor that enforces the fencing expiry ([runtime.md](./runtime.md) §Fencing), and the per-conversion one that enforces a conversion's time limit, a second binary of the daemon module. Each confines the VMM it starts ([runtime.md](./runtime.md) §VMM confinement). It holds no part of the inside, and its `main.go` wires only itself; the application's one composition site stays with `daemon/cmd/mvmd/main.go`. The supervisor's process is `daemon/internal/supervisor/`; the conversation between mvmd and it is `daemon/proto/mvmd/supervisor/v1alpha1/`, with its generated Go in `daemon/internal/supervisorapi/v1alpha1/`. The names of the files it makes in a Machine's state directory, and where each sits, are defined once in `daemon/internal/statedir/`, a leaf that imports nothing of mvmd; the supervisor, the supervision adapter and every Driver use that definition, so none imports another for a file name. How a socket in that directory is bound, connected and waited for is defined once in `daemon/internal/unixsock/`, another leaf that imports nothing of mvmd, which the supervisor, the supervision adapter and the Firecracker and Cloud Hypervisor Drivers use ([runtime.md](./runtime.md) §VMM confinement).
- `guest-agent/` — the Guest Agent as its own Cargo workspace (#2 §5, implementation language). Its Rust code follows `docs/convention/stack-rust.md`. The guest channel's contract is `guest-agent/proto/mvmd/guest/v1alpha1/`, which the daemon reaches only as that file ([ADR 0014](./adr/0014-the-guest-agent-serves-a-grpc-contract-it-owns-over-vsock.md)).
- `lib/runtimeapi/` — the runtime API contract and its client, a Go library module in the library layout of `docs/convention/stack-go.md` §1, package at the module root. It is the one module gaon imports. It is a leaf: it imports no other package of mvmd.
- `imageconv/` — the image converter that runs inside the converter microVM, and the build of its initrd ([ADR 0005](./adr/0005-untrusted-images-are-converted-in-a-converter-microvm.md)): its own Cargo workspace, whose Rust code follows `docs/convention/stack-rust.md`. It holds no part of the inside and links nothing of the daemon; the daemon reaches it only over the Converter channel. The channel's contract is `imageconv/proto/mvmd/convert/v1alpha1/`, which the daemon reaches only as that file, and `imageconv/mkfs-erofs/` builds the `mkfs.erofs` the initrd carries ([ADR 0017](./adr/0017-the-converter-serves-a-grpc-contract-it-owns-and-carries-mkfs-erofs-in-its-initrd.md)).
- `e2e/` — the end-to-end tests: a Go module that holds only tests, behind the `firecracker_real` build tag, and a `doc.go` that lets the package be listed without the tag. They run the built `mvmd` and `mvmd-supervisor` on the pinned Firecracker, with the converter's and the Guest Agent's initrds, against a registry the tests serve themselves, and reach the daemon only through `lib/runtimeapi/` as a client does. `make test-e2e` runs them, and the `e2e` job of the pipeline. It imports nothing of `daemon/`: that `internal/` encloses.
- `mvmctl/` — the name reserved for a CLI, a top-level folder if and when it ships as its own executable. It is not committed to existing.
- `docs/` — conventions, architecture, procedures.
- `tooling/protogen/` — a Go module that holds nothing but the pins of the protobuf generator (`buf`, `protoc-gen-go`, `protoc-gen-go-grpc`) as `tool` directives, released versions only, with `protoc-gen-go` at the version of the library's `google.golang.org/protobuf`. It ships no package and is not in `go.work`, so the generator's dependencies stay out of every unit's graph.
- `tooling/firecracker/` — `fetch.sh`, which holds the pins of the Firecracker binary and of the guest kernel the Driver's tests boot, each by the SHA-256 its release publishes, and fetches them for `make test-firecracker` ([driver.md](./driver.md)). It ships no package.
- `tooling/cloud-hypervisor/` — `fetch.sh`, which holds the pin of the Cloud Hypervisor binary the Driver's tests boot, by the SHA-256 its release lists, and fetches it for `make test-cloud-hypervisor`; the kernel is the Firecracker one's ([driver.md](./driver.md)). It ships no package.
- `deploy/` — added later, by the first pull request that needs one.
- `go.work` at the root, naming every Go module that ships code and carrying the one `toolchain` line every check and the pipeline use. The root holds no Go package.
- `lib/` holds libraries linked by more than one unit and no binary. It has no `shared/`, `utils/` or `common/`; a package one unit alone imports belongs to that unit.
- A unit reaches another only through what it publishes: Go's `internal/` encloses `daemon/` and keeps other modules out of it. The daemon's inside does not import `lib/runtimeapi/`; the driving adapter does, and converts between its types and the driving port's.

## Boundaries and dependency direction

- **The port is the unit.** One port per conversation with the outside, named for that conversation and never for the technology serving it.
- **Dependencies point inward.** An adapter references the application; the application references no adapter. A technology's name inside the application — a framework type, a driver, a wire format, a table — is a defect, even where the language permits it.
- **Every crossing goes through a port.** A driving adapter reaches the application only through a port; the application reaches the outside only through a port an adapter implements. Something outside reached from the inside without a port is a defect even where the call compiles.
- **A port is declared in the application's terms.** Its operations and the types crossing it are the application's, and converting them to and from the technology's is the adapter's work. A type belonging to the technology in a port's signature puts the outside inside.
- **An adapter's only counterpart is its port.** One adapter calling another carries application work outside, where no port names it and no substitute stands in for it.
- **A new port is earned** by a conversation whose technology can be replaced without the application changing, and which the application can name without naming that technology. Cockburn's statement expects two or more adapters on a port — the real technology, and one for a test harness (*Hexagonal architecture*, 2005) — so a port with a single adapter that nothing substitutes is indirection.
- **Whether the inside is itself partitioned is contested.** Cockburn's statement leaves it undivided. Later readings built on it — Jeffrey Palermo's Onion Architecture (2008), and Robert C. Martin's *Clean Architecture* (2017), which names hexagonal among its sources — divide it into concentric rings with the subject matter innermost and every reference pointing inward. A project takes one, records which, and under the second a reference pointing outward from an inner ring is a defect.

Here the last bullet is taken as follows: the inside is not divided into rings, so no reference inside it is a defect for its direction.

## Shape rules every project carries

- **The application has one composition site.** It is the one place that constructs concrete implementations, and it decides which implementation each declared abstraction receives.
- **Every other unit receives what it depends on and constructs none of it**, whatever the shape makes the unit — a domain, a layer, or an adapter.
- **The composition site stays thin.** It constructs and passes; it decides nothing else.

In mvmd the composition site is in the daemon, placed as `docs/convention/stack-go.md` §1 "Project envelope" places it.

## Rationale

- Why this shape: [ADR 0002](./adr/0002-mvmd-is-structured-as-a-hexagonal-application.md).
- Why mvmd is a leaf that gaon depends on: [ADR 0001](./adr/0001-mvmd-is-a-containerd-like-microvm-runtime-that-does-not-know-gaon.md); the principle is #2 §3 principle 3 (dependency direction is one-way).
- Why no layer that only forwards: #2 §3 principle 6; why few concepts: principle 7.
- Why Pull image is its own inside package and not part of `machine/`: it is a domain with verbs of its own, Pull and Sweep, and with dependencies the lifecycle never uses (the Registry, the Converter channel, the staging half of the Image Store); it is serialized per digest, where the lifecycle is serialized per Machine; and the lifecycle uses one operation of the Image Store, `Locate`. `fencing/` set the pattern: a separate package that imports `machine/` for the ports and types it shares, here the Driver, Supervision, the Image Store's `Locate`, the run configuration and the outcome kinds, while `machine/` imports nothing of it. This decision changes no rule of this document, so no ADR records it.
