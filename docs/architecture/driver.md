# VMM Driver

The contract between the mvmd inside and a virtual machine monitor, and what implements it first.

Checked against garamsh/discussions#2 as read on 2026-11-08, §5 (discussioncomment-19288321) and the decision-change reply (discussioncomment-19466961). Claims about what a VMM supports in the resizing table are #2's, which marks the Firecracker entry as needing a version check; claims about boot formats, disks and network devices are ADR 0009's, ADR 0010's and ADR 0011's, and claims about what a VMM opens and filters are ADR 0015's, at Firecracker v1.17.0 and Cloud Hypervisor v54.0; claims about the Cloud Hypervisor Driver are its v54.0 documentation and source; the names of the files in the VMM's root and the check of the pinned files are ADR 0019's.

## Current decisions

- **The VMM is swappable behind a Driver port.** Firecracker and Cloud Hypervisor are the first two Drivers; a VMM written later in-house must be admissible through the same contract (decision-change reply). The contract is stated in VMM-neutral terms and no VMM's vocabulary appears in it ([structure.md](./structure.md) §Boundaries and dependency direction).
- **Operations.** The contract covers create (configure without booting), start, stop, destroy, pause, resume, snapshot, restore, disk attach and detach, a read of one disk's drive ([ADR 0023](./adr/0023-a-restart-settles-a-running-machines-disks-against-the-vmms-drives.md)), memory target, inspect, list, and an event stream (#2 §5, Driver interface draft). The draft's signatures are not transcribed here; the code is the source of truth once it exists.
- **Capability negotiation (#2 §5 design principle 1).** A VMM reports which optional operations it supports, and the client matches a Machine's required capabilities to a node. The contract is not cut to what every VMM supports. An operation whose capability the Driver does not report returns an error wrapping `machine.ErrUnsupported`, so a refusal for the capability is told from a refusal for any other cause.
- **Snapshot compatibility (principle 2).** A snapshot records the Driver name and version, the CPU model and the guest kernel. A snapshot does not move to another VMM, and the contract says so. Restore compares the Driver name, version and CPU model with the Driver in service and refuses a snapshot that differs; the kernel is recorded and not compared. The Driver reports its CPU model and the kernel digest; snapshot and restore are the optional capability `snapshot`.
- **Idempotency and post-failure state (principle 3).** Create-type calls carry a request ID, and each operation defines the state a VM is left in when it fails.
- **Restart (principle 4).** The VMM runs as its own process; mvmd reattaches to running VMs after its own restart through `List`.
- **The Driver does not start the VMM process.** For start and restore it describes the process to run, and mvmd starts it under the Machine's supervisor, which enforces the fencing expiry ([runtime.md](./runtime.md) §Fencing). Every process a Machine needs runs under that supervisor, and none runs under a real-time scheduling policy. The Driver never sees the expiry, so a new VMM is fenced without fencing code of its own ([ADR 0003](./adr/0003-a-per-machine-supervisor-enforces-the-fencing-expiry.md)).
- **The VMM's needs for confinement.** The description of the VMM process also states, in VMM-neutral terms: the executable, the host files the VMM reads beyond the boot artefacts, the device nodes it opens, whether it takes its network device by descriptor, and its memory, task and CPU overhead. The supervisor confines the VMM from these alone ([runtime.md](./runtime.md) §VMM confinement), so a new VMM is confined by its Driver with no supervisor code. The description grants no capability, chooses no user and skips no step ([ADR 0015](./adr/0015-the-supervisor-confines-every-vmm-process-the-same-way.md)).
- **What the root looks like to the Driver** ([ADR 0019](./adr/0019-a-vmm-sees-its-machines-files-at-fixed-paths-in-its-root.md)). The Machine's files are at fixed paths in the VMM's root, the same for every Machine: the kernel `/boot/kernel`, the initrd `/boot/initrd`, the block device at position `n` of the boot description `/disk/n`, the run directory `/run`, and for a restored VMM the directory `/snapshot`, where the snapshot's files are bound read-only and the Driver names its own files under it. The names are constants of `daemon/internal/machine/`, and the Driver writes only them into its VMM's arguments and requests, the API and vsock sockets among them, so a snapshot records no host path. The description carries each boot file's host path and its fixed path, and a pinned file's SHA-256, which the supervisor checks on the file it mounts. The VMM executable, the host files and the device nodes the Driver names stay at their host paths. mvmd reaches the sockets at the run directory's host path. The boot description carries that directory, and it is the one the supervisor is given: the Supervision adapter names it, the lifecycle passes it to the Driver and to the supervisor, and the Driver cannot change the supervisor's. A tap taken by descriptor is the VMM's descriptor 3; the Driver writes `3` where its VMM wants the descriptor. A VMM that takes no descriptor is passed none.
- **The VMM's own syscall filter stays on.** A Driver never starts its VMM with its seccomp filter disabled or relaxed; the filter is stacked over the supervisor's baseline.
- **By VMM, at the pinned versions (ADR 0015).** Firecracker opens `/dev/kvm` and `/dev/net/tun` and takes its tap by name, so it runs in the host's network namespace. Cloud Hypervisor opens `/dev/kvm`, and `/dev/urandom` for the virtio-rng device it adds by default (the erratum of ADR 0015), and takes its tap by descriptor, so it runs in a network namespace of its own. Both create their API and vsock sockets as paths in the run directory, and on aarch64 both read `/sys/devices/system/cpu/cpu0/cache`, Firecracker also `midr_el1`.
- **The Firecracker Driver (`daemon/internal/firecracker/`), at v1.17.0.** The node's configuration names the Firecracker binary, the kernel and the initrd by absolute path, and the binary and the kernel by SHA-256; the Driver checks both digests when mvmd starts, so a node fails there, and states them in every description, where the supervisor checks the file it mounts before every boot ([ADR 0010](./adr/0010-a-machine-boots-a-pinned-kernel-and-the-guest-agent-initrd-from-raw-block-devices.md), [ADR 0019](./adr/0019-a-vmm-sees-its-machines-files-at-fixed-paths-in-its-root.md)). Boot asks the VMM for its version and refuses any but 1.17.0, so the version in `Info`, which snapshots record, is the VMM's. What it states and does:
  - **The process.** `--api-sock` at `/run/api.sock` and `--enable-pci`, so the virtio devices are PCI devices, which is the transport v1.17.0's device hot-plug needs (`docs/device-hotplug.md`). No seccomp option is passed. The boot files are the kernel and the initrd read-only, then the Machine's devices as given, each at its fixed path. It opens `/dev/kvm`, and `/dev/net/tun` only for a Machine with a network device. Its overhead is 128 MiB of memory, one CPU and eight tasks beside the vCPUs (an idle VMM with two vCPUs had five); the memory and task figures are not measured under load. On aarch64 it names `/sys/devices/system/cpu/cpu0/cache` and `.../regs/identification/midr_el1` (untested there).
  - **The sockets.** The Driver connects to `api.sock` and `vsock.sock` through a descriptor of the run directory ([runtime.md](./runtime.md) §VMM confinement), so no run directory is too long for them and Describe refuses none for its length.
  - **The Driver keeps nothing between Describe and Boot or Restore.** `Boot` and `Restore` are given the boot description the lifecycle passed to Describe, so no file in the run directory, which belongs to the VMM's user, is trusted for a host decision, and a repeated Boot or a restarted daemon needs no Describe.
  - **The console.** Firecracker's own log goes to `firecracker.log` in the run directory (`--log-path`), so `vmm.log`, the supervisor's capture of the VMM's output, holds the guest's serial console. `ConsoleLog` reads it up to its size at the call, opening it without following a link and refusing anything but a regular file. The supervisor reads the VMM's output to its end into that file before it exits, so the log of a VMM that has ended is complete unless a descendant of the VMM kept the output open ([ADR 0020](./adr/0020-the-supervisor-serves-the-vmms-serial-console-on-a-socket-outside-its-root.md)). The Driver reports the capability `console`: Firecracker's serial device is the VMM's standard input and output, which the supervisor connects to `console.sock` in the Machine's state directory, beside the run directory and outside the VMM's root, and `Console` connects to it. A socket that is absent or refuses is a VMM that has ended, "the console is not available". A session reads what the guest writes after it connected and what it writes is the guest's serial input, which the guest's line discipline echoes once a process holds the console open.
  - **Boot.** After the API socket accepts a connection: machine configuration, boot source (the command line is mvmd's `console=ttyS0 reboot=k panic=1`, plus, on x86_64, the i8042 probe parameters the Firecracker documentation gives), each device as a drive in order, at `/disk/<n>`, named as §Disk attach and detach says (read-write ones with `cache_type` `Writeback`, so the guest's flushes reach the file), the network interface `eth0` with the tap's name and the guest MAC, the vsock device at CID 3 with `/run/vsock.sock`, and `InstanceStart`. Every call is on the context the lifecycle gives.
  - **`GuestConn`.** Firecracker answers `CONNECT <port>` with `OK <n>` where `n` is the host-side port it assigned the connection, not the guest's port (`docs/vsock.md`); the Driver accepts any decimal.
  - **Stop.** `Shutdown` sends `SendCtrlAltDel` and waits up to the grace for the API socket to go away; only a missing socket file or a refused connection counts as the VMM having ended, and any other dial error is returned. The action reaches a guest only through the guest kernel's i8042 and AT keyboard drivers (`CONFIG_SERIO_I8042`, `CONFIG_KEYBOARD_ATKBD`; `docs/api_requests/actions.md`), which the pinned Kata kernel does not build (`# CONFIG_SERIO is not set` in its configuration), so with it the wait runs its whole grace and the supervisor then ends the VMM. v1.17.0 sends it on x86_64 only. It is the lifecycle's fallback and not its first request ([ADR 0018](./adr/0018-a-graceful-stop-goes-through-the-guest-agent-and-the-vmm-request-is-the-fallback.md)): a graceful stop asks the Guest Agent first, and calls `Shutdown`, with what is left of the grace, only when that request does not succeed, the Machine is Paused or the grace is zero.
  - **The pins.** The binary's tarball and binary digests, and the test kernel's (Kata Containers 4.3.1, as `guest.md` decides), are in `tooling/firecracker/fetch.sh`. They move by a pull request that edits them and reruns `make test-firecracker`. No bot proposes the move, since Dependabot does not read a shell script, so the PM owns it: the pins are reviewed against each project's releases and security advisories monthly, and at once when an advisory names the pinned version.
  - **Tests.** The Driver's requests are tested against a fake API socket in `make test`. The real scenarios live in `daemon/internal/drivertest/`, a suite any Driver runs: each Driver's real test is a thin caller under its own build tag that supplies the Driver, the start of its VMM and the checks only its VMM can make, which for Firecracker is the drive list read over its API socket, and a scenario for a capability the Driver does not report asserts that the Driver refuses the operation instead of being skipped. `make test-firecracker` runs the Firecracker caller: it boots the pinned binary on the pinned kernel with the Guest Agent's initrd, through the Driver, as the user running it, in a root holding the files at their fixed paths (a mount namespace in a user namespace, or under passwordless sudo where the host refuses that; no supervisor, no tap), and reaches the Guest Agent through `GuestConn`; it also snapshots that Machine, restores the snapshot as a second Machine with a run directory and root disk of its own, and reaches the Guest Agent on both, with no tap, so `network_overrides` is tested against the fake only; it also attaches disks to a booted Machine and detaches them and a disk it was booted with, and reads the VMM's own drive list after each, though no guest rescans its bus to find them; it needs `/dev/kvm`, is not part of `make ci`, and is a job of its own in the pipeline.
  - **Snapshot and restore.** The Driver reports the capability `snapshot`, which covers restore.
    - **Snapshot** takes the Machine paused, as the lifecycle holds it, and sends `PUT /snapshot/create` for a full snapshot with its state at `/run/snapshot.state` and its memory at `/run/snapshot.mem`, paths in the VMM's root. It returns the two files at the run directory's host path, `snapshot.state` and `snapshot.mem`, the same on every snapshot of a Machine, so a repeat writes over the files of the one before and over what a failed attempt left (Firecracker truncates the state file and rewrites the memory file of a full snapshot in whole). It returns the pinned kernel's digest. A snapshot Firecracker refuses (a guest that is not paused) is returned as its refusal, with no file named.
    - **DescribeRestore** takes the two files by name, wherever the Snapshot Store holds them, and refuses anything but that one pair. The description binds them read-only at `state` and `memory` under the fixed directory `/snapshot` (`machine.InSnapshotDir`), and the Machine's own devices at `/disk/<n>` as Boot does, so the drive paths the snapshot recorded exist in the new root. It lists no kernel and no initrd, which a restored guest has already loaded. The binary, the arguments and the device nodes are Describe's, `--enable-pci` included since the snapshot records PCI devices.
    - **Restore** waits for the API socket, refuses a VMM that is not 1.17.0, and sends `PUT /snapshot/load` with the memory backend `File` at `/snapshot/memory`, `resume_vm`, and, when the Machine has a tap, `network_overrides` for `eth0` with the new Machine's tap. The MAC is the one in the snapshot and no request names one, as no interface is configured around the load. The vsock device's socket is `/run/vsock.sock` in the snapshot as at boot, so no override is needed. The tap is the one in the boot description `Restore` is given, as `Boot` is, so the Driver holds nothing between DescribeRestore and Restore and a restarted daemon needs no DescribeRestore.
    - **What a failed Restore leaves.** Firecracker takes a load on a fresh process only, and the lifecycle ends the VMM of a failed restore and releases what it allocated. The Driver deletes no file: the snapshot's files belong to the Snapshot Store, and the run directory goes with the Machine.
    - **The compatibility check is the lifecycle's.** The comparison of the recorded Driver name, version and CPU model with `Info`'s runs in `daemon/internal/machine/` before the Driver is called, as above, and the Driver supplies what it compares: the name, the version, the CPU model and the kernel digest. The Driver is given no record, so it compares nothing itself; beyond that, Firecracker's own load refuses a state written by another release.
  - **Disk attach and detach.** The Driver reports the capability `disk-hotplug`. v1.17.0 hot-plugs and hot-unplugs virtio block devices on the PCI transport (`docs/device-hotplug.md`, a developer preview): the pre-boot `PUT /drives/{drive_id}` is accepted after the start, and `DELETE /drives/{drive_id}` unplugs. `firecracker.yaml` lists no `DELETE`; the document and the API server's request table do, so the Driver relies on them.
    - **Drive names.** A drive that holds a disk is named `disk_` and the hex of the SHA-256 of the disk's ID, which is the same length for any ID, so the name stays within a file name's limit as the link of an attached disk, within the letters, digits and underscores Firecracker accepts, and distinct for two IDs; the image, which holds no disk, is `disk<n>` by position. Boot names its drives this way too, so a disk the Machine was started with is detached as one attached later is.
    - **Attach** hard links the disk's file into the run directory under the drive's name, then sends `PUT /drives/<name>` with `path_on_host` `/run/<name>`, read-write ones with `cache_type` `Writeback` as at boot. The VMM opens only what its root holds, and the root is fixed when the supervisor starts it; the run directory is the one place mvmd adds files to a running VMM ([ADR 0015](./adr/0015-the-supervisor-confines-every-vmm-process-the-same-way.md)), so the link is how the file gets there and the disk's file and the run directory are on one file system. The Driver refuses a path that is not absolute or a file that is not a regular one (a link made to a symbolic link would name a host path in the root), removes what stands at the link's name without following it, and removes the link again when Firecracker refuses the drive.
    - **Detach** sends `DELETE /drives/<name>`, then removes the link; a disk given at boot has none. The link stays when Firecracker refuses, since the VMM still has the drive.
    - **The guest is not told.** v1.17.0 delivers no hot-plug notification: the guest finds an attached disk when it rescans its PCI bus and must release a disk before it is unplugged (`docs/device-hotplug.md`). Neither is the Driver's to do, since it has no channel to the guest.
    - **Drive** is the port's read of one disk's drive on the running VMM ([ADR 0023](./adr/0023-a-restart-settles-a-running-machines-disks-against-the-vmms-drives.md)): absent, given at boot, or added since boot. It sends `GET /vm/config` and finds the drive by the disk's name; one at its link in the run directory (`/run/<name>`) was added to the running VMM, and any other path is a device the boot gave it. It changes nothing. The drive's name cannot be turned back into a disk ID, so the Driver is asked of one disk and does not list.
    - **`PATCH /drives/{drive_id}`** (new `path_on_host` or rate limiter, after boot) is not used: the contract has no operation that changes a disk of a running Machine, so a disk's size is not changed in place.
  - **Resize is refused, and not reported as a capability.** `Resize` answers `machine.ErrUnsupported` and says why. The vCPU count is accepted before boot only (`firecracker.yaml`, `PUT` and `PATCH /machine-config`, "Pre-boot only"), and memory resizing is a virtio-mem region (`docs/memory-hotplug.md`, `PUT /hotplug/memory`, "only allowed before the `InstanceStart` action") or a balloon (`PUT /balloon`, "before machine startup") that the VMM must be configured with before it starts; Boot configures neither, so there is nothing for a resize to change.
- **The Cloud Hypervisor Driver (`daemon/internal/cloudhypervisor/`), at v54.0.** Configured, and checked at start and in every description, as the Firecracker Driver is: binary, kernel and initrd by absolute path, binary and kernel by SHA-256. What it states and does, read from the v54.0 release's `docs/api.md`, `docs/device_model.md`, `docs/vsock.md` and its source (`vmm/src/config.rs`, `serial_manager.rs`):
  - **The process.** The whole VM is on the command line, since the API takes a tap by name only and `NetConfig.fds` cannot be given as JSON, so Cloud Hypervisor creates and boots the VM itself: `--api-socket` and `--log-file` in `/run`, `--kernel`, `--initramfs`, `--cmdline console=ttyS0` (`console=ttyAMA0` on aarch64), `--cpus`, `--memory`, `--serial tty --console off` (the defaults are the reverse: serial off, console on the tty), `--vsock cid=3,socket=/run/vsock.sock`, `--disk` with each device at `/disk/<n>`, and `--net fd=[3],mac=<guest MAC>` when there is a tap, which the supervisor passes as descriptor 3 (`TapByDescriptor`). It opens `/dev/kvm` and `/dev/urandom`, the source of the virtio-rng device it adds by default; the seccomp filter stays on.
  - **A guest panic does not yet end the VMM.** The command line carries `console=` only. At v54.0 a guest reset of any kind, which `panic=1` after a panic reaches, is handled by `vm_reboot()`: the VM is rebuilt from the same configuration and the VMM stays up (`vmm/src/lib.rs`, the `Reset` event); only a power-off, which a panic never reaches, ends it (same file, `guest_exit_evt`); and pvpanic only logs (`devices/src/pvpanic.rs`). So no command line makes a panicked guest end the VMM as `reboot=k panic=1` does under Firecracker, and without `panic=` the guest halts with the VMM Running. The Driver ending the VMM itself on a panic or reset event is #155; until then the Driver is not wired into the application.
  - **Overhead figures.** The VMM's memory overhead is Firecracker's figure and its task count is an estimate; neither is measured for Cloud Hypervisor, so neither is known to cover its peak (ADR 0015).
  - **Boot.** After the API socket accepts a connection: `GET /api/v1/vmm.ping`, refusing a VMM whose `version` is not 54.0 (v54.0 reports `54.0.0`), then `GET /vm.info` until the state is `Running`; it is a 404 until the VM is created and `Created` while it boots, and any other state is an error. The spec is not read.
  - **Pause, Resume, Shutdown.** `PUT /vm.pause`, `/vm.resume`, and `/vm.power-button` for Shutdown, which then waits up to the grace for the API socket to go away. Shutdown is only a fallback: a graceful stop goes through the Guest Agent ([ADR 0018](./adr/0018-a-graceful-stop-goes-through-the-guest-agent-and-the-vmm-request-is-the-fallback.md)), and the pinned kernel has no input device to act on a power button, so the wait may run its whole grace.
  - **The console.** Cloud Hypervisor's own log is `cloud-hypervisor.log` in the run directory, so `vmm.log` holds the serial console. `--serial tty` is the VMM's standard output, and its input is read only when standard input is a terminal (`serial_manager.rs`), which the supervisor's pseudo-terminal is ([ADR 0025](./adr/0025-the-supervisor-gives-the-vmm-a-raw-mode-pseudo-terminal-as-its-console.md)). `Console` and `ConsoleLog` are `daemon/internal/vmconsole/`'s, which the Firecracker Driver calls too. The Driver reports `console`.
  - **`GuestConn`.** The hybrid vsock handshake is `CONNECT <port>` answered by `OK <n>` (`docs/vsock.md`), as Firecracker's, so the Driver calls `daemon/internal/vsockdial/` as the Firecracker Driver does.
  - **Not yet implemented.** Snapshot, restore, disk attach and detach, `Drive` and resize answer `machine.ErrUnsupported`, and `Info` reports no capability for them though v54.0 has them; they are #141 and #142.
  - **The pins** are in `tooling/cloud-hypervisor/fetch.sh`: the static builds' SHA-256 as the GitHub release lists them, since it publishes no checksum file. The kernel stays pinned in `tooling/firecracker/fetch.sh`. They move as the Firecracker pins do, by a pull request that reruns `make test-cloud-hypervisor`, and the PM owns it.
  - **Tests.** The requests are tested against a fake API socket in `make test`. `make test-cloud-hypervisor` runs the `drivertest` suite under the build tag `cloud_hypervisor_real`, in a job of its own, as `make test-firecracker` does: the boot scenario passes, and the scenarios for capabilities not reported pass by the Driver refusing.
- **In-process first (principle 5).** Drivers are Go implementations inside the daemon, with messages shaped so that they can move to gRPC. An out-of-process Driver protocol, in the role containerd's shim API plays, is introduced when the first out-of-process VMM, such as an in-house one, arrives (decision-change reply). It keeps the VMM process started by the supervisor.
- **Boot artefacts ([ADR 0010](./adr/0010-a-machine-boots-a-pinned-kernel-and-the-guest-agent-initrd-from-raw-block-devices.md)).** A Driver boots a VM from: a kernel file (on x86_64 an uncompressed ELF kernel with a PVH entry, on aarch64 a PE `Image`, both taken by Firecracker and Cloud Hypervisor), an initrd file, a kernel command line, an ordered list of block devices each a file path and a read-only flag, one network device for a Machine and none for a converter, one vsock device, and the vCPU count and memory size. A Machine's devices are its image's EROFS read-only, its root disk read-write, then its attached disks; a converter's are its output disk alone. The Driver learns nothing of what each device holds.
- **A network device** is a tap's name and the guest MAC; the Driver learns no address or policy. On restore, the Driver attaches the snapshot's network device to the tap mvmd gives for the new Machine, not the one the snapshot recorded: Firecracker through `network_overrides`, Cloud Hypervisor through the restore's net file descriptors, which needs its devices attached by descriptor ([ADR 0011](./adr/0011-each-machine-gets-a-routed-tap-and-addresses-mvmd-assigns.md)).
- **The Driver opens the stream to the guest.** `GuestConn` takes a Machine and a guest port and returns a new byte stream to that port, ready for the Guest Agent's gRPC protocol; the Guest Agent channel adapter calls it with port 1024 (`guest.md`) for each call and again after a reset, and closes what it gets. Whatever the VMM needs before the first byte reaches the guest is the Driver's and is finished before the call returns: for Firecracker, connecting to the vsock socket in the run directory, writing `CONNECT <port>` and reading its `OK` line. A Machine whose VMM has ended is `ErrVMMEnded` joined with `ErrGuestUnreachable`; a guest that refuses the port is `ErrGuestUnreachable`. The adapter knows no socket path and no handshake, so a VMM written later opens its stream its own way behind the same operation.
- **The Driver opens the console and reads its log.** `Console` takes a Machine and returns a new bidirectional byte session to the guest's console: what the guest writes to it is read from the session and what is written to the session is the console's input. Each call is its own session, none affects another or the Machine, the caller closes it, and it reads to end of file when the VMM ends. `ConsoleLog` returns what the console has written since the start of the Machine's run, which the daemon parses for the Guest Agent's lines ([guest.md](./guest.md) §PID 1 duties) when it had no stream open on the entrypoint. For a VMM that has ended, the log is complete: that nothing is still on its way to it is the Driver's to establish. A Machine whose VMM is not running (for `Console`) or that has no log (for `ConsoleLog`) is "the console is not available". The inside learns no socket and no file path, so a VMM whose serial device is a socket, a pty or a file serves the same two operations. `Console` is the optional capability `console`, like snapshot, disk hot-plug and resize: a Driver without it makes the call unsupported whatever the Machine's state, before the Driver is called, and "the console is not available" is left for a Machine whose VMM has ended. The in-memory Driver, the Firecracker Driver and the Cloud Hypervisor Driver report it.
- **Disks are raw.** Every disk is a raw file, and a Driver whose VMM takes a disk format names raw, so nothing a guest writes selects a format ([ADR 0009](./adr/0009-a-machines-root-disk-is-a-sparse-raw-file-with-one-holder.md)).
- **The command line** carries mvmd's guest parameters; a Driver may add what its VMM's devices need and removes none.
- **The converter is booted through the Driver** the node's configuration names for conversion, with no optional capability ([ADR 0005](./adr/0005-untrusted-images-are-converted-in-a-converter-microvm.md)).
- **Other driven ports.** Disk, Network, Snapshot Store and Image Store are interfaces with one implementation each at first (#2 §5, first implementation scope); Registry and Converter channel join them for image pull ([ADR 0005](./adr/0005-untrusted-images-are-converted-in-a-converter-microvm.md)). They are ports in [structure.md](./structure.md) §Ports.

## VMM support for resizing

Per #2 §5, by VMM:

| VMM | vCPU hotplug | Memory |
|---|---|---|
| Cloud Hypervisor | supported | hotplug and virtio-mem supported |
| Firecracker | v1.17.0: not supported; the vCPU count is set before boot only | balloon, and a virtio-mem region configured before boot; the Driver uses neither |

Resize operations are optional capabilities because of this difference.

## Rationale

- Why Drivers are the one thing kept swappable, and why there is no container runtime option: #2 §5, isolation unit and runtime choice; [ADR 0001](./adr/0001-mvmd-is-a-containerd-like-microvm-runtime-that-does-not-know-gaon.md).
- Why two implementations: an abstraction with one implementation cannot be verified (#2 §5, first implementation scope).
- Why the Driver describes the VMM process instead of starting it: [ADR 0003](./adr/0003-a-per-machine-supervisor-enforces-the-fencing-expiry.md).
- Why the Driver states its VMM's needs and the supervisor, not the VMM's own launcher, confines it: [ADR 0015](./adr/0015-the-supervisor-confines-every-vmm-process-the-same-way.md).
- Why the Driver names the Machine's files by fixed paths in the VMM's root, and why the supervisor checks the pinned files instead of the Driver: [ADR 0019](./adr/0019-a-vmm-sees-its-machines-files-at-fixed-paths-in-its-root.md).

## Open questions

- Two questions `guest.md` hands to the Firecracker Driver's end-to-end test are still unanswered: whether `reboot(RB_POWER_OFF)` ends the VMM, and whether the run directory's log is complete when the agent powers off. `make test-firecracker` boots the agent with empty disks, so the agent never runs an entrypoint and neither is exercised. They wait for #30's remainder.
- Whether `Shutdown` is ever reached on a real node now that a graceful stop goes through the Guest Agent ([ADR 0018](./adr/0018-a-graceful-stop-goes-through-the-guest-agent-and-the-vmm-request-is-the-fallback.md)): the pinned kernel cannot receive its Ctrl-Alt-Del, so it helps only a guest that is Paused or whose agent is down with a kernel that can. If no node reaches it, the fallback can go.
- A snapshot of a Machine with a disk attached while it ran records that disk's path in the run directory (`/run/disk_<hash>`), which a restored VMM's root does not hold, and a disk given at boot has a drive named for its disk, which a restored Machine's new disk does not carry. The Snapshot call refuses a Machine that has attached disks today, and a snapshot record has no field to hold one (#113), so no restore meets either; whoever lets one through settles how a restored VMM gets those files and names.
