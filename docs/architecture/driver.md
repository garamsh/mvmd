# VMM Driver

The contract between the mvmd inside and a virtual machine monitor, and what implements it first.

Checked against garamsh/discussions#2 as read on 2026-11-08, §5 (discussioncomment-19288321) and the decision-change reply (discussioncomment-19466961). Claims about what a VMM supports in the resizing table are #2's, which marks the Firecracker entry as needing a version check; claims about boot formats, disks and network devices are ADR 0009's, ADR 0010's and ADR 0011's, and claims about what a VMM opens and filters are ADR 0015's, at Firecracker v1.17.0 and Cloud Hypervisor v54.0.

## Current decisions

- **The VMM is swappable behind a Driver port.** Firecracker and Cloud Hypervisor are the first two Drivers; a VMM written later in-house must be admissible through the same contract (decision-change reply). The contract is stated in VMM-neutral terms and no VMM's vocabulary appears in it ([structure.md](./structure.md) §Boundaries and dependency direction).
- **Operations.** The contract covers create (configure without booting), start, stop, destroy, pause, resume, snapshot, restore, disk attach and detach, memory target, inspect, list, and an event stream (#2 §5, Driver interface draft). The draft's signatures are not transcribed here; the code is the source of truth once it exists.
- **Capability negotiation (#2 §5 design principle 1).** A VMM reports which optional operations it supports, and the client matches a Machine's required capabilities to a node. The contract is not cut to what every VMM supports.
- **Snapshot compatibility (principle 2).** A snapshot records the Driver name and version, the CPU model and the guest kernel. A snapshot does not move to another VMM, and the contract says so. Restore compares the Driver name, version and CPU model with the Driver in service and refuses a snapshot that differs; the kernel is recorded and not compared. The Driver reports its CPU model and the kernel digest; snapshot and restore are the optional capability `snapshot`.
- **Idempotency and post-failure state (principle 3).** Create-type calls carry a request ID, and each operation defines the state a VM is left in when it fails.
- **Restart (principle 4).** The VMM runs as its own process; mvmd reattaches to running VMs after its own restart through `List`.
- **The Driver does not start the VMM process.** For start and restore it describes the process to run, and mvmd starts it under the Machine's supervisor, which enforces the fencing expiry ([runtime.md](./runtime.md) §Fencing). Every process a Machine needs runs under that supervisor, and none runs under a real-time scheduling policy. The Driver never sees the expiry, so a new VMM is fenced without fencing code of its own ([ADR 0003](./adr/0003-a-per-machine-supervisor-enforces-the-fencing-expiry.md)).
- **The VMM's needs for confinement.** The description of the VMM process also states, in VMM-neutral terms: the executable, the host files the VMM reads beyond the boot artefacts, the device nodes it opens, whether it takes its network device by descriptor, and its memory, task and CPU overhead. The supervisor confines the VMM from these alone ([runtime.md](./runtime.md) §VMM confinement), so a new VMM is confined by its Driver with no supervisor code. The description grants no capability, chooses no user and skips no step ([ADR 0015](./adr/0015-the-supervisor-confines-every-vmm-process-the-same-way.md)).
- **What the root looks like to the Driver.** Each path the description names is at its own host path in the VMM's root, so the Driver writes host paths into the VMM's arguments, among them the API and vsock sockets, which go in the Machine's run directory. The boot description carries that directory, and it is the one the supervisor is given: the Supervision adapter names it, the lifecycle passes it to the Driver and to the supervisor, and the Driver cannot change the supervisor's. A tap taken by descriptor is the VMM's descriptor 3; the Driver writes `3` where its VMM wants the descriptor. A VMM that takes no descriptor is passed none.
- **The VMM's own syscall filter stays on.** A Driver never starts its VMM with its seccomp filter disabled or relaxed; the filter is stacked over the supervisor's baseline.
- **By VMM, at the pinned versions (ADR 0015).** Firecracker opens `/dev/kvm` and `/dev/net/tun` and takes its tap by name, so it runs in the host's network namespace. Cloud Hypervisor opens `/dev/kvm` and takes its tap by descriptor, so it runs in a network namespace of its own. Both create their API and vsock sockets as paths in the run directory, and on aarch64 both read `/sys/devices/system/cpu/cpu0/cache`, Firecracker also `midr_el1`.
- **The Firecracker Driver (`daemon/internal/firecracker/`), at v1.17.0.** The node's configuration names the Firecracker binary, the kernel and the initrd by absolute path, and the binary and the kernel by SHA-256; the Driver checks both digests when mvmd starts and in every Describe, which is before every boot ([ADR 0010](./adr/0010-a-machine-boots-a-pinned-kernel-and-the-guest-agent-initrd-from-raw-block-devices.md)). Boot asks the VMM for its version and refuses any but 1.17.0, so the version in `Info`, which snapshots record, is the VMM's. What it states and does:
  - **The process.** `--api-sock` at `api.sock` in the run directory and `--enable-pci`, so the virtio devices are PCI devices, which is the transport v1.17.0's device hot-plug needs (`docs/device-hotplug.md`). No seccomp option is passed. The boot files are the kernel and the initrd read-only, then the Machine's devices as given. It opens `/dev/kvm`, and `/dev/net/tun` only for a Machine with a network device. Its overhead is 128 MiB of memory, one CPU and eight tasks beside the vCPUs (an idle VMM with two vCPUs had five); the memory and task figures are not measured under load. On aarch64 it names `/sys/devices/system/cpu/cpu0/cache` and `.../regs/identification/midr_el1` (untested there).
  - **The sockets.** A Unix socket path holds 107 bytes, so Describe refuses a run directory whose `api.sock` or `vsock.sock` would be longer.
  - **The Driver keeps nothing between Describe and Boot.** `Boot` is given the boot description the lifecycle passed to Describe, so no file in the run directory, which belongs to the VMM's user, is trusted for a host decision, and a repeated Boot or a restarted daemon needs no Describe. Describe stops hashing the pinned files when its context ends.
  - **The console.** Firecracker's own log goes to `firecracker.log` in the run directory (`--log-path`), so `vmm.log`, the supervisor's capture of the VMM's output, holds the guest's serial console. `ConsoleLog` reads it up to its size at the call, opening it without following a link and refusing anything but a regular file. That nothing is still on its way to it when the VMM has ended is not verified. `Console` returns `ErrConsoleUnavailable`: Firecracker's serial input is the VMM's standard input, which the supervisor does not connect to a session, so a session that writes to the guest cannot be opened yet.
  - **Boot.** After the API socket accepts a connection: machine configuration, boot source (the command line is mvmd's `console=ttyS0 reboot=k panic=1`, plus, on x86_64, the i8042 probe parameters the Firecracker documentation gives), each device as a drive named `disk<n>` in order (read-write ones with `cache_type` `Writeback`, so the guest's flushes reach the file), the network interface `eth0` with the tap's name and the guest MAC, the vsock device at CID 3 with `vsock.sock` in the run directory, and `InstanceStart`. Every call is on the context the lifecycle gives.
  - **`GuestConn`.** Firecracker answers `CONNECT <port>` with `OK <n>` where `n` is the host-side port it assigned the connection, not the guest's port (`docs/vsock.md`); the Driver accepts any decimal.
  - **Stop.** `Shutdown` sends `SendCtrlAltDel` and waits up to the grace for the API socket to go away; only a missing socket file or a refused connection counts as the VMM having ended, and any other dial error is returned. The action reaches a guest only through the guest kernel's i8042 and AT keyboard drivers (`CONFIG_SERIO_I8042`, `CONFIG_KEYBOARD_ATKBD`; `docs/api_requests/actions.md`), which the pinned Kata kernel does not build (`# CONFIG_SERIO is not set` in its configuration), so with it the wait runs its whole grace and the supervisor then ends the VMM. v1.17.0 sends it on x86_64 only.
  - **The pins.** The binary's tarball and binary digests, and the test kernel's (Kata Containers 4.3.1, as `guest.md` decides), are in `tooling/firecracker/fetch.sh`. They move by a pull request that edits them and reruns `make test-firecracker`. No bot proposes the move, since Dependabot does not read a shell script, so the PM owns it: the pins are reviewed against each project's releases and security advisories monthly, and at once when an advisory names the pinned version.
  - **Tests.** The Driver's requests are tested against a fake API socket in `make test`. `make test-firecracker` boots the pinned binary on the pinned kernel with the Guest Agent's initrd, through the Driver, as the user running it (no supervisor, no tap), and reaches the Guest Agent through `GuestConn`; it needs `/dev/kvm`, is not part of `make ci`, and is a job of its own in the pipeline.
  - **Not yet implemented, and not reported as capabilities:** snapshot and restore, disk hot-plug and resize. A restore as a new Machine cannot work as the ports stand: Firecracker's snapshot records each drive's `path_on_host` and `PUT /snapshot/load` fails when that path does not exist in the new VMM's root (`Error manipulating the backing file: No such file or directory`), while a restored Machine's root disk is a new file at another path and the supervisor mounts each boot file at its own host path. vCPU hot-plug does not exist in v1.17.0: the vCPU count is accepted before boot only (`firecracker.yaml`, `/machine-config`), and memory resizing is a virtio-mem region configured before boot (`docs/memory-hotplug.md`).
- **In-process first (principle 5).** Drivers are Go implementations inside the daemon, with messages shaped so that they can move to gRPC. An out-of-process Driver protocol, in the role containerd's shim API plays, is introduced when the first out-of-process VMM, such as an in-house one, arrives (decision-change reply). It keeps the VMM process started by the supervisor.
- **Boot artefacts ([ADR 0010](./adr/0010-a-machine-boots-a-pinned-kernel-and-the-guest-agent-initrd-from-raw-block-devices.md)).** A Driver boots a VM from: a kernel file (on x86_64 an uncompressed ELF kernel with a PVH entry, on aarch64 a PE `Image`, both taken by Firecracker and Cloud Hypervisor), an initrd file, a kernel command line, an ordered list of block devices each a file path and a read-only flag, one network device for a Machine and none for a converter, one vsock device, and the vCPU count and memory size. A Machine's devices are its image's EROFS read-only, its root disk read-write, then its attached disks; a converter's are its output disk alone. The Driver learns nothing of what each device holds.
- **A network device** is a tap's name and the guest MAC; the Driver learns no address or policy. On restore, the Driver attaches the snapshot's network device to the tap mvmd gives for the new Machine, not the one the snapshot recorded: Firecracker through `network_overrides`, Cloud Hypervisor through the restore's net file descriptors, which needs its devices attached by descriptor ([ADR 0011](./adr/0011-each-machine-gets-a-routed-tap-and-addresses-mvmd-assigns.md)).
- **The Driver opens the stream to the guest.** `GuestConn` takes a Machine and a guest port and returns a new byte stream to that port, ready for the Guest Agent's gRPC protocol; the Guest Agent channel adapter calls it with port 1024 (`guest.md`) for each call and again after a reset, and closes what it gets. Whatever the VMM needs before the first byte reaches the guest is the Driver's and is finished before the call returns: for Firecracker, connecting to the vsock socket in the run directory, writing `CONNECT <port>` and reading its `OK` line. A Machine whose VMM is not running, or a guest that refuses the port, is "the Guest Agent is not reachable", which is the Guest port's error for it. The adapter knows no socket path and no handshake, so a VMM written later opens its stream its own way behind the same operation.
- **The Driver opens the console and reads its log.** `Console` takes a Machine and returns a new bidirectional byte session to the guest's console: what the guest writes to it is read from the session and what is written to the session is the console's input. Each call is its own session, none affects another or the Machine, the caller closes it, and it reads to end of file when the VMM ends. `ConsoleLog` returns what the console has written since the start of the Machine's run, which the daemon parses for the Guest Agent's lines ([guest.md](./guest.md) §PID 1 duties) when it had no stream open on the entrypoint. For a VMM that has ended, the log is complete: that nothing is still on its way to it is the Driver's to establish. A Machine whose VMM is not running (for `Console`) or that has no log (for `ConsoleLog`) is "the console is not available". The inside learns no socket and no file path, so a VMM whose serial device is a socket, a pty or a file serves the same two operations.
- **Disks are raw.** Every disk is a raw file, and a Driver whose VMM takes a disk format names raw, so nothing a guest writes selects a format ([ADR 0009](./adr/0009-a-machines-root-disk-is-a-sparse-raw-file-with-one-holder.md)).
- **The command line** carries mvmd's guest parameters; a Driver may add what its VMM's devices need and removes none.
- **The converter is booted through the Driver** the node's configuration names for conversion, with no optional capability ([ADR 0005](./adr/0005-untrusted-images-are-converted-in-a-converter-microvm.md)).
- **Other driven ports.** Disk, Network, Snapshot Store and Image Store are interfaces with one implementation each at first (#2 §5, first implementation scope); Registry and Converter channel join them for image pull ([ADR 0005](./adr/0005-untrusted-images-are-converted-in-a-converter-microvm.md)). They are ports in [structure.md](./structure.md) §Ports.

## VMM support for resizing

Per #2 §5, by VMM:

| VMM | vCPU hotplug | Memory |
|---|---|---|
| Cloud Hypervisor | supported | hotplug and virtio-mem supported |
| Firecracker | v1.17.0: not supported; the vCPU count is set before boot only | balloon, and a virtio-mem region configured before boot; the Driver uses neither |

Resize operations are optional capabilities because of this difference.

## Rationale

- Why Drivers are the one thing kept swappable, and why there is no container runtime option: #2 §5, isolation unit and runtime choice; [ADR 0001](./adr/0001-mvmd-is-a-containerd-like-microvm-runtime-that-does-not-know-gaon.md).
- Why two implementations: an abstraction with one implementation cannot be verified (#2 §5, first implementation scope).
- Why the Driver describes the VMM process instead of starting it: [ADR 0003](./adr/0003-a-per-machine-supervisor-enforces-the-fencing-expiry.md).
- Why the Driver states its VMM's needs and the supervisor, not the VMM's own launcher, confines it: [ADR 0015](./adr/0015-the-supervisor-confines-every-vmm-process-the-same-way.md).

## Open questions

- How a restored Machine's disks reach the paths a Firecracker snapshot recorded, which a boot file mounted at its own host path cannot do (the Firecracker Driver bullet above). A boot file named by a source and a path in the VMM's root, or a path every Machine's root disk has in its VMM's root, would; either changes the Driver port's `ProcessDescription` and the supervisor's.
- Two questions `guest.md` hands to the Firecracker Driver's end-to-end test are still unanswered: whether `reboot(RB_POWER_OFF)` ends the VMM, and whether the run directory's log is complete when the agent powers off. `make test-firecracker` boots the agent with empty disks, so the agent never runs an entrypoint and neither is exercised. They wait for #30's remainder.
- Whether the guest kernel's conditions (ADR 0010) gain `CONFIG_SERIO_I8042` and `CONFIG_KEYBOARD_ATKBD`, which a graceful Firecracker stop needs, or the Guest Agent gains a shutdown the Driver can ask for.
- The Driver contract's wire shape for the out-of-process case; introduced when the first out-of-process VMM arrives.
- The boot formats of a VMM admitted later; each new Driver is checked against the artefacts above.
