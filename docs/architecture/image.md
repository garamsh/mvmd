# Image

How mvmd turns an OCI image into something a microVM boots, and where it keeps the result.

Checked against garamsh/discussions#2 as read on 2026-11-08, §5 image section (discussioncomment-19288321), and the decision-change reply (discussioncomment-19466961). The staged plan below is #2's proposal, adopted here as scope and not as a schedule. Claims about a tool or a specification are the ADRs', at the versions each names.

## Current decisions

- **mvmd pulls from registries itself and converts to MachineImage, without a container engine.** The OCI image format is the input and distribution format only ([ADR 0001](./adr/0001-mvmd-is-a-containerd-like-microvm-runtime-that-does-not-know-gaon.md)).
- **The node understands one format, MachineImage.** It is distributed as an OCI artifact, so existing registries and signing tools apply. It carries run configuration (entrypoint, environment, user, working directory, architecture, required kernel conditions), the root filesystem as EROFS chunks with a chunk index, an integrity root hash, an optional boot prefetch profile, and an optional kernel; with none, the platform default kernel is used (#2 §5, MachineImage proposal).
- **Images arrive by conversion or, later, by a builder of mvmd's own.** Either way the node sees a MachineImage.
- **A running VM's snapshot is a node-local cache, not a distribution source.** Template snapshots are derived per (image, kernel, VMM version, CPU family) combination and are never distributed, because they are less portable, large, and constrained by security (#2 §5).
- **Efficiency comes from the format**: chunk sharing, lazy loading, prefetch, DAX-friendly layout and template snapshots. A bespoke format does not change execution speed by itself (#2 §5).
- **Security rules.** Untrusted images are converted inside isolation, microVM where possible. A converted image is never mounted on the host. Integrity is verified with the root hash (#2 §5, security).
- **Stages (#2 §5, stage plan).** v1: one image to a single EROFS. v2: template snapshots derived on the node as a cache. v3: chunk deduplication, prefetch, lazy loading. v4: a builder of mvmd's own, and images with a kernel.
- **Built by mvmd versus reused.** Reused: the registry protocol, and `mkfs.erofs` from erofs-utils as the tar to EROFS conversion tool ([ADR 0006](./adr/0006-mkfs-erofs-converts-an-image-one-layer-at-a-time.md)). Built: the registry client, the converter program and its initrd (with `mkfs.erofs` built from pinned sources into it), the node image cache and its garbage collection, the guest init and agent ([guest.md](./guest.md)). Guest kernel build and management is its own project ([ADR 0001](./adr/0001-mvmd-is-a-containerd-like-microvm-runtime-that-does-not-know-gaon.md)).

### Conversion

- **Where it runs.** One converter microVM per pull, booted from the platform guest kernel and mvmd's converter initrd, with no root filesystem and no network device, through the Driver the node's configuration names for conversion ([ADR 0005](./adr/0005-untrusted-images-are-converted-in-a-converter-microvm.md)).
- **What the host does.** It fetches every blob by digest and checks its size and SHA-256, and parses only the JSON of manifests, indexes and configs. It never decompresses or applies a layer.
- **Who holds the output.** The output file is the daemon's, mode 0600. Before the converter's VMM starts the pull gives it to the converter's user, mode unchanged, so that user alone can open it; once the supervisor has ended the VMM, before the converter's report is read or the output sealed, the pull takes it back and sets the mode again. This runs on success and on every failure, a VMM that never boots included. A VMM that cannot be ended, or an output that cannot be taken back, fails the pull and keeps the user held until mvmd restarts, since a reused user, or a VMM still running, could change what the daemon is checking. A Seal of an output the daemon does not own fails ([ADR 0024](./adr/0024-the-converters-user-holds-the-output-file-only-while-its-vmm-runs.md)).
- **What the converter does.** It receives the verified layers in manifest order over vsock, writes one EROFS to its output disk, and reports the image's length. Its VMM runs under an `mvmd-supervisor` whose expiry is the node's conversion time limit; vCPUs, memory, output size and time are node configuration.
- **The channel.** A gRPC service the converter owns, `mvmd.convert.v1alpha1.ConvertService` on vsock port 1025, in `imageconv/proto/mvmd/convert/v1alpha1/`. One call serves one conversion: the client streams the filesystem UUID, the media type of every layer and a bound on the names held for one layer, then each layer twice, a names pass and a content pass. The converter answers once with the EROFS length or with a failure naming its step, and powers the VM off ([ADR 0017](./adr/0017-the-converter-serves-a-grpc-contract-it-owns-and-carries-mkfs-erofs-in-its-initrd.md)).
- **Waiting for the converter.** The converter VM has started, not listened, when the call begins, so the client holds the call until the converter's port answers, redialling with a backoff that reaches at most one second, and gives up when the conversion limit ends. A converter that never answers fails the pull with an error that names the limit and is an unreachable guest. Only the wait for a first stream is repeated: a conversion whose connection breaks after it began is not, since the converter serves one conversion. When the converter's VMM has ended, `GuestConn` reports `ErrVMMEnded`, and the client stops waiting at once.
- **How layers are applied.** One `mkfs.erofs` run per layer, the first a full build and each later one incremental, with OCI whiteouts and opaque whiteouts applied against the layers below and removed from the result. `tar+gzip` is filtered by `mkfs.erofs` when the layer needs no rewrite and decompressed by the converter when it does; `tar+zstd` is decompressed by the converter; other layer types fail the pull before any layer is read ([ADR 0006](./adr/0006-mkfs-erofs-converts-an-image-one-layer-at-a-time.md), ADR 0017). The build time is fixed, so the same layers and UUID give the same EROFS.
- **A same-layer whiteout** of a name the layer also holds is rewritten by the converter before `mkfs.erofs` sees it: into an opaque marker when the layer makes the name a directory, dropped otherwise. The result matches the OCI layer specification in either order. The converter reads each layer twice, once for its names and once to convert it, with no copy kept (ADR 0006).
- **Failures.** A conversion that fails answers with the step that failed (start, layer type, stream order, names, name limit, convert, output) and a message; a status means the call broke. A failure of the converter outside a conversion is one console line and a power-off. Nothing the output holds after a failure is used (ADR 0017).
- **Scratch space.** `mkfs.erofs` spools a layer's file data in `/tmp`, a tmpfs in the converter VM, so the memory configured for a conversion has to exceed twice the file data of the image's largest layer (ADR 0017).
- **The converter's initrd** holds the converter as `/init` and a statically linked `mkfs.erofs` built from pinned sources by `imageconv/mkfs-erofs/build.sh`. Both the tool and the archive are built twice and must be identical (ADR 0017).
- **The output is untrusted.** Only the guests of that image's Machines interpret it; the host reads it as bytes.

### Node image cache

- **Layout.** One OCI image layout, `images/` under mvmd's state directory ([ADR 0007](./adr/0007-the-node-image-cache-is-an-oci-image-layout-published-by-one-index-swap.md)). Blobs are content-addressed by SHA-256, and identical blobs are stored once.
- **A MachineImage** is an artifact manifest with mvmd's MachineImage type, a config blob (run configuration, the converter it came from, required kernel conditions, none at stage v1) and one EROFS blob whose descriptor carries the fs-verity digest. At stage v1 the format is node-local, and the code defines its names: the manifest's `artifactType` is `application/vnd.mvmd.machineimage.v1`, the config's media type `application/vnd.mvmd.machineimage.config.v1+json`, the EROFS's `application/vnd.mvmd.machineimage.erofs.v1`, and the descriptor's fs-verity digest is its annotation `io.mvmd.fsverity.digest`.
- **What the Image Store tells the application of an image it holds**: the path of its EROFS file, that filesystem's UUID (chosen by mvmd at conversion, [ADR 0010](./adr/0010-a-machine-boots-a-pinned-kernel-and-the-guest-agent-initrd-from-raw-block-devices.md)) and its run configuration, with the entrypoint and command already one argument vector, plus environment and working directory. A start sends the last two to the guest in the boot description ([guest.md](./guest.md)). The UUID is recorded in the config blob.
- **Visibility.** An image exists exactly when `index.json` lists it, under the digest it was pulled by. A pull stages under `images/staging/` and publishes by moving its blobs into place and then replacing `index.json` in one rename. Pulls of one digest are one pull.
- **The index.** Each entry of `index.json` is the manifest's descriptor with the annotation `io.mvmd.image.digest` naming the digest the image was pulled by, which is how `Locate` finds it. `Locate` reads the manifest and config through their content addresses, so a blob that does not match its name is refused.
- **Who may read the image.** A published image's EROFS blob is owned by the daemon, mode 0444: a Machine's VMM runs as a user of its own, and the image has to be readable by it ([ADR 0015](./adr/0015-the-supervisor-confines-every-vmm-process-the-same-way.md) §Its own user). Mode, not a per-Machine grant, because a published blob is content-addressed and never written again, a VMM's user reaches only what is bind-mounted into its root ([ADR 0019](./adr/0019-a-vmm-sees-its-machines-files-at-fixed-paths-in-its-root.md)), and the store's directories are 0700, so no other host user reaches it; a grant would be added and revoked on a file many Machines share. Publish sets the mode on the staged output before it moves the blob, so a blob of the layout is never an image with another mode. The output stays 0600 while staged, lent and reclaimed, since only the converter's user may open it while it is written ([ADR 0024](./adr/0024-the-converters-user-holds-the-output-file-only-while-its-vmm-runs.md)). The config and manifest stay 0600: no VMM opens them. Opening the cache sets the mode of every listed image, so a cache published before this rule starts Machines too.
- **Start-up sweep.** Before serving any call, mvmd removes staging directories, the temporary file of an interrupted index swap, and blobs no listed manifest reaches. It removes nothing and fails when a listed manifest cannot be read, because what that image reaches is then unknown.
- **The source image is not kept** after conversion.

### Pull image

The steps and the state each failure leaves are in [ADR 0007](./adr/0007-the-node-image-cache-is-an-oci-image-layout-published-by-one-index-swap.md) §Pull image. In order: check the reference names a digest; return if the image is listed; fetch and check the manifest, selecting the node's platform from an index; fetch and check the config; fetch and check each layer; lend the output to the converter's user, convert, end the VMM and take the output back (ADR 0024); truncate, hash and enable fs-verity; write the config and manifest; publish; remove staging. Nothing before the publish changes `index.json`, so every failure leaves nothing visible in the cache (`runtime-api.md` §Images).

The use case is `daemon/internal/image/` ([structure.md](./structure.md) §Ports); what it adds to the ADR's table:

- **One pull per digest.** A call naming a digest already being pulled waits for that pull's outcome, whatever repository it names. The pull runs on a context of its own, bounded by a pull timeout (default 30 minutes), so a caller that leaves does not stop it. Publishes are applied one at a time, in the use case.
- **After a failure**, the staging area is removed on a context detached from the pull's, so a pull the bound ended is cleaned up. A staging area that cannot be removed is reported with the failure. After the publish a failed removal is not a failure of the pull; the sweep removes what is left.
- **The sweep is its own operation**, `Sweep`, which the composition site calls once before any other call. A pull never runs it.
- **A conversion that outlives mvmd is ended at start.** Before the sweep and before anything is served, the composition site lists the conversion supervision's live conversions and terminates each, so the user of a VMM that survived is free and the new allocator needs to learn nothing about it; the sweep then removes the staging area of a VMM that has ended. A conversion that cannot be ended stops the start. Not taken: reading the user from the run directory's owner and holding it in the allocator, which adds a call to the allocator for a VMM that is better ended, and waiting for the supervisor's expiry, which delays the start by up to the conversion limit.
- **The converter's VM is booted and ended through the Driver and Supervision ports as they are**, with no addition to either. It is a Machine of the Driver and the supervision the node configures for conversion, so the Driver is the one given the converter's initrd and the supervision's expiry is the conversion limit. It has an identifier of its own, `convert-` and the image's digest, one read-write output disk and no network device; its user is allocated from the node's UID range, through the one `machine.UIDs` the lifecycle allocates its Machines' users from, so a conversion and a Machine never share one, and released only once its VMM is known to have ended and the output is back with the daemon (§Conversion, Who holds the output), so a VMM that cannot be ended fails the pull and keeps the user held until mvmd restarts. The conversion also runs within the node's conversion limit as a bound of the call, and the VMM is ended whatever the conversion did.
- **The converter's report is untrusted.** A length of zero or beyond the output file fails the pull before the output is truncated.
- **The filesystem UUID** of the EROFS is taken from the image's digest, so one image always carries the same one.
- **A Publish that returns an error** is asked where the image stands. The swap of `index.json` can have happened before a later step, the sync that makes it durable, failed, so the error does not say whether the image is listed. After a Publish error the use case calls Locate: an image that is listed is a successful pull, because the swap is the only thing that makes an image visible and a visible image is what the caller asked for; an image that is absent is the failure it was; a Locate that itself fails reports both errors. Not taken: a Publish that answers success after the swap whatever followed, which hides the error in an adapter that has no way to report it (`stack-go.md` §4). What this leaves: the sync error is reported nowhere, and a crash before the directory reaches disk can bring back the old index, which leaves the image absent, so the next pull fetches it again.
- **Node configuration it takes**: the platform manifests are selected for (the node's own, `linux` and its architecture), the converter's name, its vCPUs and memory, the output file's size, the bound on names held per layer, the conversion limit, the converter's kernel and initrd, the pull timeout and the file of registry credentials. The Image Store is the `images` directory of the state directory. The converter's users come from the node's one UID range, not a range of their own. The conversion supervision keeps its run directories in the `conversions` directory of the state directory and its VMMs in a cgroup of their own beside the Machines', so the lifecycle's reconciliation never sees a conversion. Credentials are read once at start from a file closed to group and others, and never logged.

### Integrity

- **The root hash** of a MachineImage is the fs-verity digest of its EROFS file, SHA-256 over 4096-byte blocks ([ADR 0008](./adr/0008-fs-verity-on-the-host-guards-every-read-of-a-machineimage.md)). The manifest and config are covered by their content addresses.
- **Set** when a pull enables fs-verity on the output, after the converter's VMM has ended and before publish.
- **Checked** before every start and restore that boots the image: the Image Store measures the file, in constant time, and a file that is not a verity file or carries another digest fails the call before the boot begins.
- **Verified on every read** by the host kernel, whatever I/O the VMM uses; a corrupted block reaches the guest as a read error. The guest does nothing for integrity.
- **Host filesystem.** mvmd's state directory is on ext4 or f2fs with the `verity` feature, or on btrfs; mvmd refuses to start where fs-verity cannot be enabled in its image cache. The Image Store checks this when it opens the cache, by enabling fs-verity on a file it then removes.
- **The adapter's tests** need such a file system and fail where they find none. They look for one in the directory named by `MVMD_VERITY_DIR`, then in the temporary directory, and then make an ext4 with the `verity` feature in a file and loop-mount it through passwordless sudo, as the GitHub-hosted runner allows.

## Rationale

- Why not run the image as a container: no container runtime anywhere in mvmd ([ADR 0001](./adr/0001-mvmd-is-a-containerd-like-microvm-runtime-that-does-not-know-gaon.md)).
- Why a snapshot is cache and not source: #2 §5, image section.
- Why a microVM and not a host sandbox, and why the host parses only JSON: [ADR 0005](./adr/0005-untrusted-images-are-converted-in-a-converter-microvm.md).
- Why one `mkfs.erofs` run per layer, and how the tool was checked for whiteouts: [ADR 0006](./adr/0006-mkfs-erofs-converts-an-image-one-layer-at-a-time.md).
- Why the output is lent to the converter's user and taken back, and what was weighed: [ADR 0024](./adr/0024-the-converters-user-holds-the-output-file-only-while-its-vmm-runs.md).
- Why a gRPC contract the converter owns, how `mkfs.erofs` is built into the initrd, and how a failure is reported: [ADR 0017](./adr/0017-the-converter-serves-a-grpc-contract-it-owns-and-carries-mkfs-erofs-in-its-initrd.md).
- Why an OCI image layout and one index swap: [ADR 0007](./adr/0007-the-node-image-cache-is-an-oci-image-layout-published-by-one-index-swap.md).
- Why fs-verity on the host and not dm-verity in the guest: [ADR 0008](./adr/0008-fs-verity-on-the-host-guards-every-read-of-a-machineimage.md).
- The Image Store, the Registry and the Converter channel are driven ports ([structure.md](./structure.md) §Ports); the application sequences a pull across them.

## Open questions

- **Removal of images**: garbage collection of listed images and how a client removes one (`runtime-api.md` §Open questions).
- **Reconversion** when the converter changes: each image records its converter, and nothing yet decides when an image converted by an older one is replaced.
- **Distribution of MachineImages** between nodes and registries, and the published media types it needs.
- Whether and how the required kernel conditions of an image are negotiated with the guest kernel project once it exists ([guest.md](./guest.md) §Open questions).
