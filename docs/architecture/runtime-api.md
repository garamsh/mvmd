# Runtime API

The operations mvmd offers its client, the rules every call follows, and the version this contract carries.

Checked against garamsh/discussions#2 as read on 2026-11-08 (decision-change reply discussioncomment-19466961, §3 discussioncomment-19288319, §4 discussioncomment-19288320, §5 discussioncomment-19288321) and against garamsh/mvmd#4. Where neither settles a point, it is under Open questions and binds nothing.

## Scope and version

- **The API models Machines.** It does not model Pods or containers and is not CRI (#2 §1 conclusion; [runtime.md](./runtime.md) §Runtime API scope). A Machine is one microVM on this node.
- **It names nothing of its client.** No type, resource or identifier of the client appears in it. The client is whatever calls it; mvmd does not know what that is.
- **The version is `v1alpha2`.**
- **Encoding and transport.** A gRPC service defined in Protocol Buffers, served on a Unix domain socket on the node; the socket's filesystem permissions are the authentication. The protobuf package and the Go package path carry the version, and the generated code is committed ([ADR 0004](./adr/0004-the-runtime-api-is-grpc-on-a-unix-socket-with-committed-generated-code.md)).
- **Rule for changing the version.** A change that adds an operation, an optional field or a capability keeps the version. A change that removes or renames anything, changes what an operation means, or changes its idempotency rule or its state after failure is a new version identifier (`v1alpha2`, then `v1beta1`, and so on). The reason is that the client builds against the version number: it must be able to tell that nothing it relies on moved. The rule has no exception for the alpha stage, so the client can build against a version as soon as this document naming it is merged. `v1alpha2` is the version that made List and Search streams ([ADR 0035](./adr/0035-the-runtime-api-streams-listings-and-searches-and-serves-one-alpha-version-at-a-time.md)).
- **Versions in service.** mvmd reports the versions it serves in the runtime info call below, and a call naming a version it does not serve is refused as unsupported: over gRPC, a call to the service of another version is answered as unimplemented, which is the status for a service the server does not host. **Alpha versions are served one at a time**: mvmd serves the current alpha version and not the one before it, so a caller of the previous alpha version is refused and moves to the current one. How many versions are served at once from `v1beta1` on is an open question ([ADR 0035](./adr/0035-the-runtime-api-streams-listings-and-searches-and-serves-one-alpha-version-at-a-time.md)).

## Calling rules

- **Identity.** The client chooses the identifier of every Machine, snapshot, disk and exec record it creates, unique on this node. The reason: if the connection drops between sending a creating call and reading its answer, the client already knows what to look up, and no object exists that the client cannot name.
- **The form of a Machine identifier.** It is the form of a name the node can use as a file or directory name, since the node derives its state directory, its VMM cgroup, the run directory's sockets and its root disk `<id>-root` from it. Create Machine and Restore reject as invalid, before any UID, address or disk is taken, an identifier that is empty, `.` or `..`, contains a `/` or a NUL, would make a root disk name that is not a disk identifier (below, so `tmp` and a name starting with `tmp-` are refused), or is longer than 250 bytes, so that `<id>-root` fits the 255 bytes of one path component. Nothing narrower is required: the form is not a DNS label. The check is the domain's, and the client's own check ahead of a call is non-empty only, so the refusal reaches the client as the outcome, rejected as invalid.
- **Snapshot and exec identifiers have no form beyond non-empty.** A snapshot's directory is named by the SHA-256 of its identifier (`snapshotPath` in `daemon/internal/snapshotstore/snapshotstore.go`) and an exec record is a key of the node's database, so neither identifier names a file.
- **Request ID.** Creating calls (create Machine, restore, snapshot, create disk, exec) also carry a client-chosen request ID (#2 §5 design principle 3; #2 §3 principle 5). The same identifier with the same request ID and the same parameters returns the original outcome. The same identifier with a different request ID or different parameters is a conflict and changes nothing. mvmd remembers a request ID for as long as the object it created exists.
- **State-targeting calls need no request ID.** Start, stop, pause, resume, delete, delete disk, attach, detach and resize name a target state. Repeating one when the Machine is already in that state succeeds and changes nothing, so a retry is always safe.
- **Outcome kinds.** A call ends in one of: success; rejected as invalid; not found; conflict (identifier in use with other parameters); precondition failed (the Machine is not in a state that allows the call, or a rule such as fail-closed start or one writer per disk forbids it); unsupported (the Driver lacks the capability, [driver.md](./driver.md)); or failed (the attempt ran and did not finish). Rejected, not found, conflict, precondition failed and unsupported change nothing. Each failed outcome leaves the state the tables below name.
- **An unknown outcome is not an API result.** If the client loses the connection or times out, it does not know the outcome. An accepted call is not cancelled by a disconnect: it completes or fails into its defined state. The client resolves the doubt by repeating the call (same identifier, same request ID), which waits for the first call's outcome and returns it (see "A repeat while the first call runs waits" below), or by reading the Machine back.
- **An accepted call runs to its end, within a bound.** A state-changing call (create, start, stop, pause, resume, delete, attach, detach, resize, snapshot, restore) is accepted when it holds its Machine; from then on the client's disconnect or deadline does not reach its steps. A call still waiting for its turn on the Machine is not yet accepted in this sense: it runs when its turn comes, whether or not its client is still there, and then it is bound like any other. A bound that mvmd applies ends a step that hangs, so a call cannot hold its Machine for ever: the node's `call_timeout` (default 10 minutes, at most 6 hours) from the moment the call holds the Machine, plus a start's `boot_timeout` or a stop's grace period. The bound relies on each port honouring the context it is given, except for the waits for a VM to run and for the guest (a start's `Boot`, a restore's `CatchUp`), which `boot_timeout` bounds on the lifecycle's own timer ([ADR 0037](./adr/0037-a-restores-guest-catch-up-is-bounded-by-the-boot-timeout-as-a-starts-boot-is.md)). The steps that undo what a failed call did run on a context of their own with a short bound of their own, so a call the bound ends still reaches the failure state its table row names.
- **A repeat while the first call runs waits.** Calls on one Machine run one at a time, and create disk calls on one disk do, so a repeat with the same identifier and request ID returns once the first call has an outcome, and returns that outcome; it never starts the work a second time. A client that cannot wait reads the Machine back instead.
- **A guest file path is absolute.** Read file, write file, patch file, list and search take an absolute path in the Machine's filesystem. One that is empty or not absolute is rejected as invalid before the guest is called, and changes nothing.
- **Reads are never state.** Inspect, list and events change nothing and can be repeated freely.

## Machine states

| State | Meaning |
|---|---|
| Created | Configured on the node, never booted or last stopped before boot. No VMM process. |
| Running | Booted or restored; the guest executes. A Running Machine whose VMM ends with no call asking it to becomes Stopped ([ADR 0033](./adr/0033-a-vmm-that-ends-on-its-own-moves-its-machine-to-stopped-with-the-reason.md)). |
| Paused | The guest is stopped with memory held. |
| Stopped | Not executing; disks retained. Reached by Stop, by a start that failed, and by the VMM's own end: the entrypoint's end, an agent failure or a guest panic, found while mvmd runs or at its start. |
| Faulted | mvmd cannot establish the Machine's state, for example a stop that could not be confirmed. The only calls that apply are stop, delete, inspect and reads. |

Inspect reports the state, the reason for the last failure if any, the Driver and its version, the Machine's disks, resources and resource ceiling as mvmd holds them, and its network addresses, one per family its node serves, and the network policy in effect, and the digest of the image it runs, in every state (`image_digest`: the image Create or Restore recorded, which Remove image refuses to remove while the Machine exists), and the name of the kernel it was created with ([ADR 0045](./adr/0045-a-node-offers-named-kernels-a-machine-records-the-name-it-is-created-with-and-a-restore-matches-the-recorded-digest.md)), and the SHA-256 digest, in hex, of the kernel its running guest was booted with: the kernel pinned at its last start, or for a Machine restored from a snapshot the one that snapshot recorded. A Machine that has never booted reports none, and so does one whose record was written before the digest was kept, until its next boot. The name is recorded at Create, from the request or else the node's default; a name the node does not offer is refused as invalid. A Start boots the file the name maps to at that moment and, for a name the node no longer offers, fails as a failed precondition naming the kernel, keeping the record. Restore is judged by the recorded digest and not the name ([driver.md](./driver.md)).

## Operations

"Repeat" is the result of the same call made again.

### Machine lifecycle

| Operation | Needs | On success | Repeat | State after failure |
|---|---|---|---|---|
| Create Machine | Image already on the node, resources, optional resource ceiling, neither above the Driver's limits (invalid), root disk size, optional kernel name (the node default if empty; a name the node does not offer is invalid), disks (a Driver without the hotplug capability refuses any: unsupported), network policy, optional command, args, env, user and files (below) | Created | Same request ID: original outcome | No Machine exists |
| Start | Created or Stopped; network policy applied; fencing deadline armed | Running, once the VMM runs, each attached disk has been plugged and found by the guest, and the guest has been sent its boot description and its entrypoint runs | Already Running: success. A repeat while a start is in progress waits and returns that start's outcome | Prior state; a boot that began and failed, whether the VMM's or the guest's, ends in Stopped with the failure reason, which names the guest's boot step when one failed. A guest that has not finished booting within the node's `boot_timeout` (default 2 minutes, at most 1 hour) is such a failure: the VMM is ended and the reason is "the guest did not finish booting within <timeout>". So is a VM that has not reached Running within `boot_timeout` ("the VMM did not reach Running within <timeout>"), and one whose VMM ended first ("the VMM ended before its VM reached Running"), which is found within a second. So is a guest whose agent does not serve the Guest Agent API version the daemon speaks (`v1alpha1`): nothing is sent to it, and the reason names that version and the ones the agent serves |
| Stop | Any state | Stopped, once the guest has been asked to stop through its agent and the VMM has ended, by the guest within the grace period or by force at its end | Already Stopped, or Created: success, no change | Running or Paused if the stop never began; Faulted if it began and cannot be confirmed, or if the VMM ended but the Machine's network could not be removed, and a later Stop retries |
| Pause | Running | Paused | Already Paused: success | Running |
| Resume | Paused | Running | Already Running: success | Paused |
| Snapshot | Running or Paused; Driver supports snapshot; the Machine has a recorded kernel digest (a failed precondition otherwise, which a restart cures) | Machine in the state it was in; snapshot exists | Same request ID: the existing snapshot | The Machine in the state it was in, and no snapshot exists; Faulted if the Machine cannot be returned to it |
| Restore | A snapshot compatible with this node's Driver, version and CPU, whose resources and ceiling are within the Driver's limits (precondition failed otherwise), and whose recorded disks the node holds with no holder and unchanged since the snapshot (precondition failed otherwise, the reason naming the disk and which of the three); fencing deadline armed; network policy applied | New Machine, Running | Same request ID: original outcome | No Machine exists; Faulted if its VMM cannot be ended. A VM that has not reached Running within the node's `boot_timeout`, or whose VMM ended first, is a failure of this kind, and so is a guest that has not finished catching up within `boot_timeout` ("the guest did not finish catching up within <timeout>"): the VMM is ended |
| Delete Machine | Created, Stopped or Faulted | No Machine exists, its network released, its attached disks given back, its root disk removed, and its state directory removed (the run directory with the disk links in it, the supervisor log and the sockets), in that order and before its record | Absent: success; otherwise every step again, each already done succeeding | Prior state, with the record kept and the identifier not free; a step that fails fails the call as failed, and a state directory that cannot be removed is named in the reason |
| The VMM ends on its own | Running or Paused; no call holds the Machine; the Machine's supervisor is gone | Stopped, with the reason, the network released as Stop releases it and the disks retained | Not a call; a Stopped Machine is not moved again | Faulted, when the Machine's network could not be removed |

- **A VMM that ends with no call asking it to is reported, and mvmd decides nothing more** ([ADR 0033](./adr/0033-a-vmm-that-ends-on-its-own-moves-its-machine-to-stopped-with-the-reason.md)). The supervisor exits with its VMM, so a Running or Paused Machine whose supervisor is gone has lost its VMM; mvmd looks for that without asking the guest, every second while it runs and once at its start, and moves the Machine to Stopped, the state a Stop reaches, with an event. The reason begins "the VMM ended with no call asking it to" (at start, "the VMM ended while mvmd was not running") and names the cause from the Guest Agent's last console line: the entrypoint's exit code or signal, an entrypoint that did not start, or the agent's own failure or panic. A VMM that ended with no such line is reported as that, as when it was killed or crashed. The entrypoint's record is read afterwards as for any Stopped Machine. A VMM end mvmd cannot establish is Faulted. An end the fencing expiry caused is not reported as the VMM's own: while the deadline is not armed the look leaves the Machine, and the expiry's force stop settles it. A call that holds the Machine owns it: the look leaves the Machine to the call, so a Stop the VMM's own end overtakes is a Stop's Stopped, with no reason, and one event. Whether a Machine that ended is started again is not mvmd's decision: whoever drives mvmd decides.
- **Stop forces the guest down after a grace period the client names.** A guest cannot be trusted to stop (workloads are untrusted, #2 §5 security), so a stop always ends with the VMM terminated.
- **A graceful stop asks the guest through its agent.** The request is the Guest Agent's `Terminate` call, which applies the Termination rule ([guest.md](./guest.md) §PID 1 duties) whatever the VMM and the guest kernel ([ADR 0018](./adr/0018-a-graceful-stop-goes-through-the-guest-agent-and-the-vmm-request-is-the-fallback.md)). The call returns when the agent has taken the request, and mvmd then waits, until the grace period ends, for the Machine's supervisor to be gone, which is the VMM having ended. The call to the agent is bounded by the grace period, with no minimum, so a stop never outlasts its grace. The Driver's own request ([driver.md](./driver.md)) is sent, with what is left of the grace period, when the call does not succeed whatever the reason (the agent cannot be reached, refuses, fails or does not answer in time); a refusal is how an agent already ending the Machine answers, so it does not cut the grace short. When the Driver does not confirm that the guest has stopped, mvmd waits for the VMM to end until the grace period ends. Two cases do not ask the agent at all: a Paused Machine, in which nothing runs to answer, and a grace period of zero, which sends the Driver's request alone. In every case the VMM is then ended if it still runs, and neither the agent's answer nor the guest's silence decides the outcome. A force stop and the fencing expiry send nothing to the guest.
- **Start and restore are the two ways to Running** (#2 §4, node behaviour: "boot or restore"). Both refuse to run before the network policy is applied, so a Machine is fail-closed (#2 §4 invariant 6); the default network blocks all external traffic (#2 §4, core and extensions).
- **Create Machine sets the entrypoint's command, environment, user and files, and the Machine keeps them** ([ADR 0051](./adr/0051-create-machine-takes-a-command-args-env-user-and-files-which-the-machine-keeps-and-sends-at-every-boot.md)). `command` and `args` replace the image's entrypoint and command as Kubernetes does: a `command` replaces the entrypoint and drops the image's command unless `args` is set, `args` alone replaces the command and keeps the entrypoint, and neither keeps both. `args` alone on an image pulled before the node kept its entrypoint and command apart is precondition failed, naming the image, which is pulled again to fix. `env` is applied over the image's environment. An empty `user` is the image's user, and root where it sets none; a user is in the OCI form `user[:group]` ([ADR 0048](./adr/0048-the-guest-agent-runs-the-entrypoint-as-a-named-user-and-places-files-from-the-boot-call-in-a-tmpfs-it-alone-mounts.md)). `files` are placed before the entrypoint runs. Create rejects as invalid, naming the field and the name or path, an env name that is empty, contains `=` or is given twice, and files with a path that is not absolute and clean or is under `/proc`, `/sys`, `/dev` or `/run/mvmd`, a mode above 07777, a path given twice, more than 64 files or more than 1 MiB of content in all. Every Start sends the guest the same run configuration. **Secrets are never returned:** Inspect and List report the env names, and each file's path, mode, uid, gid and size, and no value or content; no error, event or log carries one either. A snapshot carries the five fields and a restore puts them into the new Machine, so it boots later with its source's; List snapshots reports none of them, and a snapshot written before they were kept restores with the image's own ([ADR 0051](./adr/0051-create-machine-takes-a-command-args-env-user-and-files-which-the-machine-keeps-and-sends-at-every-boot.md), amended).
- **Start waits for the guest's `Boot`.** Running means the entrypoint runs ([guest.md](./guest.md) §Current decisions), so until `Boot` returns the Machine is reported in its prior state, for at most `boot_timeout`: the bound is the lifecycle's own, holds whatever the caller's context does, and a Stop sent meanwhile completes once it passes. Before it sends the boot description, the daemon reads the agent's `Info` over the same connection and refuses an agent whose `api_versions` do not include the version it speaks: the Start fails with the reason in the table above and the Machine ends Stopped. A Machine that names disks first has each plugged and found by the guest, once the agent answers `Health`, inside the same bound ([ADR 0041](./adr/0041-a-snapshot-records-its-disks-a-restore-takes-exactly-those-and-a-non-root-disk-reaches-the-guest-by-hot-plug.md)): a find does not wait for the agent to listen as `Boot` does. A restore sends no `Boot` and so reads no `Info`: the guest booted before the snapshot, and it is sent `CatchUp`, which is bounded by `boot_timeout` as `Boot` is.
- **Snapshot holds the guest paused for its duration** so memory and disk are one pair (#2 §2). It records the Driver name and version, the CPU model and the guest kernel by name and digest ([driver.md](./driver.md), [ADR 0045](./adr/0045-a-node-offers-named-kernels-a-machine-records-the-name-it-is-created-with-and-a-restore-matches-the-recorded-digest.md)), and a snapshot never moves to another VMM. It also records each attached disk's identifier, read-only flag, and the file's size and modification time, and not its contents ([ADR 0041](./adr/0041-a-snapshot-records-its-disks-a-restore-takes-exactly-those-and-a-non-root-disk-reaches-the-guest-by-hot-plug.md)); the Snapshot call accepts a Machine with attached disks.
- **Delete** exists because the client must be able to release a Machine's resources; the Driver contract has a matching destroy ([driver.md](./driver.md)).
- **Machine creation does not boot.** Create only configures, as the Driver's create does.

### Disks and resources

| Operation | Needs | On success | Repeat | State after failure |
|---|---|---|---|---|
| Create disk | A client-chosen identifier no disk file on the node has, unless the repeat below; a size in bytes above zero; a request ID | A sparse raw file of that size, formatted ext4, held by the node and by no Machine | Same identifier, request ID and size: success, with nothing made again; the same identifier under another request ID or size, or the identifier of a Machine's root disk: conflict | No disk, and nothing left in `disks/` |
| List disks | Nothing | Every disk the node holds, root disks included, ordered by identifier, each with its size and the Machine that holds it, if any | Read-only | Not applicable |
| Delete disk | A disk no Machine holds, readers included | The disk file removed | Absent: success | The disk still held by the node, with no holder |
| Attach disk | A disk the node holds; no other Machine on this node holding it, readers included; the Driver's hotplug capability, in every state, since Start plugs each attached disk and a Driver without the capability could not start the Machine ([ADR 0041](./adr/0041-a-snapshot-records-its-disks-a-restore-takes-exactly-those-and-a-non-root-disk-reaches-the-guest-by-hot-plug.md)); the Machine not Paused | Disk attached, and on a Running Machine the guest has found it | Attached with the same parameters: success, and on a Running Machine only when the VMM has the drive and the guest has found it; the call makes it so, or fails | Not attached |
| Detach disk | Attached; hotplug capability if Running, and the Machine not Paused; on a Running Machine the guest has released it | Not attached | Absent: success | Still attached |
| Set resources | Absolute target (CPU, memory) and optionally a ceiling, neither above the Driver's limits (invalid); the CPU resize capability for a changed CPU figure and the memory resize capability for a changed memory figure if Running (a Driver lacking the capability for a figure the call changes refuses the call: unsupported, nothing changed), and the Machine not Paused, since its guest cannot answer; on a Running Machine the guest brings the new vCPUs online | Target held | Same target: success | The prior value; inspect shows the value in effect |

- **A disk made by Create disk is attached like any disk the node holds** ([ADR 0036](./adr/0036-the-runtime-api-creates-lists-and-deletes-a-node-local-disk-through-the-disk-adapter.md)). The Disk adapter alone writes `disks/`; it records the request ID as an extended attribute of the file before the file is published, so a disk and the request that made it exist together or not at all, and it publishes without replacing a file, so Create Machine and Restore refuse a root disk name a client's disk already has. An identifier that cannot name a file of the directory (empty, `.`, `..`, containing a `/` or a NUL, starting with `tmp-`, or over 255 bytes) is rejected as invalid. A root disk is listed with the rest, has no request ID, and has its Machine as holder for its life, so Delete disk refuses it as precondition failed and Delete Machine removes it. Delete Machine releases an attached disk and leaves its file. The root disk's name is held for its Machine before the file is published, so Delete disk cannot remove it while Create Machine or Restore makes it. While Delete disk removes a file no attach holds it.
- **A disk has at most one holder on this node, readers included** ([ADR 0009](./adr/0009-a-machines-root-disk-is-a-sparse-raw-file-with-one-holder.md)) (#2 §4 invariant 2): an attach that would add a second holder is precondition failed.
- **A disk file belongs to the Machine that holds it** ([ADR 0038](./adr/0038-a-disk-file-belongs-to-the-machine-that-holds-it.md)). Attach disk and Create Machine give the file to the Machine's user before any Driver opens it, and Detach disk, a failed attach or create, and Delete Machine give it back to mvmd's user; a restart gives each recorded disk to its Machine again. A failure to give the file fails the call with no holder taken.
- **On a Running Machine the guest takes part in both** ([ADR 0022](./adr/0022-the-guest-finds-a-hot-plugged-disk-by-rescan-and-releases-it-before-the-unplug.md), [guest.md](./guest.md) §Current decisions). Attach puts the disk on the VMM through the Driver, then asks the guest to find it; if the guest cannot, the disk is detached again and the attach fails with the disk not attached. Detach asks the guest to release the disk first, then removes it through the Driver; the guest's release is repeatable, so a detach that failed after it, or that the daemon did not live to finish, is retried by the same call and converges. A disk the guest has mounted or otherwise claimed is refused as precondition failed and stays attached; a guest that does not answer or fails fails the detach with the disk still attached, and a client who needs it gone stops the Machine, after which no guest is involved. A disk named at Create Machine is plugged at Start as an attach plugs it, and so the guest knows it and a Running Machine detaches it like any other; the Machine's root disk and its image are not detachable ([ADR 0041](./adr/0041-a-snapshot-records-its-disks-a-restore-takes-exactly-those-and-a-non-root-disk-reaches-the-guest-by-hot-plug.md)). A Paused Machine's attach and detach are precondition failed, since a paused guest cannot answer. A Machine that is Created, Stopped or Faulted has no guest to ask.
- **A snapshot and a restore carry the Machine's disks** ([ADR 0041](./adr/0041-a-snapshot-records-its-disks-a-restore-takes-exactly-those-and-a-non-root-disk-reaches-the-guest-by-hot-plug.md)). A disk's file is the client's data and a snapshot does not copy it: the snapshot records each disk's identifier, read-only flag and the file's size and modification time. A restore takes exactly those disks as the restored Machine's, with no mapping to others, and is precondition failed, with nothing created and the reason naming the disk, when one is not held by the node, has a holder, or has a different size or modification time than the snapshot recorded, since a guest restored over a disk that moved on has caches and a journal that describe another disk. A Machine that keeps running after its snapshot may write to a disk and make the snapshot unrestorable, so a client that means to hibernate snapshots it Paused and deletes it before it resumes. The origin must have released the disks, which Delete Machine does and Stop does not, so a snapshot with disks restores one Machine at a time, and a clone of such a Machine is made from copies of its disks. The check sees what the file shows: a write that leaves both as they were is the client's.
- **A restart does not leave a half-done attach reported as attached** ([ADR 0023](./adr/0023-a-restart-settles-a-running-machines-disks-against-the-vmms-drives.md)). The daemon can die between the record, the Driver's attach and the guest's find. At start, each disk a Running Machine's record lists is checked against the VMM: a disk it has no drive for is dropped from the record and its holder released; a drive added since boot is found by the guest again, and a Machine whose guest cannot is Faulted with a reason that names the disk; a drive the VMM was given at boot, which only a VMM started before [ADR 0041](./adr/0041-a-snapshot-records-its-disks-a-restore-takes-exactly-those-and-a-non-root-disk-reaches-the-guest-by-hot-plug.md) has, is kept. Nothing is unplugged, since the guest may be using the disk. A repeated attach on a Running Machine asks the same question, finds the disk again or attaches it as the first call would, and fails while the VMM or the guest lacks it.
- **Resize names a target, not a delta**, so a repeat is idempotent.
- **A failed live resize can leave the VMM ahead of the record.** The record keeps the prior value when the Driver's wait runs out or the guest does not bring the vCPUs online, but the VMM may already hold some or all of the target, and a guest that auto-onlines memory holds it too; inspect shows the record. The window lasts until a retried set resources converges it (the Driver sends only what still differs, the guest call repeats) or a stop discards it. A snapshot taken in that window holds the VMM's figures, not the record's.
- **A Machine has a resource ceiling, the most a live resize of it reaches** ([ADR 0029](./adr/0029-a-machine-has-a-resource-ceiling-chosen-at-create-which-bounds-a-live-resize-and-the-vmms-limits.md)). Create takes one; a figure left unset is the resources' figure, so a Machine created with none has a ceiling equal to its resources, and inspect returns the effective value. Resources above the ceiling, and a memory figure of either that is not a multiple of 2 MiB, are invalid. At set resources an unset ceiling figure leaves the Machine's as it is. The ceiling changes only while the Machine is not Running or Paused; on a Running or Paused Machine a change is precondition failed. A ceiling above the resources in a figure whose resize capability the Driver lacks is unsupported. In such a figure the ceiling always equals the resources: set resources with no ceiling moves it with the target, in either direction, whereas a figure the Driver can resize keeps the ceiling it holds. A target on a Running or Paused Machine below the memory its VMM booted with is precondition failed, and the reason says that stopping the Machine applies it. A restore uses the snapshot's ceiling.

### Network policy

Create Machine and Restore each carry a `NetworkPolicy`, the Machine's for its life ([ADR 0013](./adr/0013-a-network-policy-is-an-allow-list-of-address-protocol-and-port-rules.md)). mvmd enforces it on the node ([ADR 0012](./adr/0012-nftables-on-the-host-enforces-each-machines-policy-at-its-tap.md)) and assigns the Machine's address itself ([ADR 0011](./adr/0011-each-machine-gets-a-routed-tap-and-addresses-mvmd-assigns.md)).

| Message | Field | Meaning |
|---|---|---|
| `NetworkPolicy` | `egress` | Rules for packets the Machine sends. A packet leaves only if one matches. |
| `NetworkPolicy` | `ingress` | Rules for packets sent to the Machine. A packet arrives only if one matches. |
| `NetworkRule` | `prefix` | An IPv4 prefix (`a.b.c.d/n`) or an IPv6 prefix (`x:x::/n`), which sets the rule's family: the destination for egress, the source for ingress. One address is a `/32` or a `/128`. |
| `NetworkRule` | `protocol` | TCP, UDP, ICMP (IPv4 only), ICMPv6 (IPv6 only), or any protocol of the prefix's family. |
| `NetworkRule` | `ports` | Port ranges: destination ports for egress, the Machine's own ports for ingress. Empty means every port; only TCP and UDP rules may set it. |
| `PortRange` | `first`, `last` | Inclusive bounds, `1` to `65535`, `first` not above `last`. |

- **Empty is closed.** A policy with both lists empty, the default, blocks all traffic to and from the Machine (#2 §4, core and extensions).
- **Allow only, order-free.** A packet passes if any rule of its direction matches; there are no deny rules, and the order of rules means nothing.
- **Replies are implied.** Packets of a connection an accepted packet opened pass in both directions.
- **Two Machines on one node** reach each other only when the sender's egress and the receiver's ingress both allow it.
- **Invalid is rejected.** Any of these is rejected as invalid, and nothing changes: an unparseable prefix; ICMP with an IPv6 prefix or ICMPv6 with an IPv4 prefix; a port outside `1` to `65535`; a range with `first` above `last`; ports on an ICMP, ICMPv6 or any rule.
- **Both families.** A Machine gets one address per family its node serves ([ADR 0011](./adr/0011-each-machine-gets-a-routed-tap-and-addresses-mvmd-assigns.md)). A rule for a family the node does not serve is valid and matches nothing there.
- **Neighbour discovery is not policy.** mvmd admits the ICMPv6 a Machine needs to resolve its gateway and be resolved, and drops router advertisements, redirects and router solicitations from it, whatever the policy says ([ADR 0012](./adr/0012-nftables-on-the-host-enforces-each-machines-policy-at-its-tap.md)).
- **DNS** is an address like any other: the guest's resolvers are the node's, and a policy reaching them allows their addresses on UDP and TCP port 53.
- **A snapshot carries no policy.** Restore's policy is the new Machine's, and the restored Machine has a new address.
- **Adding to it.** Name-based rules, a client-chosen address and an operation that replaces a policy are optional additions whose absence means what this table means, so they keep the version. A change to what an empty list means is a new version.

### Observation

| Operation | Result |
|---|---|
| Runtime info | The API versions served, the Drivers in service (one: the node serves the Driver its configuration names, [driver.md](./driver.md)), their capabilities (`CAPABILITY_CPU_RESIZE` and `CAPABILITY_MEMORY_RESIZE` each report one of the Driver's two resize capabilities), each one's CPU model and the limits it enforces, the kernels the node offers (each with its name and digest, the default marked), so the client can match a Machine's required capabilities and a snapshot to this node (#2 §5 design principle 1), the node's capacity, including the most Machines it can hold and how many it holds, and the prefixes it assigns Machine addresses from |
| Inspect | One Machine, as under Machine states, with the digest of the image it runs |
| List | Every Machine on the node, each with the digest of the image it runs |
| Events | A stream of state changes, Machine deletions, deadline events and Driver events, each with the Machine identifier and a sequence number that grows on this node |

- **The capacity is four totals the node measures at each call** ([ADR 0039](./adr/0039-runtime-info-reports-the-nodes-capacity-and-mvmd-admits-no-call-by-it.md)): the logical CPUs mvmd may run on, the host's total memory in bytes, and the total and the available bytes of the filesystem of mvmd's state directory, which holds the disks, the snapshots and the image store. The unit and source of each figure are on `NodeCapacity` in `runtime.proto`. It does not report what Machines are given: a client sums that from List, which reports each Machine's resources. **mvmd admits no call by capacity**: Create Machine, Create disk and Restore are not refused for exceeding it, and a host that runs out of a resource fails the call as it would. Overcommit and reserving for the host are the client's policy. The field is an addition, so the version stays `v1alpha2`.
- **The capacity also states a bound the configuration sets** ([ADR 0046](./adr/0046-a-bound-the-node-is-configured-with-is-reported-and-refused-as-precondition-failed-while-measured-capacity-stays-the-clients.md)): `machine_limit`, the smaller of the count of the VMM user range and the addresses a Machine can be given in each served prefix, and `machines`, how many Machine records the node holds, read at each call. A Create Machine or Restore that finds the user range or a prefix spent is **precondition failed**, the reason naming the resource, with nothing taken and no failure recorded under the request ID, so the same request succeeds once a Machine is deleted. This is the one admission by a figure here: the configuration stated the bound, whereas the measured totals above stay the client's to weigh. Both fields are additions, so the version stays `v1alpha2`.
- **The Machine prefixes are the ones the node assigns addresses from** ([ADR 0049](./adr/0049-traffic-to-a-configured-no-masquerade-prefix-keeps-the-machines-source-address-and-runtime-info-reports-the-machine-prefixes.md)): `machine_prefixes`, one for each family the node's `network` section names, in CIDR form with the host bits clear, IPv4 first, and empty when the node has no `network` section. The field is an addition, so the version stays `v1alpha2`.
- **A Driver's limits are the most of a Machine it accepts** ([ADR 0040](./adr/0040-a-driver-states-the-most-of-a-machine-it-accepts-and-the-inside-refuses-a-request-above-it.md)): `limits` on each Driver, with `max_vcpus`, absent when the Driver states none. Create Machine (the resources and the ceiling) and Set resources (the target and the ceiling, in any state) refuse a figure above a limit as invalid, which is REJECTED, and Restore refuses a snapshot whose resources or ceiling are above one as a failed precondition, which is PRECONDITION_FAILED, before any record or resource is made; the refusal is not remembered under the request ID. The Driver's own check at Start stays, with the same figure. The field is an addition, so the version stays `v1alpha2`.
- **A Driver's CPU model is the value Restore compares a snapshot's CPU model with.** A restore needs a snapshot whose Driver name, Driver version and CPU model equal those of the Driver in service, so a client that lists snapshots and reads runtime info tells which are restorable on this node without calling Restore. The field is an addition, so the version stays `v1alpha2`.
- **Events are resumable and not the source of truth.** The client may resume from a sequence number. If mvmd no longer holds events that far back, it says so and the client lists to resynchronise, so a missed event never leaves the client wrong (#2 §3, level-triggered reconciliation). How long events are kept is an open question.
- **One ordered sequence.** Events held after the requested sequence, then each new event, come as one sequence with no gap or repeat between them. A sequence of zero starts at the oldest event held, and a sequence equal to the latest one waits for the next event. Mvmd answers "resync required" and ends the stream when the events after the requested sequence are no longer held, when the sequence is ahead of what this node has emitted (its log starts empty at each start), or when a client that reads too slowly falls behind what is held; a stream never skips an event.
- **What is emitted.** Every committed change of a Machine's state, among them a VMM's own end, each change of the fencing deadline (armed, renewed, expired) and each event a Driver raises. A deleted Machine has no state to name, so Delete Machine emits its own event, Machine deleted, once the deletion has committed; a repeat that finds the Machine absent emits nothing. A stream ends cleanly when mvmd stops, and the client resumes from the last sequence it holds.

### Guest access

| Operation | Needs | On success | Repeat | After failure |
|---|---|---|---|---|
| Exec | Running; Guest Agent reachable; the command, and optionally an environment and a working directory | Command started under the exec identifier | Same request ID: the same exec record, never a second run | Machine unaffected; the exec record says it did not start |
| Read exec output | An exec record; an offset to resume after; Running, unless the record is already final, which is answered from the record | The output chunks after the offset, each with its offset, then the final exec record once the command has ended | Always safe; resumes from any offset still held | Machine unaffected; an offset no longer held is answered with the earliest offset held |
| Read file | Running | Content, in chunks | Always safe | Machine unaffected |
| Write file | Running | Whole new content or whole old content, never part (#2 §2, atomic write) | Same content: success | The old content |
| Patch file | Running; the base content digest and the digest expected afterwards | Content with the patch applied | File already at the expected digest: success | The old content |
| List | Running; a directory path | The directory's direct entries as a stream, sorted by path across the messages, each with its path, kind (file, directory, symlink or other) and size in bytes | Always safe | Machine unaffected; a path that names nothing is not found, and one that is not a directory is rejected |
| Search | Running; a directory path and a glob pattern | The paths under the directory that match, as a stream, sorted by path across the messages | Always safe | Machine unaffected; a path that names nothing is not found, one that is not a directory is rejected, and so is a pattern that is not a valid glob |
| Signal | Running; an exec record of this Machine whose command runs, or `entrypoint`, which the guest holds though mvmd keeps no record of it; a signal number as on Linux | The signal delivered to the command | Delivers again: a signal is not idempotent, and a repeat to a command that has since ended is refused | Machine unaffected; an exec identifier this Machine has no record of, other than `entrypoint`, is not found, a number that is not a signal is rejected, and a command that has ended is a failed precondition, the guest's own answer |
| Console | Running or Paused; Driver supports console | A session to the console | Another session; no state changes | Machine unaffected |

- **The console is a bidirectional byte stream, and a session is not an accepted call.** The first message names the Machine and may carry input, each later message carries input, and each response carries output; a later message that names a Machine is ignored. The wire message has an input field for this reason: the console takes keystrokes. The session ends cleanly when the client ends its side of the stream, when the Machine's VMM ends the console, or on the first failure of either side. It is a read path that changes no state, so there is no step to finish for a client that has gone: it does not detach from the client's context as an accepted call does ([Calling rules](#calling-rules)), and it ends with it. It holds no lock on the Machine, so any number of sessions are open at once, and none delays a lifecycle call or is delayed by one. A Machine that is neither Running nor Paused is refused as precondition failed, and so is one whose console the Driver reports gone after the state was read (its VMM ended in between); any other Driver error is failed, one that does not exist as not found, and a first message that names no Machine as rejected. The inside names no technology: the session comes from the Driver's `Console` ([driver.md](./driver.md)).
- **Output of the console before a session opened is not replayed.** A session carries what the guest writes after it opens. The daemon reads the console log only for the entrypoint's end (the record `entrypoint` of Read exec output, [guest.md](./guest.md) §PID 1 duties), so a client that needs the guest's output reads the exec's output, which the channel carries.
- **Exec is at most once per request ID.** mvmd never retries a command by itself, because a command has effects mvmd cannot see. If the Machine stops while a command runs, the exec record reports that it was cut short and why.
- **An exec record that mvmd cannot read back is that exec's alone.** After a restart, an exec and a read of its output under such an identifier fail, whatever the request ID and with the reason, and run or answer nothing; the Machine and its other exec records are unaffected, and Delete removes it with the Machine.
- **Exec output is read separately from starting the command**, so a client that lost its connection reads it again. Output is one sequence of bytes, stdout and stderr in the order mvmd received them, each chunk naming its stream and its offset in that sequence. A read resumes after an offset because the channel to the guest can reset (vsock connections reset on restore, [guest.md](./guest.md) §Rationale). The guest keeps only the newest output of each command, so an offset older than what it holds is answered with the earliest offset it holds, and the client resumes from there ([guest.md](./guest.md) §Current decisions). Once the command has ended, the exec record carries its exit code, or, for a command a signal ended, the signal number in `term_signal` (zero otherwise; `exit_code` then means nothing), and `ended_at`, when it ended. `ended_at` is the guest's clock, not the node's: the Guest Agent's reading of `CLOCK_REALTIME` when it reaped the command, which the node sets at Boot ([ADR 0044](./adr/0044-boot-sets-the-guests-wall-clock-to-the-hosts-as-catchup-does.md)) and at a restore, and between those is the guest's own. mvmd stores it with the record and passes it through unchanged, and it is unset for a command that has not ended and where the time is not known, never a time of the node's put in its place. It is on every exec and on the entrypoint's record, including one read from the console log after the VMM ended ([ADR 0043](./adr/0043-an-exited-command-carries-the-time-the-guest-agent-reaped-it-by-the-guests-clock.md)).
- **A listing and a search are streams, and no result is bounded by a message.** List and Search send their entries in messages, as many as the result needs, sorted by path from the first message to the last, so no directory is bounded by one message or by a limit the client sets on one. mvmd passes each message of the guest on as it arrives and holds none of the result, so its memory does not grow with the directory, and a read that the channel's reset cuts resumes after the last path sent, so no entry is sent twice or missed. A call that fails after some messages ended with its outcome, and what was sent stays sent. There is no bound on the result and no paging field ([ADR 0035](./adr/0035-the-runtime-api-streams-listings-and-searches-and-serves-one-alpha-version-at-a-time.md)).
- **The pattern of Search is the Guest Agent's glob.** It is matched against each path relative to the searched directory, with `/` a literal separator: `*` and `?` do not cross it, `**` does, and `{a,b}` and `[ab]` are supported, as the [globset syntax](https://docs.rs/globset/0.4.21/globset/#syntax) defines. The agent defines it in `search` in `guest-agent/crates/guest-agent/src/files.rs`, and `runtime.proto` states it on the field; a change to the glob the agent matches is a change to this contract and follows the version rule under Scope and version.
- **File content moves in chunks.** A read returns the file as a stream of chunks, so no file is bounded by one message. A write sends the path, then chunks, and mvmd commits the whole new content only when the stream ends cleanly; a stream that breaks leaves the old content, which is the whole-old-or-whole-new rule above.
- **Patch carries a precondition and a postcondition** so a retry after an unknown outcome is decidable without a request ID: the file is at the base digest (not yet applied), at the expected digest (applied), or elsewhere (precondition failed).

### Images

| Operation | Needs | On success | Repeat | After failure |
|---|---|---|---|---|
| Pull image | A reference that names a digest | Image converted and in the node cache | Already present: success | Nothing visible in the cache |
| List images | Nothing | Every image the node holds, ordered by digest, each with the digest it was pulled by, its size in bytes and the time the node stored it | The node's images at that time | Failed with no partial list; nothing changed |
| Remove image | An image digest; no Machine references the image, in any state; no snapshot references it; no Create or Restore call is locating it | The image is unlisted and the files only it reached are deleted | Already absent: success | The image is still listed, or is unlisted with some files left for the next start's sweep, never half-listed; a repeat succeeds |

- **An image reports its size and the time it was stored** (`size_bytes`, `created_at`). The size is the disk space the node holds for the image: the allocated blocks of every blob the image reaches that the cache holds, so a sparse file counts what it occupies and a blob two images share is in the size of each, and the sum over the images can exceed what the cache occupies. The time is when the node stored the image, written into the cache's index at publication; an image stored before the node recorded it reports none, which is an unset `created_at` and not the epoch. Both are facts for the client's own retention policy, which the node does not apply (ADR 0034). The fields are an addition, so the version stays `v1alpha2`.
- **A reference names a digest, never a tag.** A tag can move, which would make a repeat mean something different from the original and would defeat the integrity check (#2 §5 image security).
- **An image becomes visible only after conversion and integrity verification finish** ([image.md](./image.md)), so a failed pull leaves no partial image. Each step of a pull and the state its failure leaves are listed in [ADR 0007](./adr/0007-the-node-image-cache-is-an-oci-image-layout-published-by-one-index-swap.md) §Pull image.
- **Remove identifies an image by its digest**, the one a pull named and Create takes as its image, not by a reference: the repository a pull came from is not what the cache holds. An empty digest is rejected as invalid. A digest the node does not hold is absent, and removing it succeeds.
- **Remove refuses an image in use, with precondition failed.** An image is in use when a Machine record references it, whatever the Machine's state (a Created or Stopped Machine boots it again), or a snapshot references it, which is read from the Snapshot Store at the call and not from a cache. Create and Restore hold the image's lock shared from locating it until the Machine's record is set, and Remove takes it exclusively without waiting, so a Create in flight is refused too, atomically, and no other image is. The client deletes the Machine or snapshot first.
- **Remove unlists, then reclaims only what no listed image reaches.** One swap of `index.json` unlists the image; the blobs it reached that no remaining listed manifest reaches are then deleted, so a file two images share stays. A blob left by a failure or a crash is the start-up sweep's ([image.md](./image.md) §Node image cache, Removal). Like Delete snapshot, it only unlinks: a VMM that has the file open keeps reading it. Retention is the client's: the node removes no image by its own policy ([ADR 0034](./adr/0034-the-node-reclaims-nothing-by-its-own-policy-and-the-runtime-api-lists-and-removes-what-it-holds.md)).
- **A boot checks the image.** Start and restore measure the image's root hash before the boot begins; a mismatch fails the call in its prior state, with the reason ([image.md](./image.md) §Integrity).

### Snapshots

| Operation | Needs | On success | Repeat | After failure |
|---|---|---|---|---|
| List snapshots | Nothing | Every snapshot the node holds, ordered by identifier, each with its identifier, source Machine, image digest, Driver name and version, CPU model, root disk size, the name and digest of the guest kernel the snapshot's Machine was running, the disks it had attached, each with its identifier, read-only flag and size, its own size in bytes and the time it was taken | The node's snapshots at that time | Failed with no partial list; nothing changed |
| Delete snapshot | A snapshot identifier; no Snapshot or Restore call is using the snapshot | The snapshot and its files are removed from the node | Already absent: success | The snapshot is unchanged or already removed, never half-listed; a repeat deletes it |

- **A snapshot is a public resource, listed for reconciliation.** The list reports what the node holds, so a client that lost its own records can reconcile. There is no separate inspect call. A snapshot a Snapshot call is still writing is already listed ([ADR 0034](./adr/0034-the-node-reclaims-nothing-by-its-own-policy-and-the-runtime-api-lists-and-removes-what-it-holds.md)).
- **A snapshot reports its size and the time it was taken** (`size_bytes`, `created_at`). The size is the allocated blocks of every file in the snapshot's directory on the node: the root disk, the state files and the record, so a sparse root disk counts what it occupies. The time is the node's clock when the Snapshot call recorded it, kept in the snapshot's record; a snapshot stored before the node recorded it reports none, unset and not the epoch. The fields are an addition, so the version stays `v1alpha2`.
- **Delete refuses a snapshot a call is using, with precondition failed.** A Restore holds the snapshot until it returns, and a Snapshot call until it ends. The refusal is atomic with that call: delete takes the per-snapshot lock Snapshot and Restore already take, exclusively and without waiting, so it refuses only the snapshot in use and not another. A snapshot whose Machine exists is not refused, since a snapshot is a copy. A Machine restored from the snapshot is not using it once Restore has returned.
- **Delete only unlinks.** A file a restored VMM has open or mapped stays readable until that VMM ends, and the node's space comes back then. The reasoning is in ADR 0034.

## Fencing deadline

The deadline exists so a Machine cannot run on two nodes when its client is gone ([runtime.md](./runtime.md) §Fencing). The client chooses its length; mvmd keeps it and acts on it. It is one deadline for the node, covering every Machine on it.

| Operation | Effect |
|---|---|
| Renew deadline | Carries a length and a renewal number. If the number is greater than the last applied, the deadline becomes the length from the moment mvmd receives the call, and the renewal number is recorded; otherwise nothing changes and the current expiry is returned. The first renewal arms the deadline. |
| Inspect deadline | The length, the time remaining, the last applied renewal number, and whether it is armed, expired, or stopped everything. |

- **The client sets and changes the length** with each renewal; a shorter or a longer one is accepted. The length is any positive duration: zero or a negative length is rejected as invalid, and nothing changes. mvmd imposes no other minimum or maximum, and the length it chooses is outside this document.
- **Renewal is idempotent and replay-safe.** A duplicate or a delayed older renewal carries a renewal number that is not greater, so it cannot extend the deadline. The reason: a late duplicate must not move the expiry beyond what the client last meant. After a client restart that lost its counter, the client reads the last number from inspect and continues above it.
- **The time is counted from receipt.** Network delay between the client sending a renewal and mvmd receiving it lengthens the deadline relative to the client's own clock; the client allows for that when it picks a length. The bound the client can rely on: because a renewal is acknowledged only after it is recorded, and recorded only after it is received, mvmd's expiry is never later than the moment the client receives the acknowledgement plus the length, measured on the client's monotonic clock. That is the figure the client compares with its own validity.
- **Renewal is acknowledged only after it is durably recorded.** The reason: once the client has an answer it relies on that expiry, and an expiry mvmd could lose in a restart would be a different one. The cost is a durable write per renewal.
- **Start and restore are refused while the deadline is not armed or has expired.** A Machine started without a deadline cannot be fenced. Pause, resume and the other calls are unaffected, and the Machines already running keep running until the deadline passes.
- **When the deadline passes, mvmd stops every Machine under it by force**, with no wait for the guest, because the guest cannot be trusted to cooperate and the client's own margin is already spent. Disks are retained. mvmd then starts nothing by itself; a later renewal re-arms the deadline and the client decides what runs ([runtime.md](./runtime.md) §Boundary with gaon).
- **Guarantee: the expiry is enforced whether or not the mvmd daemon process is running, and a VM runs at most δ past a recorded expiry.** δ is the time from the clock reaching the expiry to the end of the Machine's VMM process: the enforcing process waking, exiting, and the kernel killing the VMM ([ADR 0003](./adr/0003-a-per-machine-supervisor-enforces-the-fencing-expiry.md)). It is finite and not yet a figure; it is measured with the single-node prototype ([runtime.md](./runtime.md) §Open questions). VMs survive an mvmd restart only until the recorded expiry (#2 §5 design principle 4). The reason: the deadline exists for the case where the client and mvmd's own process may both have died while the VMs live on, and a deadline that nothing counts then protects nothing. It is not weakened to "enforced once mvmd returns". A per-Machine supervisor provides it ([runtime.md](./runtime.md) §Fencing).
- **What the guarantee covers.** Failures of mvmd (a crash, a kill and a restart alike), of the enforcing process, and of the host (a reboot or a suspend). It does not cover a privileged host process that stops or traces the enforcing process while mvmd is down.
- **The client's margin covers δ.** A Machine can execute until mvmd's expiry plus δ, so the client keeps that sum, not the expiry alone, at or below its own validity.
- **Across an mvmd restart, a passed deadline is never extended.** The recorded expiry is held against a clock that keeps counting while mvmd is down and cannot be set, tied to the identity of the host's current boot, and not against the wall clock, which can be stepped backward. On start, before it serves any call, mvmd reattaches to its VMs ([runtime.md](./runtime.md) §State and stability) and compares: if the expiry has passed, it stops every Machine first; if not, the remaining time is what is left of the recorded expiry, never the full length. If the host has rebooted, no VM survived, and the deadline is treated as not armed.

## Rationale

- Contract rules: versioned interface, idempotency and defined state after failure (#2 §3 principle 5); request IDs on creating calls (#2 §5 design principle 3).
- Client-chosen identifiers and state-targeting calls are the two ways a retry becomes safe without a transaction: the first names the object before it exists, the second makes the repeat a no-op.
- The deadline's recorded-before-acknowledged rule and the receipt-time rule follow the safety requirement stated in garamsh/mvmd#4 Context: the client keeps the deadline at or below its own validity, which it can do only if mvmd's expiry is what the client was told.
- The mechanism that enforces the expiry while mvmd is not running: [ADR 0003](./adr/0003-a-per-machine-supervisor-enforces-the-fencing-expiry.md).
- Why the node reclaims nothing by its own policy, and the rule that refuses a snapshot's delete: [ADR 0034](./adr/0034-the-node-reclaims-nothing-by-its-own-policy-and-the-runtime-api-lists-and-removes-what-it-holds.md).
- Why List and Search are streams, the version is `v1alpha2` and one alpha version is served at a time, and why the pattern is the agent's glob: [ADR 0035](./adr/0035-the-runtime-api-streams-listings-and-searches-and-serves-one-alpha-version-at-a-time.md).
- The scope and why the API is not CRI: [ADR 0001](./adr/0001-mvmd-is-a-containerd-like-microvm-runtime-that-does-not-know-gaon.md).
- Why the policy is an order-free allow-list of prefix, protocol and port rules, and what it leaves for later: [ADR 0013](./adr/0013-a-network-policy-is-an-allow-list-of-address-protocol-and-port-rules.md).

## Open questions

- **A remote listener.** The API is served on a Unix domain socket on the node and nowhere else ([ADR 0004](./adr/0004-the-runtime-api-is-grpc-on-a-unix-socket-with-committed-generated-code.md)). Whether a network listener exists, and how it would authenticate, is undecided.
- **Running without a deadline.** Start and restore are refused unarmed; whether a standalone or development mode may opt out is undecided.
- **The unit of CPU and memory in Create Machine and Set resources.** The encoding is a vCPU count and a memory size in bytes, the same for the resource ceiling. A change to that encoding follows the version rule under Scope and version.
- **The format of a patch in Patch file.** The encoding is an opaque byte string. A change to that encoding follows the version rule under Scope and version.
- **How the console is framed.** The encoding is a bidirectional stream of bytes, the Machine named in the first message. A change to that encoding follows the version rule under Scope and version.
- **Authorisation of callers beyond the socket.** Authentication is the socket's filesystem permissions (ADR 0004); #2 states no finer rule.
- **Classes, durability and movement of a disk other than a root disk**: depends on #2 §6 item 9 ([runtime.md](./runtime.md) §Open questions). Create disk makes a node-local sparse raw file and nothing more ([ADR 0036](./adr/0036-the-runtime-api-creates-lists-and-deletes-a-node-local-disk-through-the-disk-adapter.md)); a root disk is created by Create Machine and deleted by Delete Machine ([ADR 0009](./adr/0009-a-machines-root-disk-is-a-sparse-raw-file-with-one-holder.md)).
- **Changing a running Machine's policy.** A policy is fixed for the Machine's life in v1alpha2; a replace operation would be an addition.
- **How long events are kept**, how long request IDs are kept after their object is deleted, and how many API versions are served at once from `v1beta1` on (alpha versions are served one at a time, [ADR 0035](./adr/0035-the-runtime-api-streams-listings-and-searches-and-serves-one-alpha-version-at-a-time.md)).
- **Whether a snapshot has an inspect call.** A snapshot is a public resource with a list and a delete (§Snapshots), and the list carries what a client needs to decide, so no separate inspect exists.
